> 设计源文件：[index.html](./index.html)
> 覆盖画布：桌面 `1440 × 900`、窄屏 `390px`

## 交接结论

这份交付物定义的是 **BONE 多智能体工作台的产品界面语言与关键状态**，不是一个可点击原型，也不是技术实现说明。`index.html` 中的按钮、列表、抽屉与决策面板均用于呈现某个确定的设计状态；它们不代表已经定义了前端交互、后端状态机、数据接口或快捷键方案。画面中的工作项、Agent 名称、命令、时间、数量、路径与仓库内容都是用来说明语义的示例，不能被当成数据模型、API 或权限契约。

产品目标是让多智能体工作始终处在一个用户可以理解、判断、追溯的表面上：系统安静地推进工作；只有目标被阻塞、需要人作判断，或结果可被接受时，才清晰地请求用户行动。

## 不可丢失的产品原则

1. **一个注意力入口。** 「需要你」是跨会话、可行动事项的唯一权威队列；它不是运行日志、任务总览或“忙碌动画墙”。
2. **事实先于叙述。** 工作中的目标、持久事实、变更声明、证据、风险与用户接受状态必须可区分，不能用一段 Agent 自述替代。
3. **上下文可见。** 用户在当前表面上能看到工作、变更、上下文和审计入口；不能把理解当前局势的关键内容藏进二级页面或要求记忆快捷键。
4. **风险诚实表达。** 真实主机、进程、网络与外部副作用的边界必须被说清。未知外部写入不能被“自动重试”“已安全”或假沙箱等表述掩盖。
5. **快捷路径不是前提。** 所有高频且重要的动作都必须有可见文字入口。未来即使提供快捷方式，也只能是渐进加速，而不是完成任务的必要知识。

## 画板与要传达的决定

| 画板 | 设计状态 | 交接时必须保留的含义 |
| --- | --- | --- |
| 01 · 默认工作台 | `IN PROGRESS` | 常态围绕一个目标展开，而不是堆叠指标的 Dashboard。左侧会话列表优先显示最后一个有意义的事实；中间是因果时间线；右侧按当前对象显示变更、上下文或审计深度。 |
| 02 · 需要你 | `SELECTED ATTENTION` | 队列条目必须说明：为何现在需要用户、阻塞哪个目标、已知事实、缺失证据与安全默认。选中态只用于展示同一上下文中的依据，不应暗示“点一下就自动执行”。 |
| 03 · 高风险决策 | `UNKNOWN EXTERNAL WRITE` | 决策面板的重点不是批准按钮，而是原始动作、事实缺口、影响边界、核查位置、每个选择的后果，以及“保持阻塞”的安全默认。 |
| 04 · 结果验收 | `EVIDENCE 3 / 4` | Agent 声明、测试通过、证据覆盖和用户接受是不同的状态。未满足所有验收条件时，界面不能宣称完成或自动接受结果。 |
| 05 · 窄屏 | `NARROW ATTENTION` | 窄屏优先保留严重性、为什么需要用户、事实依据与下一步；不应用隐藏快捷键或静默降级来换取表面简化。 |

## 信息架构

### 桌面三栏的稳定职责

| 区域 | 负责回答的问题 | 不应被替代成 |
| --- | --- | --- |
| 会话轨道 | 哪个目标最值得关注？最新可追溯事实是什么？ | 只有“运行中 / 已完成”的任务清单 |
| 主工作面 | 这个目标如何走到当前状态？哪些事实、变更与工作项构成因果链？ | 原始聊天 transcript 或纯日志瀑布 |
| 对象详情 | 当前选择的工作、变更、上下文或审计证据究竟是什么？ | 模态窗里没有来源的摘要 |

### 注意力状态的阅读语法

每个需要人处理的事项，至少应能读出下面五件事：

1. 为什么是现在需要用户；
2. 它阻塞或影响的目标；
3. 已知的、可追溯的事实；
4. 缺失的证据或尚未作出的判断；
5. 系统在用户暂不处理时采取的安全默认。

## 风险与验收的行为护栏

这些是后续补齐交互设计、文案和实现时不可弱化的产品约束：

- `request_sent` 存在但 `result_received` 缺失的写入请求属于**未知外部影响**，而不是可直接重放的失败请求。
- 未知写入默认保持阻塞；关闭、稍后处理或离开当前表面都不能被解释为“拒绝”“失败”或“允许重试”。
- “已发生 / 未发生”必须伴随核查位置和判断依据进入审计记录；它们不能只是无依据的一键断言。
- 只读动作与会造成外部副作用的写入动作必须采用不同恢复规则。
- 证据覆盖率不是完成率。验收界面应明确区分：条件、支持或反向证据、当前判定，以及用户最终的接受、带风险接受、等待或退回。
- 当后台继续运行时，除非产生可行动事项，不抢夺用户当前焦点。

## 视觉语言

色彩承担稳定的状态语义，但每一处关键状态仍须同时有文字标签、图标或明确说明，不能只依赖颜色。

| 语义 | 设计色 | 在界面中的用途 |
| --- | --- | --- |
| 当前焦点 / 人类行动 | 橙色 | 当前会话、需要用户推进的显性操作、焦点状态 |
| 等待证据 | 黄色 | 待决策、外部核查、尚未证实的条件 |
| 未知外部影响 | 红色 | 可能产生重复副作用、需要人工判定的风险 |
| 待验收 | 紫色 | 证据尚不完整、结果尚未被用户接受 |
| 已证实 | 绿色 | 可追溯事实、通过的证据与已验证条件 |

界面采用深色、终端原生的层级，但不应为了“终端感”牺牲可读性。等宽字体用于状态、证据、路径、时间、审计回执和小型元数据；正文与决策说明需优先保证扫读与理解。

## 当前交付物的边界

已经交付：

- 一份完全自包含的静态 HTML/CSS 设计稿；
- 五张关键画板及相同的状态色、层级与阅读语法；
- 桌面与窄屏的设计样张；
- 明确的静态设计状态标识与视觉语义图例。

有意未定义：

- 真实的交互行为、焦点管理、动画、API、数据模型和后端编排；
- 具体快捷键集合；
- 所有边缘状态与错误恢复分支的逐项交互规格；
- 可用性测试结果、无障碍验收和真实终端尺寸下的排版验证。

不要把“有意未定义”补成默认行为。例如，高风险写入的恢复规则不能因为实现方便而退化为自动重试；验收也不能因为数据暂缺而直接显示为完成。

## 后续设计工作建议

在进入实现前，建议先以这份设计稿为基线补齐以下设计决策：

1. 为「需要你」队列定义完整的进入、暂停、恢复、过期与已处理状态，并验证它仍只包含可行动事项。
2. 为未知外部影响定义统一的证据字段、来源展示方式与审计回执格式。
3. 为验收定义「等待」「部分接受」「带风险接受」「退回工作」「接受」的结果语义和理由要求。
4. 对窄屏的信息优先级做真实内容压力测试，确认不会裁掉风险、理由或安全默认。
5. 以可见文字入口完成主流程，再把少量快捷方式作为可发现、可关闭的加速层进行设计。
6. 用一份状态 / 事件矩阵把这五张样张转成可评审的行为规格：`对象 → 事实 → 风险级别 → 可见动作 → 安全默认 → 用户判定 → 审计事件 → 恢复分支`。

## 评审与交付检查表

- [ ] 用户能够在不阅读日志、不记忆快捷键的前提下，说出当前为什么需要自己。
- [ ] 每个高风险事项都能展示影响、已知事实、事实缺口、安全默认与选择后果。
- [ ] 写入结果未知时不会出现自动重试或虚假的“已安全”表述。
- [ ] 证据覆盖、Agent 完成声明与用户接受状态在文案和视觉上清楚分离。
- [ ] 桌面与窄屏都保留了相同的风险与判断语义。
- [ ] 实现或后续设计变更没有把工作台退化成指标 Dashboard，或把注意力队列扩张成全部任务列表。
