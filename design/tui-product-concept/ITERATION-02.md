# BONE TUI · 从整体工作台到局部细节

2026-09-10 · 第二轮产品设计提案。本文重新组织设计叙述，并提出对第一轮布局的调整；现有 HTML 尚未按此重绘。

## 1. 第一眼：一个主工作区，两种阅读深度

BONE 的画面围绕当前会话展开。用户进入后，首先看到自己正在推进的事情，以及可以继续表达要求的位置。会话导航退居侧面，深入资料在需要时展开。

推荐结构是：**默认两栏，查看详情时展开为三栏。** 左栏切换会话，中央承接当前工作的交流与推进，右栏解释当前选中的内容。中央始终是视觉中心。

```text
默认工作台
┌──────────────────────────────────────────────────────────┐
│ BONE · 当前工作区                       需要你 2   设置 │
├──────────────┬───────────────────────────────────────────┤
│ 新建会话     │ 当前会话标题                   查看详情   │
│              │ 当前目标 / 一行进展                       │
│ 当前会话     ├───────────────────────────────────────────┤
│ 其他会话     │ 你的要求                                  │
│              │                                           │
│ 最近会话     │ 工作进展、答复与结果                      │
│              │                                           │
│              ├───────────────────────────────────────────┤
│              │ 补充要求…                         发送    │
└──────────────┴───────────────────────────────────────────┘

展开详情
┌──────────────┬─────────────────────────┬──────────────────┐
│ 会话导航     │ 当前会话                │ 所选对象   关闭  │
│              │                         │                  │
│              │ 保留正在阅读的内容      │ 摘要             │
│              │ 与选中位置              │ 相关资料         │

```

两栏让常态拥有足够阅读空间。第三栏承接深入查看，使用户可以对照原文与详情。能力的丰富程度通过阅读层级承载，不要求所有信息一直同时出现。

右栏由用户主动打开。后台新事件不能擅自展开它。关闭后，主区域恢复宽度，阅读位置与输入内容保持不变。

## 2. 画面如何分配空间

左栏约 22–26 个字符列，保持窄而稳定。中央使用剩余主要空间。右栏展开时以约 36–44 列作为设计起点，宽度需要用中文正文、路径与证据内容验证。

约 160 列可探索三栏；120 列优先保留导航与主工作区，查看详情时可以临时收起左栏。80 列以主工作区为主，“会话”入口打开列表，详情进入完整阅读页。40 列收敛为单列，保留标题、返回、输入和必要操作。

这些尺寸是待排版验证的起点。先保证正文和输入可读，再决定同时显示多少面板。现有 390px 样张仅作视觉参考，不代表新增手机产品需求。

顶部承担工作区身份与全局入口。会话标题在主区顶部。模型与连接状态可在输入附近以次要文字出现，更多信息进入设置或详情，避免标题栏堆满编号、权限、时间与模型参数。

## 3. 左栏：找到并回到一件事

左栏以会话名称为主体。当前会话用低对比底色与窄焦点标记确定位置；每项最多附一行有意义的进展，例如“正在验证”“等待你的回答”“上次执行中断”。

导航位置需要稳定。建议按用户固定项与最近使用组织，后台活动不自动重排整列。待处理数量集中在顶部“需要你”，用户可主动浏览需要判断的事项。

“新建会话”是可见入口。搜索、归档与更多管理动作在会话列表内部展开。项目目录、任务树与 Agent 组织不同时占用这条导航栏。

## 4. 中央：从要求到结果的连续阅读路径

主区顶部用标题和一句进展帮助用户定位。正文承载用户要求、面向用户的答复、必要的工作进展与结果。

用户提出“修复恢复后重复写入”后，先保留这句要求，再显示对目标的简短理解。工作被拆成几项时，正文出现紧凑的工作概览，用户无需先学习 Agent 的组织结构。

正常进展在既有位置收敛更新。有值得阅读的新结论，再作为正文段落出现。工具输出默认使用短摘要，完整正文在展开或详情中阅读。任务之间的内部往返不逐条占据主时间线。

阶段结果使用明确标题、简短说明与产物入口呈现。用户需要检验时，选中结果打开右栏，中央仍保留原来的工作脉络。

输入固定在中央底部，默认表达“补充要求”。回答问题时，输入上方出现正在回答的问题，以及取消回答入口。发送前不要求选择调度模式。

## 5. 右栏：从摘要逐步进入证据

右栏只解释当前选中的对象。标题说清正在看哪个任务、哪项结果或哪份背景。

详情先呈现摘要，再呈现相关资料，最后才是原始来源。内容多时使用文字明确的分类入口，不把每一类内容都做成同等醒目的卡片。

查看“当前工作的背景”时，第一层说明工作参考了哪些内容；第二层区分会话共享背景与当前任务资料；第三层提供摘要对应的原始记录。用户先理解范围，再决定是否核对来源。

查看结果遵循相同层级：先说交付了什么，再说验证了什么与仍缺什么，最后提供文件与详细证据。用户接受结果的操作放在相关结果内，操作后保留判定记录。

## 6. 视觉语言：用重心与留白组织信息

整体使用深色背景、等宽文字和字符网格。区域通过细分隔线与轻微明度差区分。正文、标题与次要信息依靠明度、字重与空行建立层级；真实终端不靠网页式字号缩放容纳内容。

最醒目的是当前阅读内容、当前焦点与下一步操作。导航与元数据降低对比度。橙色用于焦点和主要行动，避免所有入口同时发亮。

状态色在需要解释状态时出现：绿色表示已证实，黄色表示等待或需留意，红色表示明确风险，紫色表示待验收。每个状态同时有文字，普通活动不必逐行附高对比标签。

常态使用连续文本与适度空行。边框主要用于区域边界、输入区及确实需要成组对照的内容。减少卡片套卡片、彩色标签和重复分割线，使视觉注意力集中于当前工作。

## 7. 从日常使用逐步进入复杂场景

初次进入仍使用同一个工作台结构。没有历史时，主区说明可以开始什么；未配置模型时，在输入附近提供设置入口，草稿仍可编辑。完成配置后沿用当前会话和草稿。

工作开始后，左栏留下这件事，中央承接交流。用户想知道更多，才展开工作项和右侧资料。多智能体的组织细节随阅读深度逐步出现。

需要判断时，在会话内提出明确问题，同时更新全局“需要你”计数。打开该入口后，主区展示待处理事项，选中后再查看依据。普通澄清在会话内回答，影响较大的决定使用专门的决策界面。

重新进入中断会话时，回到熟悉的中央阅读区，说明记录已保留、执行已中断及受影响工作。外部操作结果确实未知时，才展开核查内容。

这些场景共享一套空间结构：找到会话、理解当前工作、深入所选对象。不同底层状态不需要各自成为同等重要的独立页面。

## 8. 静态设计稿的讲述顺序

开场是一张普通工作状态的完整画面，让读者直接认识 BONE。随后介绍左、中、右职责，以及右栏展开前后的空间变化。

接着展示同一件工作的连续样张：提出要求、查看进展、打开结果详情。示例保持连续，避免每张图都换背景。

整体与正常使用清楚后，再介绍上下文详情、需要判断、中断恢复与设置。最后对照宽窄终端，解释空间不足时各区域如何收起与返回。

完整产品范围仍包括会话管理、模型与连接、工作与子任务、上下文、产物、验收及恢复。介绍按用户理解界面的顺序展开，功能细项留在相应章节与交接附录。

## 附录：代码基线与交接约束

核对基线为 `56920ca3`，上轮设计提交为 `5a64d9c6`。以下用于交接，不作为设计介绍的开场。

- 当前 App 输入包含文本、请求身份与问题引用；精确定向任务、强制新工作或排在某步骤之后需要额外定义。已接收不能推断为已理解或已采纳。
- Core 已区分会话公共背景与任务局部上下文，按需生成摘要并保留原文。App 尚未完整公开摘要、来源和输入审阅事实；上下文详情需要对应产品投影。
- Core 恢复记录与结构化状态，旧执行按中断处理。历史恢复不能表示外部进程仍然运行，未知写入不能自动重试。
- 当前 App 未定义独立的用户接受、部分接受与带风险接受事件；完整验收需要对应契约，不能用输入结束替代。
- 建议 Esc 用于返回或关闭，停止使用可见入口；与 docs/tui.md 旧方案的差异属于待统一的产品决定。
