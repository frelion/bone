# C · 连续记录与原生输入

设计稿，160×40 字符，左24 / 中96 / 右40。右栏默认空白，无伪入口。本轮不改产品代码。使用审美 skill 的层级、间距与密度规则；没有新增角色前缀、编号、Dashboard 或全局工具栏。

## 方向及自我否决

C 初稿仅把以前的输入框削成单行，正文沿用旧稿几何。主 agent、A 和 B 都指出这仍是旧图，且单行底色像选中条，节约的行数变成了空白。这项批评成立，初稿不推荐。

当前重画版不是初稿换色：它把正文改为两轮连续工作记录，代码脱离大底色卡片，文件定位与代码连续显示；输入改为透明的两行编辑视窗，和正文同轴，元信息紧邻，正文获得原来用于卡片和无意义大间距的行数。

它与 A 的竞争点是：BONE 是否需要一整块高对比编辑台，还是更适合终端原生 prompt。它与 B 的竞争点是：是否需要局部框角才能辨认输入。C 不将边框少直接等同于好看；输入的可发现性是本案需要被反方推翻的风险。

## 已知代价与落地限制

透明编辑区的鼠标命中范围仍要定义为完整矩形，不能只允许点文字；空白区域可点。空态/焦点切换可能仍不如A的明确台面可发现，必须拿实机验收，不能仅以“终端感”解释。

原生prompt常见于shell和其他CLI，因此本案不主张靠一个箭头建立品牌。独立性来自三栏稳定空间、低干扰连续记录、精确输入与对象阅读行为，最终用户是否喜欢不能靠设计师投票保证。

## 最新稿复审与最终反方意见

已实际查看 `a/revised.jpg`、`b/revised.jpg`、`c/revised.jpg`。

A 改为6行、删除“继续对话”和顶部色带标题之后，编辑台真正成为独立且可识别的工作面。它比C的透明prompt更容易发现编辑范围；不应为了保护自己的方案而忽略这一点。我支持A按实际内容采用4/5/6行编辑台，条件是空输入默认4行，而不是把6行固定到底。

仍反对A三点：模型行贴台面上沿过紧、空稿继续留6行、文件路径在工具摘要和代码头重复（当前截图仍有，A已接受修改）。编辑台不能因为更完整就自动获得更多屏幕面积。至少用空稿、两行稿、六行长稿分别检查真实空间成本。

B 的回复阅读节奏仍是最好的，可吸收它的两轮分组与紧凑工具呈现。但用户历史消息与编辑区都是相近灰色块，身份分化较弱。C重画后解决了旧布局照抄、过疏和单行选择条问题，但透明编辑区的鼠标范围、空态发现性仍比A弱，不推荐作为最终默认。

最终不建议把三案拼成“都有一点”：A稳定停靠面与C透明prompt属于相反结构，要选择其一。吸收B正文节奏不等于把B的输入块或C的箭头一起塞入A。

主agent另实际核查运行时提交：App会接受输入并进入Queued，再尝试投递。因此最终可写“enter 提交”，不能在设计文案承诺立即打断或steer。C旧画面中的“enter 发送”只是通用措辞，最终收敛稿应采用已核查的“提交”。
