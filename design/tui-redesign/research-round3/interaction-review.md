# 第三轮：交互与信息架构独立评审

2026-09-10。设计提案，未改产品代码。检查了 `docs/tui.md`、前两轮 PLAN / DIRECTION 及第二版主图。第一方资料见文末；网页文档阅读与主图观察是事实，以下改法是设计判断，并非已完成的可用性验证。

## 判断

第二版的问题不是缺一种更好看的青色。它把标题、用户消息、工具、Job、代码、输入都作为彼此分离的长条摆放，信息关系靠大段空白解释，用户却要从三个 Working 中判断同一件事。最重要的编辑位置只有一条变亮的横线，与标题分隔的语法相近；细线没有表达出“这里正在接收键盘”。

原版值得保留的是输入表面可识别、消息与过程有明暗区分、少量暖色集中于动作。需要改变的是成组方式、焦点可靠性和状态冗余，不必为了区别 OpenCode 把所有温度与质感一起去掉。

### 优先级

1. 当前用户在写的内容是唯一主要交互目标；编辑器有真实光标、清楚的内边距和表面。
2. 最终回答与当前对话正文是阅读主角；工具是附属的过程证据。
3. 左侧只是目录；右侧只有主动打开具体对象后才成为阅读目标。
4. 状态说明一次即可；同一事实不要同时成为标题、对象和输入区的装饰。

## 三个尺寸的几何

沿用已确定的断点，不以审美为由重新谈判三栏。各栏宽度包含自己的边距；这里的字符数是 ASCII 单元，中文占两格。

| 终端 | 左 | 中 | 右 | 中栏正文可用宽度 | 纵向预算 |
|---|---:|---:|---:|---:|---|
| 160×40 | 24 | 96 | 40 | 88（左右各4） | 局部标题2 + 历史31 + Composer7；无活动/单行时 Composer 可降至5 |
| 120×30 | 24 | 96 | 隐藏 | 88（左右各4） | 标题2 + 历史23 + Composer5；详情替换中栏 |
| 80×24 | 切换页 | 80 | 切换页 | 74（左右各3） | 标题2 + 历史17 + Composer5；多行输入增长至9时历史仍13 |

160与120的中栏宽度恰好一样，这是既有断点的优势：关闭右栏后无需再次把同一消息改行。80列由内容驱动折行，不能直接缩放宽屏图。正文、用户文本与Composer文本共享起线；代码只额外缩进2格。所有行宽按grapheme测量。

Composer默认1行可见编辑文本，增长到最多6行（40高）、4行（30高）、4行（24高）。结构固定4行：可选状态/间隔占1、上内边距1、下内边距1、模型与当下动作1。单行默认5；活动行替换间隔，不额外顶起一行。40高输入7行总高只是设计稿常见3行输入示例，不应硬编码。

80列会话页标题提供可点击返回；普通正文视图仍可通过 `/sessions` 进入。不要在窄屏长期保留三个tab。打开详情时只替换中栏的历史+输入可视面，草稿完整保存在每会话状态里；局部 `← Conversation` 是返回，不是全局动作栏。宽度恢复后同一详情回右栏，阅读锚点不丢。

## 状态的唯一主要位置

当前执行状态完整表述放Composer上方的一行，句子回答“现在正在发生什么”。标题只显示会话名，稳定不跳。左栏继续满足“标题+短状态”契约，但当前项运行状态压成短词或活动符号；背景会话保留 `Needs you` 等需行动状态。完全去掉当前项短状态属于契约变更，暂不必做。

| 状态 | Composer附近主反馈 | 历史 | 左栏 |
|---|---|---|---|
| Idle | 留空；不用 Ready | 已完成内容 | Draft / 已有事实短态 |
| Submitting | Saving… | 用户发送项可呈pending | 不提前显示Working |
| Saved, not executing | Saved · choose a model to continue | 用户内容已保存 | Needs setup |
| Running | Working · 按App实际活动命名 | 实际工具过程 | 当前简短，后台Working |
| Waiting for answer | Reply to this question | 真实问题在来源位置 | Needs you |
| Stopping | Stopping… | 过程不伪装完成 | Working直到确认 |
| Failed | 动作可执行时显示Retry / 配置入口 | 关联位置显示具体原因 | Failed或实际投影 |
| Completed | 回到Idle，不永久挂Finished | 回复/结果自然成为终点 | Completed等已有短态 |

工具自身结果仍有局部状态，例如 `Tests  12 passed` 是结果，不应被去重成一个全局Done。当前主反馈是执行状态，Job详情是对象状态；两者不同才各显示。图稿禁止同一个Working原样出现三遍。

## 工具呈现

最小条目：`动作  目标  具体结果`，目标保留主辨识段，必要时中间省略路径。成功读取可以按连续过程组成 `Read 2 files`，展开后才看每条路径；不按固定两条就折叠，也不把失败藏入成功组。

- 单条工具成功：一行足够。仅有可读详情时才有 `›`。
- 运行中：一行正在操作的目标；不用虚构elapsed、花费、进度百分比。
- 错误：默认展开2–4行可读原因，保留查看完整输出入口；恢复动作只来自真实可执行能力。
- 代码片段属于回答的论据，语言标记弱化，不要每段都套和输入同等明度的大块。
- 主动展开后保持展开；新的快照不能再次折叠用户正在看的输出。
- 自动收起只适用于尚未手动操作的已完成过程，而且用户正在读旧内容时要保持位置，不能让下方文字上跳。

## 四组状态机

### 焦点

`Composer ↔ Conversation ↔ SessionRail`，右栏只有已启用对象时才能进入 `ObjectReader`。菜单是覆盖层，保存returnFocus。焦点与选中对象分开：打开会话是持久选择，在列表移动只是候选；阅读右栏时中栏来源保留浅底，但不再出现焦点色。

编辑焦点：真实光标+输入表面局部短标记。列表/对象焦点：候选行浅底+左端1格标记。区域标题可以额外点亮一个小标记，但不能只靠整条横线表达焦点。只允许一个键盘焦点目标；非焦点区不显示假光标。鼠标hover轻量且不选择。

Ctrl+方向沿既有空间映射；普通↑↓在Composer编辑文本，在正文滚动，在列表移动候选。菜单活动时捕获自己的↑↓。PageUp/Down允许滚历史而保留Composer编辑焦点。词移动沿既有Alt+方向。

### 编辑与提交

`Editing(revision) → Submitting(requestId, revision) → Saved → Executing / Waiting / Finished`。等待回执时仍可继续编辑，回执只能清掉对应revision。发送期间Enter不能用新的requestId复制同一次输入。粘贴永远只插入。草稿、光标、选区、撤销分别按Session保留。

生成中发送是否排队/steer必须按App语义显式说明；不能照抄其他产品的Send now而后端只支持普通submit。若未接线，设计稿只展示继续写与停止，不展示“插队”按钮。无模型保存后的恢复不重新submit。

### 命令

`Closed → Open(query, candidate) → Close / FillArguments / Execute → ReturnFocus`。菜单锚定Composer，遮盖历史、不移动Composer；最多6条可见结果，选中项始终可见。命令名固定列，描述次要，快捷键右对齐；窄屏先省略描述，再省略快捷键，不截掉命令名。

Esc关闭保留输入；Enter选中命令，有参数的填入输入，不凭空执行不完整动作；Tab补全。空结果有一句可读说明，不能出现看似可选择的空高亮。菜单footer只显示当前层的 Enter/Tab/Esc，背景不再提示Esc stop。

### 对象与滚动

`Closed → Loading(objectId, generation) → Content / Error / Expired → Closed`。对象来源焦点在打开时记录，关闭准确返回来源；期间切会话使旧generation失效。80/120读详情与160右栏是同一状态的不同布局，resize不能重取身份或自动关闭对象。

历史 `FollowingTail ↔ ReadingAnchor(messageId, offset)`。滚轮或PageUp进入ReadingAnchor；新消息只产生局部 `↓ New reply`，不会抢焦点或跳尾。显式返回最新才恢复FollowingTail；resize按内容锚点排版，不保存旧屏幕行号。

Esc优先级：关闭菜单 → 取消局部选择/返回详情 → 停止当前执行 → 无动作。一轮按键只命中一个分支。局部返回优先于停止；Stop是明确的可点击目标，不能只有隐藏键盘路径。

## 第一方研究依据

[Zed Agent Panel](https://zed.dev/docs/ai/agent-panel)：官方明确区分thread pane焦点与message editor焦点的导航；主动follow agent是单独动作；工具/历史能力依不同agent而异。启发：焦点决定键语义，阅读与追随不要混成一件事，不能画后端不支持的操作。这里借鉴行为原则，不复制Zed界面与快捷键。

[VS Code Terminal Shell Integration](https://code.visualstudio.com/docs/terminal/shell-integration)：命令有独立边界与成功/失败修饰，用户能导航到命令，sticky scroll让输出保持来源。启发：工具输出必须有稳定来源与可导航边界，长输出在视窗中可保留一行来源；无需持续展示工具图标、卡片标题和重复状态。

本子任务直接查看了BONE已有主图，阅读了上述实时网页文档；没有声称实际运行Zed/VS Code或做过它们的截图体验。参考图的视觉研究由并行reference_research负责，避免把网页文字当成实机观察。

## 设计验收前的五条走查

交叉讨论收敛：visual_critique同意状态去重、局部焦点，并建议段内连续、段间1空行、身份切换2空行；输入可作为唯一明显闭合编辑轮廓，代码表面更暗、用户消息更弱。reference_research同意来源selection与键盘focus分开，辅助栏密度应高于对话。用户消息仍遵守现有“不显示YOU/BONE标签”契约，不能把新增身份标签当作本轮默认选择。

1. 把所有强调色临时变灰，仍能认出焦点、消息来源、工具与正文吗？
2. 在当前图上圈出所有运行状态，相同事实是否多于两个位置？标题中是否有可删的状态？
3. 从输入打开命令，关闭后光标准确恢复；Esc没有停止后台工作吗？
4. 160→120→80→160过程中同一对象、草稿与阅读位置是否都能说清楚？
5. 运行、等待配置、需回答、失败，四张图的主要行动能否一眼识别，且有真实App能力支撑？

## 候选A及SVG walkthrough复审

实际看过 `boards/01-candidate-a.jpg`，并阅读第三轮 `draw.py` 的全部绘制和链接代码。A的编辑区比第二版明确，暖灰细框也比整条青线更能表现输入范围；标题去掉运行状态是正确的。以下是交付前必修，而非实施后再说的边缘条件。

| 必修 | 当前证据 | 修订 |
|---|---|---|
| 左侧状态必须是状态 | `shell()` 对所有当前项写“当前会话”，空态与blocked同样如此 | 浅底已说明当前选择，第二行应写App真实短状态。运行态“执行中”，空态“草稿”，blocked“需要配置”。标题不写状态；Composer活动描述更具体，不形成三处Working复读 |
| 右栏焦点可见 | `shell(focus='detail')` 的focus形参未用于渲染，详情态只有Composer失焦，右栏本身没有焦点指示 | 标题前一个焦点符或局部短边标记即可；不得整块右栏变成选中底色 |
| 返回到来源对象 | 详情关闭/返回的SVG链接直接指向01，01已有Composer光标 | 新增“返回对话对象”态：右栏空、来源行焦点标记、Composer无光标。通过Ctrl+↓或点击输入进入01。演示和文字规则一致 |
| 查看文件按钮有去处 | `message()` 将“查看”绘为蓝色，却未建立link | 补一张展开2文件列表的状态并连通返回，或从稿里删掉查看这个动作。不可把纯装饰按钮称可交互walkthrough |
| 新建不会抹掉会话列表 | 04菜单/new链接03，而03只剩新会话一个列表项 | 区分首次空态与既有会话中新建。新建后的状态应保留旧列表，并新增选中“新会话”；后台旧会话继续执行的事实可保留在原项 |

其他应修但不应阻止视觉方向评审的细节：

- 目前只有/menu、/new、close、Job入口有SVG链接；不能宣传整个菜单或键盘均可操作。walkthrough说明清楚哪些是链接跳转，SVG本身未实现Esc/方向键事件。
- 主图模型名 `Worker · GPT-5.5` 是fixture，应在图外说明，不要让用户以为是其真实运行配置。
- `compose()` 把光标固定画在最后一行首；占位文本态合理，多行真实文本态应画在符合示例编辑位置的字符后，不能覆盖第一字。
- 输入框光标在单行placeholder前，此时placeholder只作提示；输入有实际文本后应使用正文色并消失placeholder。
- 已打开Job行仍链接06本身，若显示▾收起语义，应点击返回对象态；或者把符号换成稳定的打开标记，避免承诺折叠但无行为。
- `/model`可见但尚未连到模型选择状态；blocked页对应动作必须在最终走查里有可见后续，至少以待实施状态明确，不用“选择后即可继续”假装恢复链路已验证。

密度方面：代码块和用户消息仍与Composer使用同一个INPUT色，代码块占了大幅面但只有三行；建议代码背景降低一级，留白从六行缩至五行；保留回答段间一行、身份切换两行的节奏。这是审美优化，不替代上面的行为必修。
