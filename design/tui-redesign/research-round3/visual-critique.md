# 第三轮 · 独立视觉审查

审查日期：2026-09-10。范围是静态设计与第一方视觉材料；没有运行第三方软件、不改产品代码。以下意见是设计判断，不是用户研究结论。

## 看过什么

已读前两版 BOARDS、DIRECTION 与两份 draw.py，并通过图像工具查看两张 160×40 主对话 JPG。浏览器实际查看了：

- [Zellij 官方基本操作教程](https://zellij.dev/tutorials/basic-functionality/)及其[分栏示意原图](https://zellij.dev/img/zellij-new-panes.png)。图中非活动 pane 用低对比边框，当前 pane 的边框与标题共同变亮；标题占据边框行，底部操作提示贴到统一状态栏。多个 pane 没有重复大号页头。对 BONE 有价值的是：边界承载焦点和范围，标题嵌入现有几何，不额外增加横线。不要照搬彩色全屏快捷键带或给三栏都套框。
- [Charm 官方 Crush 发布文章](https://charm.land/blog/crush-comes-home/)中的[官方演示视频](https://charm.land/crush-demo.238e393760cf226.webm)。实际查看了开始及完成工具调用的帧。侧栏同组信息紧凑，组间一空行；对话正文与工具输出通过缩进、局部底色、少量语法色分层。高饱和紫色大 Logo 非 BONE 所需；视频中多处文字对比偏低也不应照搬。参考的是密度差与局部色彩，而非这个配色本身。
- 搜到 Lazygit 官方仓库但所查看的首张图片是品牌图，没有将它冒充实际 UI 证据。

## 为什么第二版不如第一版

1. **颜色退让的同时，层级也被拿掉。** 第二版的用户消息、代码、Composer 都用 #1d2324 表面，代码取消了语法色。三个不同任务的区域变成三条同权横带。第一版至少有明确的编辑侧线和代码色。
2. **换了颜色，没有换构图。** 两版同是 24/96/40，正文几乎同一起线，用户消息—说明—工具—代码—结论的各段都间隔2至3空行。第二版还在头部加长横线，正文开始从第5行推到第7行，左栏条目由3行周期变成4行周期。可读内容更少，视觉更松散。
3. **唯一的焦点变成一条远离文字的长线。** Composer 的上边线从中栏一端贯穿另一端，光标被放在 placeholder 左边，状态/模型又移到容器外。看起来像文档分隔，并不自然表达“这是可以编辑的区域”。
4. **重复状态抢注意力。** Working 同时在会话列表、页头、Job行出现。它没有形成优先级，只重复同一个词。这个问题与交互审查 agent 的判断一致。
5. **静态示例制造了空旷错觉。** 第一版正文只有约16行内容，第二版更少，却铺过25行高。低对比宽条及默认空右栏叠加后，界面像未完成骨架。右栏留白是明确要求，不能填无关统计来掩盖；必须让有内容的中栏形成完整、稳定的构图。

## 推荐给主设计的 160×40 格方案

以下坐标从0计数。坚持左24 / 中96 / 右40，不把改栏宽当作改善的捷径。

- 左栏 x0..23，中栏 x24..119，右栏 x120..159。左右栏底 #151515，中栏 #101010，默认右栏不画标题、不画占位框。
- 左栏 x2 起线；当前会话文本 x3，选择块 x1..22。标题 y1，Sessions/新建入口 y3，首条 y5；每条最多2行，条目间1空行。当前会话的 Ready/Working 不与正文重复；后台会话 Needs you 可以保留。
- 中栏标题 x27,y1；不加 y3 全宽规则线。正文主起线 x29，右界 x114（86格），表面外边缘 x27..116（90格）。标题、正文、编辑区只使用外起线27和内起线29两套基线。列表符号/折叠控件占x27，文字仍从29开始。
- 正文从 y4 开始。段内连续行；同一回复的段落间1空行；发送者变化间2空行；工具同组逐行连续，不单条加底。标题后0或1空行，不在每一个短句前后塞2空行。
- 建议同屏节奏：y4 用户消息；y5 第二行（如有）；y7..8 Agent解释；y10..11 工具组；y13 小标题；y14 解释；y16..20 代码；y22..23 结果/列表。y25可开始第二个用户追问，演示真实多轮，不用一句话撑满整个屏幕。
- 用户消息底 #1a1a1a，至多上下各0至1空行，保留项目约定的中性细竖线作身份提示，不加 YOU/BONE 前缀、不使用彩色粗侧线。正文白 #e8e6e0。静态已发送内容不使用输入边框。
- 代码背景 #181818，与 Composer 的 #242424 明确区分。代码首行是 rust / path 的淡标签，代码正文最多2种语法辅助色（例如关键字 #c6b0df、字符串 #d8bd88），变量/标点仍中性白。不能整段染焦点色。代码整体内缩2格即可，避免 x+3再x+2 的多层漂移。
- Composer 是屏幕上唯一常驻闭合编辑轮廓。x27..116，单行输入时 y33..37，共5行：边框上沿含 Draft 或 Replying to…；y34留空；y35正文从x29开始；y36可容纳模型信息（或留空，必须全方案一致）；y37下沿。y38一行局部操作提示。可用终端 ╭╮╰╯ 字符（真实终端glyph，不用SVG圆角），也可直角细线；边框活动 #bbb8ae，非活动 #56544f；只光标/小焦点标记使用强调色，不整圈高饱和。
- 如需执行状态，将 y31 固定为紧凑局部状态行，显示具体 “Running checks…” 与 stop 入口，空闲不占用额外状态标签。不要把 Working 同时放进标题。建议轻微骨白暖色，但不要暖橙左粗条。
- 多行输入向上增长，正文真实滚动，避免逐次增加表面内padding。正文和模型/快捷键的排布对3行、6行输入保持不变。
- 右栏激活时 x123 起线，y1对象名称；详情标签与值相邻或同一行，不要 Goal 到值隔一行再到下一组隔三行。8行内容不要铺到30行。对象产生的diff或结果可以占主要区域。

## 我与交互 agent 已讨论的决定

同意状态去重；同意当前焦点不能只依赖整条细线变色，应有局部光标/选择标记；同意工具输出以组来展开，不让每条日志抢视觉权重。静态稿必须有真实多轮、长代码、菜单和多行编辑来验证密度，不能只用空态证明好看。

主设计准备两种几何候选：开放对话+有边界Composer、紧凑文档/编辑器。我的初步偏好是前者，因为保留第一版已有的可亲近感，修正层级和密度；不建议突然把 BONE 做成全屏规则线/多窗格调试器。应在相同内容、相同字符尺寸下比较，不能用不同内容制造某版更好的假象。

## 第二次审查：实际查看候选 A / B 后

已通过图像工具查看 `01-candidate-a.jpg` 与 `02-candidate-b.jpg`，并读本轮 draw.py 核对位置。A/B 使用同内容、同160×40尺寸，比较有效。它们与前两版语言和文案不同，故只能判断结构、层级改善，不能把信息含量变化当作严格优劣测量。

**判断：推荐 A；A 明显修复第二版的弱输入焦点与重复状态，但还不足以直接宣称“已经很好”。B 不推荐。** B 的 01/02/03/04 不对应可解释的章节或交互对象，正文不变、密度不变，额外数字只是装饰；平面输入再次回到第二版边界不清的问题。

A 必须完成以下有限修正：

1. **统一输入与正文起线。** 当前用户块外边x27、正文x29，Composer外边却x26、文本x28。改 Composer `x=l+3,w=c-6`，文本/模型 `x=l+5`，右側操作距框2格。只有两套基线，不让输入整体向左漂一格。
2. **三个表面区分。** INPUT只留给Composer，建议 #242424；已发送用户块 #1b1c1f，中性竖线；代码 #18191c。中栏 #111214 继续可用。这样即使截去文字，也可分辨编辑控件与已发内容。代码语法色保留。
3. **进一步压缩规则间距。** 当前代码从y16开始，lang y16、code y18..20，底色又多占y21；结论y24/25、Job y28。改代码y15..20，lang15、code17..19；结论y22/23；Job y26。分段靠语义分组，不机械地每块前后空2行。不要为了填满160×40去添加虚构任务或统计。
4. **左栏需要处理的状态胜过重复普通状态。** “当前会话”重复选择高亮事实；多个“已结束”也占用同等信息高度。经主agent核对标题＋短状态是当前明确契约，因此保留统一两行；将“当前会话”改为真实语义状态：执行中／草稿／需要配置／就绪。Needs you 用较亮正文+小标记。列表语义状态与当前局部执行细节可有限重复，不再在页头和Job复制同一个 Working。此次不引入时间戳、摘要或单行项。
5. **焦点边框略退让。** A的闭合轮廓方向对；整圈黄线可改中性骨白活动边框，暖色留给具体工作状态和小焦点标记。不需要回到全灰，也不需要模仿OpenCode橙色粗侧线。图中 box-drawing 连接略有断续，稿件在真实字体下还需确认。
6. **右栏详情另行压缩。** 目前目标/值相隔一行，各组跨度6行，八行正文铺到28行。改y4类别，y6目标标签、y7值，y10完成条件、y11值，y14范围、y15值，y18状态、y19值。空白集中在组后，不把标签与其内容拆开。当前页只凭源码核对，生成后仍需实际查看图。

修正后仍需看：一张包含真实两轮对话的长正文截图、菜单覆盖、3行输入、右栏焦点切换。现有主图可用于判断风格，但不能单独证明新密度在长任务中成立。

## 最终主稿复审

再次实际查看 `boards/final-main.jpg`。此前要求的输入起线、USER/CODE/INPUT 表面层级、段距及真实列表状态已得到改善；Composer成为明确编辑控件，默认空右栏没有被塞入无关内容。当前达到可让用户判断方向的静态稿水平，不等于用户接受或实机体验验收通过。

剩余仅两点：

- 左侧“需要回答”仍与普通“就绪”使用相近灰色，待用户介入的会话缺乏扫描优先级。建议只提升该状态文字到正文白或局部强调色，可加一个字符的标记；不把整条背景染色。
- JPG中闭合边框的字符连接仍略断续。应记录为实际终端字体与字符连接尚未验证，实施时在目标终端检查，不将静态稿当作实机轮廓效果保证。

不建议继续为区别OpenCode添加装饰或改换配色；后续改动应由用户对这一方向的评价与真实长对话/输入操作走查推动。
