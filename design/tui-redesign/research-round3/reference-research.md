# 第三轮设计参考研究

2026-09-10。研究对象是第一方公开材料；通过联网搜索定位来源，再用 Browser 实际查看页面上的截图/GIF/视频帧。没有运行这些应用，不能把宣传帧称为实机体验。以下视觉判断是本轮设计推论。产品代码未改。

## 参考与可用语法

### Crush：层次来自不同内容的表达，而非全局去色

来源：[官方 README](https://github.com/charmbracelet/crush)。浏览器实际观察官方 Crush Demo 的空态及代码变更帧：主内容采用开放布局，代码变更以独立浅底区域组织；局部语法色与 diff 行底色承担信息识别。旁栏内容明显次于主内容。紫色 Logo 和装饰斜线形成很强品牌联想。

BONE 可借：开放的回复、分组的工具结果、必要语法色、少量强操作强调。不可直接搬：紫色巨型 Logo、斜线边饰及其整体组合。V2 去掉语法色，不是原创，反而丢失阅读帮助。

### Glow：连续文档也可以有明显节奏

来源：[官方 README](https://github.com/charmbracelet/glow)。实际观察 Glow UI Demo 阅读帧：正文有控制的阅读宽度；标题、链接、引用、列表和表格的处理不同。引用靠短侧线，标题靠字重及颜色，列表连续紧凑；底部状态条很薄。

BONE 可借：Markdown 依语义排版，不对每一段加卡片；空行只分段落/组，不把每个工具动作拆散。不可照搬其独立阅读器的居中窄页面、紫色品牌块及标题配色全套。

### Yazi：三栏的价值是当前对象与预览的持续对应

来源：[官方功能展示](https://yazi-rs.github.io/features/)。实际观察 Scrollable Preview、Visual Mode & Bulk Rename 的视频显示帧：三列高密度排布，选择状态是清晰整行底色，右侧直接呈现对象内容；底部极薄状态行提供模式/位置，不用三个大标题证明有三个区域。

BONE 可借：选中对象与右栏保持对应、一次一个阅读对象、区分 selection 与 focus。不可搬：文件管理器的逐行密度、图标满列、Vim 模式状态栏。BONE 的正文仍应有正常段落呼吸。

### Zed：辅助面板要比主内容更安静、更紧凑

来源：[官方 panel 文章](https://zed.dev/blog/new-panel-system)及[文中原始截图](https://images.zed.dev/blog/new-panel-system/overview.png)，文章日期为 2023-05-31，作为历史设计参考，不声称代表当前全部 UI。实际查看截图：多个工作区由薄边界与轻微背景层级分隔，工具栏高度很低；文件侧栏的紧凑密度和主编辑区不同。

BONE 可借：稳定细边界、主辅不同密度、恢复上次阅读位置。不可搬：GUI 标签栏、可拖拽 dock 的完整机制、像素字号层级。终端稿必须尊重整字符格。

## 对前两版的批判

已实际查看 `boards/02-conversation.jpg` 和 `bone-direction/boards/02-conversation.jpg`。

第一版已有可保留的基础：近黑底色、明亮正文、较紧凑的左栏、代码与输入的局部底色。相似感主要是暖色粗侧边 Composer 与整套黑灰组合，不是所有暖色都应该被禁用。

第二版把差异化误解成换冷青、加横线、减少颜色。问题很具体：

- 顶部横线与输入横线几乎等长，两个结构强调争夺注意；输入的横线比内容更有存在感。
- 左栏每条会话之间的空白增多，没有增加可理解的信息，反而像没有排完。
- 用户消息、代码、输入区均使用接近的灰青底色；都安静，却没有清楚主次。
- 代码失去颜色后成为另一块正文，语义区别变弱。
- Working 在左栏、标题、Job 重复，容易显得原型式堆状态。
- “骨白”“案头”等概念无法替代具体的行距、对齐和互动反馈；用户首先看到的是屏幕，不是品牌说明。

## 推荐策略：保住完成度，通过结构建立身份

不设“与 OpenCode 不同的颜色数量”这种目标。常见颜色、浅底输入框、Markdown、命令搜索都不是某个产品独占的语法。避免直接复刻的是高度可识别的组合外形。

推荐采用更成熟的第一版基底，独立组织三个组件：

1. 左栏为紧凑会话目录：选择底色可辨，正常状态不重复播报；后台需要用户/未读才提醒。
2. 中栏为连续工作记录：用户消息局部底色；回复开放；工具以动作+对象紧凑成组；结果层次优先。
3. Composer 有完整且轻的局部边界，与历史消息明显不同；当前执行状态只在其上方完整出现一次。

右栏保留既有默认空白约定，仅在主动打开对象时显示。其独特价值来自同名对象、来源选中、返回恢复，而不是加装饰连线或为填空塞仪表盘。

需要在最终稿验证：把颜色暂时去掉仍能辨认用户消息/回复/工具/编辑；焦点和选中不混淆；140列中栏可读；活跃状态不会推挤输入。审美应以可视稿比较，不把主观评价伪装成分数测量。

## 多 agent 讨论

与主设计 agent 已达成：候选 A 恢复近黑/清晰正文、语法色、紧凑分组与局部完整 Composer 边界；避免“为了不同而减掉好东西”。

与交互 agent 已达成：当前状态集中在 Composer 上方；左栏只保留必要后台异常/未读；主动滚动后不自动跟随；中栏来源选中与右栏阅读焦点可以共存。以上是推荐设计决策，未声称已实现或获得用户批准。

## 候选稿独立复审

实际查看本轮 `boards/01-candidate-a.jpg` 与 `boards/02-candidate-b.jpg` 后，仍推荐 A，但并不是所有 A 的细节都应保留。

A 的闭合 Composer 明确了“正在编辑”的范围，与上方已发送消息浅底块区别成立。近黑底、清晰正文、有限语法色恢复了第一版的阅读质量。它已移除 OpenCode 暖橙粗侧线的组合外形；也未出现 Crush 强紫 Logo、Yazi 高密度文件行或 Zed 标签栏的整套移植。当前没有明显的新 clone 对象。完整终端输入框本身是通用语法，不能因为其他工具也使用边框就再次删掉。

B 的编号沟槽 01—04 在小图里显得像行号，但实际上编号不同段落；其行为和编号粒度没有解释，04 又落在代码与列表之间，无法立即判断它标识哪块内容。如果它没有消息跳转或可引用语义，就是额外的视觉负担。下方横线 Composer 也再次接近 V2 中“入口不明确”的问题。不能为了原创感保留这一层。

A 的剩余纠正建议：

- 运行状态、回复正文、编辑文本现在有三条近邻起线。边框可以外扩，但运行状态文字应和主正文统一，输入文本也应建立明确的等量内边距。
- “已读取 2 个文件 · 查看”和“草稿恢复 · 查看任务详情”属于两个可展开入口，却使用不同间距与文字结构。统一为“动作/对象 + 末端查看动作”，可减少原型拼接感。
- 左栏每条会话仍有“当前会话/已结束”等常态第二行，影响密度；当前浅底已说明选择状态。应优先把第二行留给需要回答、未读或草稿这类有意义的信息，或让普通元信息更安静。
- 不要把这张静态主稿称为已经证明了 BONE 品牌独立。它证明的是更好的通用基础；BONE 自己的空间关系需要对象打开、来源选中、返回恢复等配套状态来体现。

A/B 比较没有提供“外部用户已认可”证据，也不是品牌识别测试。这里是跨 agent 的设计判断，最终仍供用户视觉评审。
