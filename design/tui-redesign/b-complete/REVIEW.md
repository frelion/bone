# B 完整设计：反方验收与能力边界

状态：已完成初稿审查与最终SVG结构/导航复核，最终结论见文末。用户偏好 B 的构图，但明确指出颜色对比度低、仍不好看；这不等于视觉批准。本文不改产品，不改主绘图，不另起候选方向。

## 五条硬条件

1. 保留 B 的连续多轮正文与小型写作表面。增加状态时不得扩成后台、全局工具条或 A 的整宽停靠台。
2. 文字必须清亮，辅助字、选择、输入表面必须可辨。改善对比度不等于切浅色主题；色值或对比率合格也不等于审美通过。
3. 菜单、问题、错误、工具长输出与右栏阅读都要有进入、执行、退出、焦点恢复。任何局部 Esc 都不能误触全局停止。
4. 提交、已接收待处理、运行、停止中、回执不确定必须分清，草稿、光标、阅读位置和请求身份不能因切状态丢失。
5. 每项产品事实与动作区分当前已接线、App已有但TUI待接、尚需新增能力及示例fixture。右栏默认空白；不得把Git、证据、测试统计画成已有事实。

## 依据与证据强度

已读 [当前产品契约](../../../docs/tui.md) 与 [B方案及修订](../adversarial/b/PROPOSAL.md)。B的后续中性深炭、单prompt修订优先于该文档前半段的绿调和残缺角标描述。

本轮已针对真实代码检查：

- `crates/bone-tui/src/state/update.rs` 的 `submit` 不因Agent运行而直接禁止提交；它阻止重复未失败的提交，保存提交时草稿revision，失败后相同文本复用RequestId。
- 同文件 `UiEvent::Submitted` 仅在revision与文本匹配时清草稿，`SubmitFailed`保留待重试身份。
- `crates/bone-app/src/session.rs` 的 `Command::Submit` 先 `accept_input`，发布状态并返回receipt，然后尝试 `deliver_queued`。因此“enter 提交”有依据，“立即打断当前工作”无依据。
- `crates/bone-app/src/api.rs` 的 `SubmitInput` 有 `reply_to: Option<QuestionId>` 与 `answer(question)`；当前TUI `submit` 仅构造普通 `SubmitInput::new`，没有在这条路径写入问题身份。问题回答设计须明确TUI待接。
- Session公开API有 `retry`、`control`、`stop`、`snapshot`、`observe`、`history` 等；存在API不等于每个UI入口都已实现。

本轮不重做外部视觉研究；之前实际看图证据保留。静态图只能验证布局和文案，不能证明键鼠行为或异步正确性。
