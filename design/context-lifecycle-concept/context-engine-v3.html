Current architecture · 2026.09

Context 不是一包聊天记录，
而是 Core 对事实的有界投影。

App 管产品与存储，Runtime 管执行与提交，Kernel 管事实和规则，模型只提出建议。Session 记共同历史，Job 记局部工作；每次调用都从这两层重新组装上下文。

一句话

原始事实只存一份；谁能看到什么、什么时候压缩、重启后如何恢复，都由 Core 的确定性规则决定。

01 / MAP

先把四层放回各自的位置

最容易混淆的是 Kernel、Router 和 Runtime：一个是规则，一个是轻模型，一个是执行容器。

Product shell

App

拥有产品 Session

配置、SQLite、UI 视图、Workspace 写门禁和外部写核查。

注入 ports
Execution host · Core

Runtime

执行 Effect

调用模型和工具；等待 durable 提交成功后，才发布状态并启动后续动作。

async actor
Authority · Core

Kernel

裁决所有状态

管理 Input、Routing、Job、Call、Record、权限、预算和提交资格。

deterministic
Model roles

Router / Worker

提出建议

Router 轻量分配意图；Worker 理解、计划、执行、委派，也能纠正交付理解。

untrusted proposal
真正的边界：模型不能直接改状态；App 不能替 Core 拼执行记忆；Runtime 不能在存储确认前发布候选状态。

App 分配产品输入身份，Kernel 接受完整原文并建立 routing。相同 ID 和相同内容可重试；相同 ID 配不同内容会被拒绝。

  • 合并仍未关闭的 routing 批次

03 / MEMORY

一份 Record，形成两种记忆

Session 和 Job 不各存一套聊天记录。它们从同一事实账本选择不同范围，服务不同问题。

Session Context

“这段长期协作里，大家共同知道什么？”

进入Input、公开 Reply、用户 Clarification、root Published / Outcome
不自动进入私有 Note、child 内部成果、工具全文
压缩产物独立 SessionCheckpoint + 最近公共原文
给谁之后的 Router 和 Worker 调用
问题“选 A 还是 B？”+回答“第二个”
问题和回答一起保留，不能只留下脱离语境的“第二个”。

Job Context

“为了完成这项工作，这个 Worker 被允许知道什么？”

进入输入交付、工具结果、私有 Note、child Outcome、显式 evidence
权限由 owner 树和显式引用决定，不能横向偷看
压缩产物自己的 Checkpoint + 尚未处理的局部 Record
给谁这个 Job 下一轮具备资格的 Worker
摘要不会推进“已读”水位；被摘要覆盖的输入仍需 Worker 真正审阅。
04 / BUDGET

压缩不是定时清理，而是组装失败后的受控动作

真正检查的是完整模型请求。Session 和 Job 单独看都没超限，相加后仍可能放不下。

SessionJob当前必需事实输出余量
1. 组装生成完整 Core DTO
2. 测量按最终序列化字节
3. 减负先分页工具正文
4. 压缩选 Session 或 Job 前缀

两层共用一种协议

  1. CompactScope 决定压哪一层
  2. 只压合法旧前缀，保留新尾部
  3. 草稿必须非空、限长、确实变小
  4. 无收益或关键事实本身过大，明确失败
05 / DURABLE

重启恢复的是 Core 状态，不是一段旧模型对话

App 提供存储实现，Core 定义必须保存什么以及怎样恢复。当前只接受一种严格协议。

Kernel 候选状态新 Record + 结构化 Snapshot
→
DurablePort 提交commit_id 幂等 + expected_revision 冲突检查
→
Runtime 发布只有 ACK 后才能观察并启动依赖动作
硬规则：“写入 future 被丢弃”不等于“数据库没有提交”。未确认提交必须显式报告，等事务结束后重新读取权威状态。
容量

Core 状态按 512 KiB UTF-8 分段，在一个 SQLite 事务中提交；累计历史不受单文档 8 MiB 上限卡死。

投影

App 用独立 core_through 记录产品视图进度，恢复后只补尚未投影的 Record。

来源

每条 Record 和 Call 的原始 Runtime 来源是必需字段；缺失就报错，不猜当前 Runtime。

06 / EDGES

这次重构专门封住的边界

这些不是附加优化，而是 durable、取消和上下文语义能成立的前提。

永久 pending 也能按时关闭

FIXED

shutdown grace 到期后返回最后已确认状态，并标出 pending_commit；不会把候选状态冒充已保存。

启动途中关闭不会错过 Runtime

FIXED

关闭请求持续观察 Runtime 安装；即使请求发出时还没有 Agent，也会在安装后立即转发 shutdown。

取消的压缩不能改写任务结果

FIXED

暂停、取消或重配置后，迟到的 compact 成功/失败只结束调用记账，不提交摘要，也不终结 requester。

恢复提交不会漏掉产品投影

FIXED

即使 Core 已提交而 App 尚未登记新 Runtime 就再次崩溃，core_through 和来源索引也能补齐且只补一次。

root 知道输入为何交给自己

FIXED

root 卡片持有固定大小 latest_handoff，可沿 previous 链回读；目录不会无限累积输入列表。

旧状态被明确拒绝

STRICT

没有旧单文档迁移、bootstrap 注入或字段推断。已删除字段、未知字段和缺失必需来源都会报错。

07 / STATUS

现在已经是什么，未来才可能是什么

把实现与想法分开，后续讨论才不会再次把提案误认为系统能力。

能力状态当前做法
轻 Router + 强 Worker已实现Router 只 Assign / Read / Clarify；Worker 负责计划与执行
Session / Job 两层上下文已实现共同事实账本，不同权限投影，分别 checkpoint
组合预算与按需压缩已实现先分页，再选择合法前缀压缩，失败显式可见
Core durable 与严格恢复已实现提交后发布，分段存储，来源必需，旧协议拒绝
按任务选择不同 Worker 模型以后当前所有 Worker 共用一个模型配置
误投后的原子负责人转交以后Worker 可纠正理解和澄清，但没有 transfer 协议
后台预压缩、惰性加载与 GC以后当前同步按需压缩；进程仍保留完整原始记录
The mental model

把 Context Engine 看成“事实账本上的视图系统”。

事实

Kernel 记录发生了什么，模型不能直接改。

视图

Session 与 Job 按公开性、权限和预算选择事实。

连续性

Runtime 提交后再发布；重启从严格 durable 状态恢复。
