# BONE TUI 0.6：独立交互批评

日期：2026-10-02。角色：独立批评者。仅修改本文件；没有改生产代码、既有报告、使用个人凭据或调用真实模型。

## 随机触发前的三项根因

这一节先于随机构想写入。随机种子由主代理通过真实 OS 随机源抽取并提供：`7d23c2b28a2a9b7d7a0c7885`。固定映射词为信号灯、显微镜、铅字排版；本代理不再次抽签或重新选择喜欢的词。

1. **动作的后果不能从动作位置读出。** Enter 可以发送、插入补全、执行命令、展开或选中；Esc 可以关闭、改发新要求或跳回输入；Ctrl+C 又受选区影响。设计把上下文记忆交给用户，却没有在触发点展示足够明确的后果。
2. **执行状态按实现事件排列，用户决定按工作结果发生。** 当前把工具全文、事件原文、对话和常驻通知叠在时间线上；用户要判断的是正在做什么、刚才要求何时生效、失败后的下一步、哪些写入未确认。状态文字被截断或过期时，用户只能翻事件猜。
3. **视口没有稳定的阅读契约。** 窄屏切换整个主面板，展开、详情、搜索、焦点和追随尾部各自管理状态；关闭详情会落回输入，阅读旧内容不显示未读。可操作不等于能顺畅完成阅读后继续工作。

## 证据边界与空间账本

读过 `src/tui.rs`、`src/tui/view.rs`、既有 `pty/*.json` 以及真实软件的 `01/07/14/24/35-screen.txt`。既有 JSON 是 PTY VT 输出的文本重放，HTML 是重放展示，不是终端截图。真实软件捕获有 diff 更新后的词间空格缺失（如 `defretry_after_seconds`），不能据此指控源码或排版。原报告的 failure 是 **80×20**，shell-live/question-target/reading-detail 是 **110×30**；下表的 80×24占用来自布局源码计算，另标新实测。

修正记录：最初按帮助文本行数推断80×24会遮住Ctrl+C说明；实测推翻这一点，该行恰好可见。保留的缺陷是命令列表/关闭说明被裁且帮助无法滚动，80×20正文更少。

本轮额外实测：`target/release/bone` 配合 `tests/tui_pty.py` 的隔离 loopback Fixture、合成凭据，在 **80×24** 启动、F1、PageDown、Ctrl+Q；没有真实模型请求。结果：帮助打开，PageDown 不改变画面；Ctrl+C说明在第19行可见，命令列表和末尾关闭说明不可见。同一release另用真实本地shell隔离fixture确认：输入`PRESERVE_ORIGINAL_DRAFT`、Shift+Left选中末尾T、Ctrl+C后剪贴板为T且paused=false；右移取消选区、Ctrl+C后unknown_writes出现。保留草稿时Ctrl+P搜索reconcile、Enter打开待核查列表、Enter进入详情、Esc关闭，草稿变成`/reconcile <call-id>`，原草稿消失。另以422响应验证失败，**80×24、退出前**捕获：header“就绪”，正文“执行失败 / ProviderResponseError: status 422”，notice“已保存 · 等待纳入执行；运行中可追加新要求”，footer末尾停在“? tokens ·”。没有创建新证据目录；结果记录在本文件。

80×24：常态 header 1行 + 输入3行 + footer2行 = **6/24行**，对话18行。多行草稿把输入撑到7行时，固定占用10行、对话14行。工具默认显示标题1+正文6+省略1+空白1 = **9行**，两个折叠工具就填满常态阅读区。inline候选最多6条+边框2 = **8行**，覆盖已有对话；最长草稿时仅剩6行未覆盖正文。详情/帮助在80×24 inset=(6,3)，外框68×18，内文 **66×16**。

真实颜色以源码核对：background/text Reset，主强调 Cyan，次要字 DarkGray；工具正文整体 DarkGray；失败消息标题 Red，完成工具标题 Green，运行 Blue，未知写 Yellow；活动选择背景 RGB(36,49,65)。既有 HTML 的页面背景和字体不是终端环境证据，因此本报告不声称实测某主题的对比度。

## 九个由固定随机词强迫生成的交互构想

生成约束：每个词产生三种改变动词、操作顺序或层级的方案；三种方案不共享同一个“加状态栏”的解法。任何方案都保持一个Session只有一个Agent，Job不作为可选对象，未知写/lease/版本检查/停止保护不被UI替代。

| 词与编号 | 操作构想 | 它改变的交互层级 | 取舍/排除理由 |
|---|---|---|---|
| 信号灯 S1 | **先确定下一动作，再显示历史。** 将一个始终可见、最多2行的当前动作放在输入上方：执行中“Ctrl+C暂停”，已暂停“Ctrl+R继续”，等待问题“Enter回答X”，未知写“Enter查看待核查”；Enter只在该动作被显式聚焦时执行 | 用户先读Agent当前可做什么，底层事件仅解释这项决定 | 保留为方向A；不能让状态动作占用所有Enter，输入有自己的发送语义 |
| 信号灯 S2 | **发送前逐条预览转向。** 新要求发送时先弹“追加/替换/暂停后执行”选择 | 把每次新输入都变成执行策略决策 | **否定**：这会要求用户理解调度，诱发用户选内部Job，还把日常插话变成两步。现有输入版本语义应由Agent承担 |
| 信号灯 S3 | **取消回复只解绑路由，不换焦点。** Esc在问题目标上先明确显示“已改为新要求”，目标作为独立可聚焦字段；退出读原文时Esc只回阅读，不能同时解绑 | 分离“离开某层”和“改变发送对象” | 保留；将回复目标当用户可理解的问题ID，不能显示内部child/root Job |
| 显微镜 M1 | **逐层钻入同一个事实。** 摘要→结果文本→工具参数/持久事件；每次进入记进入点，Esc逐层返回同一位置 | 持久原文是证据第三层，普通阅读不从event/kind/revision开始 | 保留为方向B；不删原文，只改默认入口 |
| 显微镜 M2 | **固定两项并排比较。** 在历史中选任意两个事件，对比本次插话前/后的参数及结果 | 跨时间比较取代顺序滚动 | **否定作为默认方向**：80列分成两栏仅约37列，代码/命令频繁断行；一般用户不应先挑事件才能知道新要求是否生效。可作为远期高级读法 |
| 显微镜 M3 | **跟随一个正在运行的输出。** 选当前工具“观察输出”，只显示stdout/stderr尾部；离开保留锚点，运行结束同一对象转成最终结果 | 实时观察是可进入的阅读状态，未交付内容不是普通Agent消息 | 保留；观察不暂停、不切Agent、不引入Job选择。完成后不能默默替换用户已经滚开的行 |
| 铅字排版 T1 | **按阅读意图配行数。** 工具默认压成1行结论+1行证据入口，Agent交付按段落展示；Enter展开“结果”而不是整块事件，参数再下钻 | 结果与证据占用预算分开；折叠从截前6行变成选有用层 | 保留；结论必须机械来自工具状态/exit等，不得由UI伪造成功总结 |
| 铅字排版 T2 | **在正文旁持续保留编辑栏。** 80×24把输入/回复目标固定占右24列，剩余正文54列 | 输入和阅读永久并排，不需要焦点上下移动 | **否定**：中文正文及代码被迫窄到频繁换行，长输出比现在更难读；固定空间并不能自动解决焦点语义 |
| 铅字排版 T3 | **让异常插入阅读节奏。** 正常完成工具压成一行；失败/未知写自动显出原因首段和下一动作，用户正在读旧消息时只增加未读标记 | 信息展开由“用户需要判断”驱动，异常优先获得行数 | 保留；不能把异常自动滚到用户视口抢读位，完整证据仍一键进入 |

三次反驳不是以实现成本否定：S2迫使用户接管调度；M2毁掉窄屏阅读；T2毁掉正文宽度。它们各自有表面吸引力，但违背主要使用路径。

## 两种成熟终端交互的调查

1. **less 668，正式发布日期2024-10-17。** 本机 `less --version` 确認668；没有在本轮对其所有交互做PTY实测。官方固定版本手册列出`F`跟随新增输出、Ctrl+C停止等待、单引号返回先前大幅移动位置/标记、`/`搜索，和可配置提示。由资料推断：阅读位置、跟随模式、回到先前阅读点可以成为明确的一组操作；这比让一条记录既当普通对话又当实时预览更容易形成契约。不要直接照搬Ctrl+C的less行为到Agent执行：BONE必须显示这是暂停执行还是退出观察。来源：[668发布说明](https://www.greenwoodsoftware.com/less/news.668.html)、[v668官方手册源代码](https://raw.githubusercontent.com/gwsw/less/v668/less.nro.VER)。这里选择已安装且可固定的668，不声称它是当前最新（官网现有710于2026-09-17发布）。

2. **lazygit 0.65.1，正式发布日期2026-09-13。** 本机没有lazygit，未安装/实测，以下仅来自官方版本文档。Files层的Enter进入逐行操作，main staging层Esc返回Files，菜单Enter执行，Input/Confirmation层Enter确认；每个上下文有分别生成的键位说明。由资料推断：多层界面可以使用同一按键，但必须有稳定父子返回和可见的当前动作范围。BONE当前Esc直接Input，破坏了详情→选中工具的父子关系。来源：[0.65.1发行页](https://github.com/jesseduffield/lazygit/releases/tag/v0.65.1)、[固定版本键位文档](https://raw.githubusercontent.com/jesseduffield/lazygit/v0.65.1/docs/keybindings/Keybindings_en.md)。没有从其Git命令功能推导BONE应暴露Job，也不复制多面板布局。

## 完整方向A：当前动作常驻、对话继续作为主阅读面

选用S1/S3/T1/T3。默认80×24分配：Session/模型简头1行，正文17行，当前动作1行，输入3行，当前焦点键位1行，状态1行，共24行。多行编辑最多增加2行；剩余正文15行。workspace/model长名移入Session信息，不与暂停、失败、待核查争一行。这里的“当前动作”是Agent层语义，不展示可选Job。

**执行。** 正文可滚，输入始终可写；当前动作显示“正在运行 shell · Ctrl+C暂停”，完整命令在证据里。Ctrl+C无条件暂停执行，Ctrl+Y复制，停止动作文字随状态改变。用户不需要先切回输入。工具结束只形成一行“检查完成 · exit 0 · Enter结果”，不把启动、结束、结果三份记录都挤进主文。

**插话。** Enter发送新要求后，该要求旁有自己的“已保存→Agent已采纳”标记，采纳标记只在已有引擎事件证明后改变，不以调用次数猜。运行的旧观察结束或失效时明确标注“已停止/被新要求取代”；等待问题时输入上方目标行显示“回答：问题短摘要 [改发新要求]”，用户显式操作解绑，Esc只处理当前阅读层。用户不选Job。

**失败。** Session当前动作持续显示“执行失败 · Enter读原因 · 输入新要求”，直至用户实际采取动作或开始后续工作；不以quiescent推导“成功/就绪”。如果写入未知，优先显示“待核查写入 · 执行已暂停”，失败是历史证据。自动展开错误首段但不改变用户阅读锚点。

**阅读。** Tab进入阅读，↑↓选摘要，Enter进入结果层；d再进持久原文。每层Esc回进入前层、选择、滚动偏移，最后一次Esc才回输入。读旧消息时常驻状态记录“新增3条 · End回最新”，不抢滚动。正文数据trim后用事件ID恢复锚点，否则给出“该条在持久历史中”的明确入口。

**恢复。** Ctrl+R只有在当前动作明确显示可恢复且保护条件满足时恢复；未知写时跳到核查说明，保存现有草稿作为独立草稿，不执行复放。核查填写用专门的有标签输入状态，Enter只记录观察；记录完成后继续暂停，用户看见“核查已记录 · Ctrl+R恢复”。关闭/退出核查恢复原草稿。重开Session保持暂停，保留草稿与绑定问题ID；失效目标不改投其他问题。

弱点：默认正文仍混合用户输入与机械工具结果，若工具非常密集，摘要虽节省行数，用户还是会在时序里找最终交付。方向A适合先消除D01–D09的行为冲突，不能以此宣称所有视觉问题已解决。

## 完整方向B：执行现场与证据阅读分成两个明确层

选用M1/M3/T1，S3作为发送契约。80×24默认“现场”：header1行、正文17行、行动状态1行、输入3行、上下文操作1行、Session简讯1行。现场正文只包含用户输入、Agent已交付段落、正在运行的一个观察对象、失败/待回答事实。工具完成收束为相邻证据入口，不另起一个Activity事件宇宙。进入“证据阅读”时输入缩成一行“草稿已保留 · Esc返回现场”，给原文20行；不能在证据层意外把字符发送给模型。

**执行。** 跟随当前观察对象仅在现场尾部且用户明确处于跟随时更新；工具stdout/stderr分别有标签，最终结果保留同一对象身份。其他工具结果作为证据数量出现，用户不选内部工作单元。Ctrl+C仍全局暂停，观察层不覆盖这条保护手势。

**插话。** 用户在现场输入，发送后请求旁显示本条采纳状态。用户在证据层按专用“返回输入”动作回现场、还原草稿与阅读位置，再Enter发送；证据层保持查看期间执行可继续，输入不会隐藏丢失。问题目标独立于阅读层，新的待答问题只增加指示，不接管正在编辑的草稿。

**失败。** 当前观察对象转成失败结果，并在行动状态保留“失败”；正在证据层时不强制返回现场，只在一行状态显示“新失败1 · 查看”。未知写把执行状态设为暂停及待核查，原文中的工具参数是核查的证据而不是可重复执行按钮。

**阅读。** Enter从结果摘要进入20行结果正文，下一层才是含event ID/参数的原文。PgUp/PgDn按真实内容高度滚；搜索先在当前结果找，用户显式切“整个会话”才开全局搜索；Esc逐层回原位置，避免每次返回都去输入。长代码默认保持纯文本，提供换行/横向读法，两者都不能改变原文；复制读取持久记录。

**恢复。** 失败的重试是新用户动作，不由阅读关闭触发；普通暂停的Ctrl+R显式恢复。未知写核查以独立表单读取当前工具证据，记录观察后仍暂停；退出表单回同一证据位置和原草稿。重开Session落在现场暂停态，允许回到保存的阅读锚点但不会自动继续。所有界面恢复动作都使用现有执行保护判定。

弱点：用户在两个阅读层间更频繁地进出，必须证明Esc回退与输入还原比目前省操作；如果“现场”把证据藏得太深，会让对Agent的不信任更难解决。应以失败定位、重复查看同一输出、恢复后插话三条连续路径比较A/B，而非单屏美观评分。

## 交付第一稿的判断

最应守住的不是选哪一个方向，而是四条可检验契约：停止不受选区影响；读完原文回到原处；失败与未知写持续成为当前事实；插话的采纳属于那条输入。视觉密度随后由一行工具结论与20行证据阅读来改变。两方向均不增加Agent/Job导航，均保留显式恢复与未知写核查。

## 第二轮对抗：反例、淘汰与自身修改

已完整读 `research.md`。此时 `divergence.md` 尚未落盘，以下四项发散方向按主代理转述的摘要攻击，属于对方案摘要的反例，不冒称读过不存在的细节。对抗不是投票：每项必须说出会在哪一次按键、哪一种异步状态变化上失败。

### 对 research A：工作段落＋现在条＋editor

- **反例RA1：Ctrl+C被“更明确的prefix”替换。** 80×24输入区正在选中一行草稿，真实shell还在写；用户按惯常Ctrl+C，若A仍保留当前复制分支却把真正停止藏到Ctrl+X s，危险认知依然存在。两步键能避免冲突，却增加紧急停止成本。否定“以prefix替换Ctrl+C”；Ctrl+C必须在所有焦点无条件请求暂停，复制另用Ctrl+Y。prefix可保留为可发现的命令入口。
- **反例RA2：“已生效”被过度解释。** shell在t0启动，用户t1发送“不要再改”，t2 input_handled到达；旧工具在t3写入未知。若回执t2显示“已生效·后续写入已停止”，用户会把输入采纳理解成物理写入已经停止。采用真实Engine语义最窄的文字：“Agent已采纳此要求”；只有保护层确证停止边界才能说哪些动作没有继续。新要求的段落分组不能充当执行证据。
- **反例RA3：完成收束改变阅读身份。** 用户位于段落中尚未显式展开的第4个输出，输入已有多行草稿；任务完成时整段收成“交付摘要”，即使恢复相同event ID，源内容已不在视口。保护“用户主动展开”不足以保护“正在阅读”。禁止当前阅读段落的自动折叠；未选中、未阅读的已完成段落也应只按用户明确压缩动作收束。
- **反例RA4：核查跳转与草稿共享editor。** 用户Ctrl+P选择核查，进入未闭合事项；若复用editor填写观察但没定义草稿栈，就重复D02。要求核查目标、观察草稿、原要求草稿三项身份分开，Esc可返回原稿；Enter在核查中仅“记录观察”，不能隐含恢复。

A的段落价值成立的必要条件：从单条证据能看到它关联的输入，且没有以视觉同段来断言发生时序。没有这些条件，工具压成组会把用户需要核查的关系藏得更深。

### 对 research B：120宽双证据面／80原位切层／旧版本不覆盖

- **反例RB1：80列隐藏对话恰好藏掉待处理项。** 用户在第132行错误，已选三行且editor有两行草稿；同文件第二次编辑失败并产生未知写。仅给“新增2项/新版本”会像普通通知。第2行“现在”必须优先显示“执行暂停·写入待核查”，不能继续显示旧cargo check或仅统计对话新项。未知写优先级是执行事实，不是注意偏好。
- **反例RB2：缩窗后F6的对象变了。** 120宽时焦点在右侧证据，缩至80后主阅读面若默认变对话，F6或y现在作用于对话而非原文件。尺寸切换只能重排同一焦点对象；当前证据必须成为80列主面，标题写它的版本。宽度改变不能悄悄改复制对象或问题目标。
- **反例RB3：旧版本稳定依赖“确有一份旧版本”。** 用户打开的是`/diff`当前工作区快照，Agent随后改文件，点击引用三行。仅把文件路径+时间写标题，不足以把引用解析为第一次diff。记录中必须有不可变的正文和来源；没有快照时明确说“当前工作区”，禁止标“本轮已应用”。保留旧展示缓存而全文复制读取新文件会直接违背承诺。
- **反例RB4：并读主张不代表操作更少。** 80×24已用身份/现在/对象/锚点/editor/键位9行，只剩15行结果；用户为引用一条长命令要收起editor、选内容、引用、再展开editor，四次操作可能比当前d→Ctrl+Y更重。把B当默认方向之前必须实测引用路径；如果关键收益仅在120宽成立，B应是用户显式进入的阅读状态。

我没有否定旧版本保留；否定的是缺少不可变内容时仍向用户作版本保证，以及把宽屏并读收益推广到80列。

### 对发散1：稳定锚点纵向工作账本

**反例D1-1：** 用户正在读同一次shell输出第132行，最终输出到达；把“运行中观察”和“工具最终结果”当两条账本事实追加，event ID变了，语义锚点必须重新关联；若仅event ID＋偏移，用户读位会丢。需要显式的call→观察→最终记录同一性和差异提示。

**反例D1-2：** 80×24两个工具标题、exit、输出、省略行共18行；账本只把事件排稳定、不改变默认摘要预算，密度问题原样保留。它若再加请求修正线、时间戳、关联边、版本标记，完整输出更被挤走。只记录用户决定需要的事实；底层事件按需读。

这个方向与我的A最接近，但稳定锚点不能代替信息删减策略，也不能解决同键后果不同。若两个缺陷都不处理，不能称完整方向。

### 对发散2：原生终端输出＋临时阅读器

**反例D2-1：** `less`进入F跟随，用户Ctrl+C只退出less等待；Agent shell仍执行。若临时reader独占stdin，BONE不能同时收到全局暂停；若两者都读stdin，同一字节会被哪个进程拿走不再可靠。

**反例D2-2：** 80×24正在用原生scrollback选择旧日志，Agent新增stdout；终端选择、光标与最新输出的关系由宿主终端决定，BONE无法保证“草稿已保留、选区没变、当前未知写仍可见”。原生回滚的优点是宿主选择熟悉；它不能自动提供稳定的执行状态入口。

**反例D2-3：** 未知写需要核查原始参数→写结论→保持暂停→显式恢复。reader关闭返回shell后若恢复命令打印在不断增长的输出底部，用户从旧阅读位返回要重新定位；若reader退出即恢复，会违反保护。需要独立持续控制面与单一键盘所有者，这又把方案推回受管理TUI。

**明确淘汰作为默认架构。** 看似“终端最原生”的优秀方案，在BONE的运行中插话与全局停止要求下给出两种输入/屏幕所有权。导出到pager可以成为用户明确的只读支路；默认执行主面必须保证Ctrl+C与暂停状态的统一所有权。若其临时阅读器是BONE内部状态且保留全局控制，它实际上接近我的B，不能再声称靠原生scrollback解决状态契约。

### 对发散3：文件／错误／问题对象工作台（非Job）

**反例D3-1：** Agent连续对同文件改两次，第一次测试失败，第二次测试通过；工作台若按文件或错误类型去重，“失败对象”可能因第二次成功消失。未知写发生在第一次时仍未核查，成功检查不等于核查完成。待处理项必须以发生实例＋明确结束条件保留，不能跟可替换的当前文件对象共用生命周期。

**反例D3-2：** 80×24顶栏/文件列表/问题计数/editor挤掉结果，用户在文件上Enter应该“阅读”，在问题上Enter应该“选回复目标”，在失败上Enter可能“重试”。相同“对象工作台”名称不解决动词。当前焦点必须显示下一动作；重试不能成为列表Enter默认动作，问题到达不能把已选文件替换成回复对象。

**反例D3-3：** 工作台鼓励用户选文件后写“改这里”，但界面若把已打开文件自动绑定发送内容，会扩大用户指令范围且隐去版本。引用必须显式插入草稿、带来源、发送前可见；只读对象选择不影响Agent任务。

此方向保留的条件是工作台作为进入证据的层，不常驻文件树、不让用户维护对象队列。否则它虽不叫Job，仍把选择和组织工作单元交给人。

### 对发散4：激进可编辑任务契约、弱化聊天

**反例D4-1：** 用户在运行中把“允许改文件”编辑为“只读解释”，保存契约时有旧shell在执行且随后写入未知。一个可编辑文本必须至少区分正在编辑稿、已提交版本、Agent已采纳版本；把文本直接刷新成现在的契约会让用户误以为旧执行已受新条款约束。这是新的版本解释负担。

**反例D4-2：** Ctrl+C暂停后，用户修改契约再按Enter。Enter是保存契约、提交新要求还是恢复执行？如果同一步恢复，会绕过显式恢复意图；如果保存后保持暂停，必须给“契约已提交·执行仍暂停”的可见状态。未知写期间修改契约不能核销未知写。

**反例D4-3：** Agent问“JSON还是CSV”，用户原契约编辑稿尚未完成。把答案写入契约会混合局部问答与长期规则；临时editor回答又重新引入发送目标和草稿栈。需要保留独立问题回复，不应为了去聊天把所有协作硬塞成契约编辑。

**暂不接受作为本轮默认方向。** 它可以适合少数长任务，但目前缺少“无需概念学习即可插话、回答、核查”的连续操作证明。降低聊天权重是表述选择；必须先证明版本与回复目标更容易理解，而不是把输入组件改名后宣称范式变化。

### 对我自己的两个方向的修正

1. **A的“当前动作”不能成为隐形第二焦点。** 改成该行只提示状态与已确定的快捷动作，不因后台变化接管Enter。进入核查/问题由一个显式入口；输入Enter始终按可见发送目标。这样免去新状态到达时同键目标突变。
2. **B不默认要求用户在现场／证据来回切换才能插话。** 证据阅读是用户显式放大结果的状态；editor保留一行草稿摘要，用户可以明确返回输入后恢复原稿。普通现场保持A的单面。B现在作为A可进入的读法，只有引用/长输出实测显示明显收益，才独立成为默认方向。
3. **两方向都撤去过强“采纳=生效”的文字。** UI先显示“已保存”、后根据已有事件显示“Agent已采纳”；物理动作与未知写单独列证据。若没有后台的物理停止边界，不能凭文案承诺“以后不再写”。
4. **不为淘汰方案折中加入其面板。** 全局Ctrl+C、原稿栈、父子Esc、未知写的结束条件，是任何方向的基础。若一个构想只有在取消其中一条后显得简洁，应淘汰该构想而非降低基础契约。

## 第三轮：读到发散原稿后的勘误与实际原型检查

### 勘误：shell与检查的副作用

独立初稿沿用了“先前已启动的只读验证/只读检查”措辞。仅凭`cargo test`、`shell`工具名或看起来像检查，不能判定只读：构建会写产物，测试和构建脚本也可能有其他副作用。上述初稿作为设计过程保留；正确表达改为**先前已启动的检查**、**禁止新的源码修改**。如果工具的effect或执行边界不能证明实际影响，就展示未知及核查，不能因“检查”归类推导0写入。核查是观察、记录实际效果；不自动回滚，也不等于取消已经发生的改动。

### 用 divergence.md 实际四方向修正第二轮反驳

已读实际第3—7节。此前第二轮以摘要攻击；本节明确撤回已被原文处理的指控，再提出尚未闭合的反例。

**A，带锚点线性账本。** 原稿已经有start/end收据、稳定#14、原位校样、ask/reply草稿分开；不能继续指控它只按到达时间排序或切reply会直接转移已有文字。保留的致命点来自共用底线：选区Ctrl+C只复制；无选区又只停止“当前外部命令”，不是整个Session进入显式暂停。反例：读错行时选字，shell仍在执行，Ctrl+C不会停止；取消选区后Ctrl+C终止当前shell，Agent若继续启动另一个动作，用户仍以为工作已停。必须把暂停事实绑定Session保护层，而不是外部命令名。另有Ctrl+K同时属于惯常editor删除至行尾与作用切换的冲突；作用切换需要独立的可见手势，不能以“prompt遵循编辑键”掩盖。

**B，原生文档＋按需Ratatui阅读器。** **撤回“B使用外部less、两进程争stdin”的指控。** 实际原稿明确是BONE内部Ratatui独占reader，一套事件循环可以保留全局Ctrl+C入口，因此我先前基于摘要的external reader反例不适用于实际B。仍不接受B作为默认，理由改为：原生终端上滚位置和文本选择不由BONE管理，关键未知写/暂停状态可能在scrollback底部，用户读旧文本时不可达；“选区Ctrl+C复制”更无法可靠识别终端原生选区。反例：用户在tmux或SSH中上滚旧V1，后台write断开产生UNKNOWN；完成块append与prompt一行状态都在视口之外。只有显式/live能看到，不符合默认紧急状态必须可见的契约。原稿已经承认prompt重绘与alternate screen恢复风险，我的淘汰理由应基于这两个真实代价，不再制造外部reader前提。

**C，对象工作台。** **撤回旧错误会因新成功被去重消失、窄屏必定挤目录、未区分captured/current的指控。** 实际原文已经要求失败对象持续、已解决也保留选中、80列目录退成breadcrumb、captured/current分开，方向比摘要更完整。我仍认为其主要验证风险是来源关系：同一工具结果可能关联多个用户修正，E1→V1→意图v2→业务Q1不能凭一个“related”字段自动推导。反例：E1是v1启动构建所得，用户v2限制新改动，Q1回答只改业务答案；用户按r答完后查看“为什么改这块”，因果页必须显示v1开始、v2限制、Q1回复、独立v3授权，不能把最近意图当所有对象的统一出处。若一跳来源做不到，这个方案会迫使用户维护五类对象的关系。它已规定不自动发问答，因此不再用“选问题就发送”攻击它。

**D，可编辑契约。** **撤回“编辑字段没有版本、Q1回复会解锁写规则”的指控。** 实际稿有saved/local fence/accepted分列、当前v2与阅读v1提示、Q1不改变write rule。我对默认D的拒绝仍成立，但落点更具体：e编辑write rule `NO NEW EDITS→EDITS ALLOWED`声称“只提交明确变化、不批准未知未来动作”，而当前任务执行本来就需要授权Agent决定后续动作，这个边界没有显示。反例：用户仍在未知写状态下e把规则改允许；保存成功应保持Session暂停与UNKNOWN，两者不能因规则变化变绿。界面要同时表达“用户允许未来源码修改”“过去作用未核查”“执行仍暂停”，六段契约只是表面信息排序，不能自行实现三套授权/效果/执行状态。若这些状态都由真实Engine判定，D有可试验价值；若本地自然语言转换生成新fence，必须明确这是新的产品语义和执行器工作，不能称仅是UI设计。

我现在的排序判断：A或C都值得做连续路径原型；C比摘要显示出的设计更有竞争力，不能仅因“用户要选对象”淘汰。B默认代价真实存在但外部reader指控撤回。D仍需证明自然语言→规则的变更过程比原请求更可理解。

### index.html 的独立交互评审：三个破坏契约的细节

证据方法：读原型源代码；本机没有Playwright，未安装浏览器依赖。本轮用Node `vm`执行HTML实际script，提供最小DOM支撑原有click/keydown/paint回调，检查`window.designLab.screen()`与状态。这是**执行脚本的交互逻辑核对，不是浏览器渲染或截图实测**。80×24返回24行且每行80格通过；通过字符预算不代表下面语义契约成立。

#### R01 / P1：问题到达会改变未发送草稿的发送目标

复现：初始step1，草稿设`UNSENT_ORIGINAL_DRAFT`；不点任何“回复”操作，切到step5等待问题。screen第21行从“新要求 · Enter发送”变成“回答Q1 · 可明确改发新要求”，草稿仍完全相同。

`screen()`直接用`step===5`决定目标标签；原型没有独立replyTarget、用户选择或取消目标状态。外部textarea保留了文字，但路由表意已变，恰好违反“新问题不会抢已有草稿”。本页不真正发送，所以这里不是声称模型收到错误文本；是原型展示的操作契约已经将同一Enter改向Q1。

要求：问题到达只增加待回答事实；当前输入仍是新要求。显式选择回复后才绑定Q1；取消回复恢复原新要求草稿，并在80列保持目标标签可见。

#### R02 / P2：子层返回没有保存进入层，Esc回不到证据窗口

复现：step4打开证据→点击命令发现`/`→Esc。执行脚本结果reader=false、palette=false，回主面。证据→打开核查→取消也把reader清掉。提示却写“Esc回到进入位置”。

原因：palette/核查打开时都将reader=false；`closeLayer()`只关当前布尔值，没有进入层、对象、偏移。它甚至没有可保存的证据滚动位置。草稿字符仍在，不代表阅读契约成立。

要求：保存父层与所读对象；命令关闭或核查取消返回原证据，保留同一证据位置/选区。End“回最新”是用户显式离开整个阅读链的动作，才清空返回栈。80↔120切换只改变布局，不改变父层。

#### R03 / P1：证据与工具生命周期、故障对象和宽窄屏选择不一致

复现一：step1“运行8s”按E，证据正文已经显示“finished14:02:28 · exit101”和E0063，提前呈现未来失败。复现二：step8未知写按E，仍打开“auth build原始记录”的exit101，而不是断开的write参数与实际/预期内容。复现三：design2、step4、80列选择标记是“检查auth build · failed”；只改尺寸到120列，选择标记变成“src/auth.rs · v1”，右侧却继续显示构建结果。

原因：全局常量evidenceLines绑定所有步骤；screen按宽度生成两个不同默认选择，而没有selectedObject。用户无法判断“这次看见的证据究竟属于我打开的对象、当前阶段还是未来预写剧情”。这直接破坏了两条承诺：原文证据可信，以及缩窗/扩窗不改阅读对象。

要求：运行态只能显示已发生的观察，最终结果到达再附完成事实；未知写的E入口必须指向该write的原始参数/核查证据。保存selectedObject/对象版本，80与120都渲染该同一对象的内容。核查窗口关闭不表示问题已解决，工具故障不能因打开普通编译记录变成可恢复事实。

这些问题不来自真实执行保护；原型已经声明不执行模型/工具。恰恰因为是设计原型，展示的状态和键位必须能解释进入、返回、目标和证据身份，否则漂亮24行图会给下一轮实现留下错误契约。
