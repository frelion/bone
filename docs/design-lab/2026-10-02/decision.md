# 设计裁决：先让操作可信，再选择主模型

2026-10-02。这是设计建议与原型检验，尚未修改生产 TUI。当前基线为 `7d45efb`。

## 结论

默认方向建议采用 **A：可阅读的工作段落**。用户继续正常聊天；工具以证据进入正文；当前执行、当前阅读、当前草稿有分别可理解的状态。它需要大幅改信息层级和交互规则，不能靠加 slash 或换颜色完成。

**C：对象主页仍是有竞争力的替代主模型。** 发散组认为 A 只是现有聊天的可信修复，C 更适合离开一小时后的改动审阅；我接受这项反驳。现有证据足以决定先修正操作契约，尚不足以证明 A 的整体体验优于 C。推荐 A 基于当前用户“正常对话、内部 Job 自管”的约束，以及较少新增状态；没有冒充真人体验数据。

B 原生 scrollback 不选为默认，D 可编辑契约不进入首版。保留它们的独立稿和否定记录，避免把四者混成一套功能更多的控制台。

## 当前产品的问题有具体证据

批评组在隔离 fixture、80×24、退出前的终端帧中确认：

- 执行失败后正文已经出现 422，header 仍称“就绪”，底部仍说“等待纳入执行”。
- 输入选区存在时 Ctrl+C 只复制，执行仍未暂停；取消选区后同一手势才暂停。
- 核查未知写入口会把已写草稿换成 `/reconcile ID`，原稿消失。

另有原文返回位置、窄屏状态截断、工具前六行预览、帮助不能滚动等源码与布局证据。完整复现及证据类型见 [critique.md](critique.md)。这些是用户判断与操作的缺陷，不能由此推断执行器的版本保护已经失效。

## 四种方案真的在哪里不同

| 模型 | 默认入口与主要动作 | 长任务优势假设 | 反例与取舍 |
| --- | --- | --- | --- |
| A 工作段落／因果账本 | 按合作顺序读；从某个结果下钻证据；返回同一位置 | 连续理解“为何做了这个动作” | 10k 事件后找交付仍可能慢；UI 猜意图归组会造假。先做可信修复，保留结果直达入口 |
| B 原生输出＋内嵌 reader | 宿主终端回滚；临时进入 Ratatui 阅读器 | 终端选区与原文保持熟悉感 | 宿主滚到旧输出时，BONE 不知道读位；新未知写可能不可见。不是两个进程抢 stdin。淘汰默认 |
| C 对象工作台 | 从问题、证据、改动、交付实例中选一个对象；全文→目录 | 返场直接看改动／检查，而无需读因果历史 | 连续理解可能需解释→错误→问题→改动四次选取。未核查旧实例不能被新成功去重。保留竞争，不默认文件树＋聊天双栏 |
| D 用户可编辑契约 | 编辑目标／授权字段；预览变更；提交版本 | 当前目标和授权更可检查 | 编辑稿、提交版、采纳版；旧稿覆盖新约束；口语被错误结构化。否定默认。只读原话引用是删减后的另一个方案 |

HTML 对 A/C 提供结构比较和公共阅读契约；B 只模拟输出排版，没有模拟宿主 scrollback；D 展示只读替代，没有实现字段版本提交。因此不能根据这些共用 JavaScript 交互宣称四个完整模型都通过了体验验收。原始四模型、8 份字符布局见 [divergence.md](divergence.md)。

## 随机法与对抗留下的机制

三个独立 GPT-6.1-Sol 使用 OS 随机字符串、固定词表、固定映射生成 27 项机制。记录先于相互阅读；第二轮交换方案，第三轮检查原型与误读。方法见 [README.md](README.md)。

保留：执行与阅读两条时间线；同一事实的结果／原文／审计层；异常先给原因；输入自己的接收／采纳回执；固定旧证据来源与版本；可回到进入位置的阅读层。

删除：每次插话先选择路由／执行策略；用户画执行 DAG；停止自动回滚；失败占满视口并接管输入；窄屏永久右栏输入；默认并排两事件；默认常驻双证据面。

这些机制有的在随机前已有近似假设。随机法推动了跨领域联想，但本轮没有对照组证明它提高设计质量。代理相互一致也不是用户研究。

## 对抗修正：保留犯错过程

1. 第一轮把发散 B 当作外部 `less`，提出 stdin 冲突；读实际稿后撤回。它是内嵌 Ratatui reader；淘汰理由改为宿主读位与新异常的可见性。
2. “cargo test 是只读”被撤回。测试可能写构建产物、运行脚本或其他副作用。新约束保护不能由命令名推导，不能承诺已启动动作零写入。
3. 研究者撤回由 UI 猜“用户意图段落”。只能用持久输入与可靠关联；未知归属保留可追溯条目，不靠到达顺序解释因果。
4. root 原型被发现 Q1 出现就改草稿目标、运行阶段提前展示失败、关闭命令／核查丢父层、宽窄屏改变所选对象。均已修正原型；这不是生产修复。
5. 发散组反对 root 把 C 改成聊天侧栏＋旧文件面，也反对把 D 删成只读后继续当原 D 比较。C 原型现以对象目录进入，默认没有聊天侧栏；D 明确标只读替代。
6. 有分歧的停止键：批评组希望 Ctrl+C 无条件暂停；发散／研究组倾向独立全局停止入口，保留终端复制习惯。原型暂以 Ctrl+C 暂停、Ctrl+Y 复制展示。生产选型须验证终端键盘和选区语义，不能在存在选区时默默变义。

## A 的具体设计语法

### 信息优先级与行数

80×24：身份 1 行、分隔 1 行、正文 16 行、分隔 1 行、当前事实 1 行、输入目标 1 行、草稿 1 行、当前键位 1 行、阅读位置／新内容入口 1 行。宽屏 120×40 将正文增为 32 行，默认仍为纵列。原型使用单行草稿；生产多行编辑最多占 5 行，主动编辑时可以减少正文，不能由通知自动扩高。

常驻身份只需 BONE／项目。模型、token、call count、Session ID、绝对目录按需查看。未知写优先于失败，失败优先于笼统空闲；工具失败与 Agent 是否仍在处理分别表达。“已完成”绑定特定输入交付，不表示整个 Session 的所有事项都已闭合。

空白与对齐承担段落边界，不给每个工具套框。普通成功一行：工具、对象、结果；失败先展开最有用的错误及所在文件，完整命令、stdout/stderr 仍在结果层。机械结论可以来自 exit/status，UI 不创造语义摘要或成功判断。

### 输入与焦点

默认输入目标是新要求。问题到达只显示待答事项；用户明确选择 Q1 才绑定。已关闭的问题回复不自动改投新要求或别的问题：保留草稿、解释目标失效、提供明确改发动作。

普通输入、问题回复、核查表单各自保存文字与目标。暂开阅读／命令／核查不消费原稿。Esc 只退出当前层；关闭详情回相同对象与位置。停止从任何焦点可到达，状态要区分“正在停止”和“已暂停”；复制反馈必须指出复制了哪个对象。

Enter 在输入发送，在选中候选确认，在阅读展开；触发处写清下一步。slash 补全插入与执行不能只因为文本是否刚好完整而静默变义；建议补全候选确认始终插入，输入再 Enter 执行，命令面板选中 Enter 执行。两类入口分别标清动作。

### 阅读、到达与版本

用户滚开后保持事件／调用身份与原文偏移；新输出更新入口和当前事实，不抢焦点。观察帧转换为最终持久结果必须对账：原观察不在最终结果时给出说明，不假定两份文本行号一致。宽窄变化保留语义对象，不重新选择第一项。

结果层先内容、再参数、再审计元信息。原文复制从持久事实读取。选择旧文件显示 captured/current 来源，文件后来变化不能默默把旧证据替换成当前文件。未知写表单展示预期与实际观察；记录后仍暂停，不能由关闭表单或业务回答触发恢复。

### 不新增“第二个 Agent”

渲染只投影已有事件。正文标题可直接引用用户原话，工具结果可机械压缩。理解、计划、归组解释、长任务摘要、契约合并若需要模型，仍在所属 Job 内产生并持久化。没有 UI 外模型调用，没有可选 Job 导航，没有 TUI 自己创造的权限 fence。

## 最小实现边界

保留 Ratatui 与现有 editor、SQLite 历史、Rig/native 模型路径。框架已存在；这轮问题的证据不支持为了设计换框架。

| 边界 | 直接做法 | 为什么需要／可以删除什么 |
| --- | --- | --- |
| 当前事实 | 一个普通函数从未确认写、暂停、当前输入终态、活动调用、待答问题计算可见状态 | 代替由 quiescent 得“就绪”及多个 sticky notice；不新建总线或运行状态框架 |
| 草稿 | 普通结构体保存 text、cursor、selection、reply target；核查用独立临时稿 | 有明确不同生命周期；删除取走原稿再塞工具命令的转换 |
| 阅读位置 | source/call/event identity＋原文偏移；按需详情保存返回点 | 缩窗与观察→最终需要稳定身份；减少全局 focus、scroll、selected 的松散互相改写 |
| 阅读层 | 少量具体枚举／返回记录 | 结果／审计／表单有父子生命周期；不建通用导航系统 |
| 工具显示 | 按具体结果类型渲染一个摘要函数与一个正文函数 | 删除统一截前六行；保留原文唯一来源，不新建流协议 |
| 交付入口 | 引用已有 delivery/response event | 让长任务直接查看交付，不以 UI 推断完成；无需另一个 Task/Artifact 业务内核 |

这里是实现边界建议，尚未立新类型。任何新增结构仍需回答需求、普通实现不足点、消融损失与新增状态四问。

## 下一轮比较与验收

先修当前已复现的行为契约，再比较 A 与真正的 C 对象主页。两条轨迹分别检验它们的强项：

1. 连续操作：80×24、10k 日志、读原文行 132、有草稿与选区、插话“先解释”、编译失败＋新问题＋旧未知写、核查取消、回答、继续、回原读位。
2. 返场审阅：离开一小时后直接找改动／失败批次／验证，说明旧失败与新通过是否同一次检查；判断有没有未闭合的未知写。

记录错误目标发送、误认已经停止／完成、原文定位步骤、回来是否同一位置、解释行动时间边界是否正确。不能凭主代理或其他代理对截图投票宣告胜利，也不以工具次数当可用性指标。

## 本页实际验证范围

用本机已安装 Chrome 与 Playwright 加载本地 HTML。检查 72 个字符布局（4 方向 × 9 步 × 2 尺寸）及 9 个具体状态契约：不显示未来结果、阅读快照不被替换、原文行锚点缩窗保留、命令／核查／审计返回父层、显式回复目标、草稿保留、新结果不移旧正文、未知写证据身份、宽窄同对象。390px 页面无全页横向溢出，终端区域可横向滚。无 page error。

结果见 [prototype-check.json](prototype-check.json)，实际浏览器截图见 [design-80.png](design-80.png)、[design-120.png](design-120.png)。没有模型、工具执行；没有证明真实终端输入分发、剪贴板、选区或生产执行保护。HTML 的单独 textarea 只演示本地草稿生命周期，不等于生产终端内读写并行。
