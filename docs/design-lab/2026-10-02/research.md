# BONE TUI：跨领域研究与两条完整方向

研究日期：2026-10-02（Asia/Shanghai）。随机 seed：`6b1fc077208c654e5ba39c1e`。触发词：缝纫、绳结、乐队排练。作者角色：独立跨领域研究者；尚未吸收其他设计 agent 的方案。

本文件只提出设计、记录证据；没有修改生产代码、既有报告或提交 Git。研究目标不是补齐竞品功能表，而是解释：信息如何积累、用户在何时看什么、每次按键作用于谁，以及一个动作如何真正收尾。

## 研究边界与非随机起点

BONE 为本地 Rust Agent terminal。一个 Agent 自动管理内部 Jobs；日常入口是聊天和文件工程。用户不需要创建或选择 Job。约束为 80×24 和 120×40。0.6 已具备 editor、slash、文件引用、live tools、search、diff；下列方案不能将这些已有能力重新计作创新。

没有使用随机词时的三个假设：

1. **主要信息对象应是用户的工作意图和证据，而不是工具事件。** “解释登录流程”和“修改登录流程”有不同的阅读目标；十次 grep 可以属于同一个工作段落。假设可被证伪：如果分组之后更难找到具体输出，或更容易误认修改已发生，分组就不成立。
2. **Agent 的执行时钟和用户的阅读时钟必须独立。** 输入可以持续编辑，执行可以继续，阅读可以停在旧证据；三者只在明确操作时相交。假设可被证伪：如果用户保留位置以后不知道当前是否仍在运行，则缺少可见连接。
3. **小终端中的细节质量首先来自可预测的按键契约与状态闭环。** 相同的 Enter / Esc 不应随后台事件突然改变目标；“收到停止请求”不等于“已经停止”。假设可被证伪：如果操作变得冗长、常用动作难以到达，契约过度保守。

这些是设计假设，不是由下列资料证明的 BONE 用户研究结论。随机机制之后仍需要真实操作检验。

## 广泛研究：每个对象回答一个不同问题

### 1. Pi：输入在执行时间轴上落在哪里

**文档观察。** 当前 Pi 默认 fullscreen，固定 editor/status，transcript 在内部滚动；regular 才使用终端原生 scrollback。运行中 Enter 发出的 steering 等待当前 response 和 tool calls 完成；Alt+Enter 的 follow-up 等待当前 task 结束。停止会把排队输入还给 editor；Alt+Up 可取回队列。不能沿用“Pi 默认原生回滚”或“steering 立即终止当前 shell”的印象。

**推断。** 输入对象需要一个可读的交付时点，接收状态和生效状态应分开。BONE 不应照搬两个难发现的发送键再用术语区分；更应借鉴队列可取回、停止不会丢稿的闭环。Pi 无内置 subagents 的产品说明也不能变成 BONE 禁用内部 Jobs 的依据。

来源：[固定版本使用说明](https://github.com/earendil-works/pi/blob/28eaccb8e87d075562593073282cc0774f2c2e3b/packages/coding-agent/docs/usage.md)、[固定版本快捷键](https://github.com/earendil-works/pi/blob/28eaccb8e87d075562593073282cc0774f2c2e3b/packages/coding-agent/docs/keybindings.md)。文档观察，未实测。

### 2. OpenCode：可见键位不等于实际操作契约

**文档观察。** 默认 leader 为 Ctrl+X，命令面板为 Ctrl+P。文档区分会话 undo/redo 与输入编辑；文件回滚依赖 Git。diff 的 auto 布局适应终端宽度；attention 默认关闭，可针对问题、权限、错误和完成请求注意。

**源码观察。** 固定版本 prompt 中 interrupt command 检查 autocomplete 与 input focus，在五秒计数窗口内达到两次才调用 abort。可见 `session_interrupt: escape` 不能单独解释实际停止行为。源码还有 prompt stash 与卸载时保存草稿的路径；它们不是“发送后执行队列”的证据。

**推断。** BONE 应直接展示下一次按键会做什么；阅读 Esc 和停止行为分开。会话 undo 同时涉及文件状态，不宜用一个无目标的 undo 入口合并。注意请求可以是低频状态变化，不需要每次工具完成都打断用户。

来源：[官网 TUI（页面标记更新日 2026-10-02）](https://opencode.ai/docs/tui/)、[官网 keybinds](https://opencode.ai/docs/keybinds/)、[固定版本 prompt interrupt 源码](https://github.com/anomalyco/opencode/blob/1ddb0873aee50d209d1a8d7f91b89c5daf692d49/packages/tui/src/component/prompt/index.tsx#L392)。本机仅验证版本。

### 3. Lazygit / Tig：对象清单与证据阅读应如何接力

**文档观察。** Lazygit 的键位按上下文列出：文件 Enter 进入行级 staging，commit Enter 查看文件，确认面板 Enter 确认；Space 在 commit 上可以 checkout。主视图滚动可以从清单上下文操作，另有 normal/half/fullscreen 布局。Tig 默认单视图，commit Enter 可以上下分屏，Tab 切换两视图。Tig stage view 对未跟踪文件展示文件内容。

**推断。** 迁移价值是“当前选择指向一份可检查证据”，以及阅读空间可以按需扩大。不能照搬 Lazygit 的密集面板或 Space 直接变更仓库的习惯到聊天阅读：终端 Agent 中稳定的读动作尤其重要。也不能因支持 diff 就忽略新增文件。

来源：[Lazygit 固定版本键位上下文](https://github.com/jesseduffield/lazygit/blob/ff375b124d149f03f9156d3720a998cbc04482fa/docs/keybindings/Keybindings_en.md)、[Tig 固定版本 manual](https://github.com/jonas/tig/blob/7d841c9302456b8c8f0629a559344137dc4faa4f/doc/manual.adoc#L63)。两者未实测；此处不是可用性排名。

### 4. Helix / fzf：焦点应怎样承担明确意义

**文档观察。** Helix 将 Normal、Insert、Select 分开，遵循先选择后操作；picker 有自己的按键，prompt 快捷键只在不冲突时适用。fzf preview 跟随当前候选，由配置的外部进程产生；reload 是显式绑定的动作／事件。fzf 可以只占当前终端的一部分高度；它不是内置文件知识库。

**推断。** BONE 的输出复制、问答目标和 diff 操作都应先显示作用对象。可以复用列表→预览→确认的轻量流程；不需要让整个聊天成为 Vim 模态编辑器。BONE preview 更应采用只读本地原文入口，不能因为候选高亮就启动 Agent 或任意 shell 命令。bat 着色属于 fzf 的外部示例，不算 fzf 内置能力。

来源：[Helix 官方 usage](https://docs.helix-editor.com/usage.html)、[Helix 官方 keymap](https://docs.helix-editor.com/keymap.html)、[fzf 固定版本 README preview](https://github.com/junegunn/fzf/blob/b1be3a8be1b833ce5b92fbbac11637643d60a046/README.md#L1008)。未实测。

### 5. Zellij / tmux：阅读旧输出怎样与进程继续运行并存

**文档观察。** Zellij 离开 scroll mode 后仍保持回滚位置；明确 ScrollToBottom 才回到尾部。重新聚焦一个已回滚 pane 会进入 scroll mode。其模式很多，并且模式与按键各自关联。

**源码／手册观察。** tmux copy mode 显示当前位置与历史行数。固定版本的自动 refresh 默认关闭；开启后只在底部继续滚动，选中文字时暂停刷新。

**推断。** BONE 需要稳定的阅读锚点和可见的“更新还在到达”入口。阅读暂停不应让用户误认执行暂停。不能照搬 multiplexer 的 pane 数量、前缀层级或完整模式集；用户需要读证据与写要求，不需要管理终端会话拓扑。

来源：[Zellij 官方 modes](https://zellij.dev/documentation/keybindings-modes)、[tmux 固定版本 manual source](https://github.com/tmux/tmux/blob/5a820e63b72f05c121441149c72327aeeb16dfa4/tmux.1#L1862)。tmux 本机只查版本，没有操作实测。

### 6. 原作者 HCI：时间关系、注意成本与完成闭环

**论文观察。** Shneiderman（1996）将 temporal data 与一维序列区分，因为事件有起止时间且会重叠；其任务分类同时包含 overview、relate、history 和 extract，不能只抽取“按需详情”。Horvitz（CHI 1999）的 mixed initiative 原则明确讨论不确定意图、注意时机、便捷调用／停止、错误推断成本和合作修正。Shneiderman 本人的 golden rules 页面强调操作组要有结束反馈、降低记忆负担，并要求按领域验证。

**推断。** Agent 的十个 tool events 不是十条平等聊天消息。界面需要把请求、指令修正、行动和证据连接起来，让用户知道“我输入后哪些动作仍发生过”。这些原则不证明 80×24 双栏更好，也不支持让模型猜测何时自动抢走焦点。

来源：[Shneiderman 1996 原文，作者 UMD 页面](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)、[Horvitz CHI 1999 原文，Microsoft Research](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)、[Shneiderman 原作者 golden rules](https://www.cs.umd.edu/~ben/goldenrules.html)。属于概念依据，非 BONE 实验。

## 随机触发：九个机制及淘汰记录

随机词是生成操作机制的约束，不作为主题皮肤或产品中的新术语。以下名称只用于设计讨论；屏幕仍使用“输入、正在执行、阅读、修改、待回答”等普通词。

| 触发词 | 机制与具体屏幕行为 | 代价／失效方式 | 判断 |
| --- | --- | --- | --- |
| 缝纫 1：固定布料，再移动针 | 用户滚到构建日志第 132 行，阅读区锚定事件＋原文行；新行只改变 `新增 14 行 · 返回最新`。输入光标独立移动，缩窄窗口后仍尽量显示原文第 132 行 | 日志更新与最终持久输出需对账；只存视觉行号会在缩放时错位 | 保留。BONE 已有 follow，新增价值是可见锚点和真实内容位置 |
| 缝纫 2：一针的两面 | 修改记录显式显示 `提议` → `已应用` → `已验证`；打开同一条记录可以切换这三种证据，头部写基线、时间和来源；无法归因时显示 `当前工作区差异` | 可靠基线和修改归属有后端成本；不能将 Git diff 自动算为本轮变更 | 保留，作为阅读结构，不要求每次写前人工批准 |
| 缝纫 3：自动拆线 | 用户发送“别改了”，UI 自动回滚此前文件，聊天中补一个“已恢复” | 停止新的行动与撤销已发生动作混淆；用户自己的修改可能被覆盖 | **淘汰**。语义与可恢复性都不成立 |
| 绳结 1：收束未完成事项 | 状态条只显示未闭合事项：`1 待回答 · 1 写入待核查`。Enter 查看具体对象；处理后显示带结果的收尾记录，条目消失但历史保留 | 阻塞与非阻塞事项需区分；数量可以变但焦点目标不能随新增条目跳走 | 保留，不能直接展示内部 Job 清单 |
| 绳结 2：可回到的位置 | 阅读位置／已打开输出可以暂存为最多三个书签，回到输入后仍有一行 `固定：错误行 132`；Enter 回去，关闭不删除源内容 | 书签很容易堆积；80×24 常驻展示只能留一个摘要，全部列表按需打开 | 限制保留，只由用户显式固定，不自动生成 |
| 绳结 3：用户打结控制执行顺序 | 屏幕展示各行动节点，用户连线和拖动决定依赖；Agent 按新的 DAG 执行 | 把内部调度责任交给用户；终端下需要大量键位，偏离普通聊天 | **淘汰**。违反 Agent 自动管理 Jobs 的产品边界 |
| 乐队排练 1：修正从哪一拍起生效 | 运行中发送“先解释”后形成一条回执：`已接收 · 当前 cargo check 已启动`，之后变成 `Agent 已纳入 · 新源码修改被阻止`；查看可以看到生效前后行动 | 纳入和阻止必须分别有证据；已启动的命令可能仍产生副作用，TUI 无法靠计时器承诺生效 | 保留，核心是时间边界，不是新术语 |
| 乐队排练 2：谱面与演奏分开 | 上方保持正在做的目标和实际阶段，下方可阅读之前的答案／文件；用户在输入区排练下一条消息，直到发送都不影响执行 | 两个区域若重复摘要会浪费空间；120×40 可宽屏，80×24 只留一行当前状态 | 保留，与固定阅读位置合并 |
| 乐队排练 3：独奏自动放大 | 任何失败自动占满阅读区，把输入改成错误处理快捷键，完成后恢复 | 故障恰好打断草稿与复制；权限／问题多时会连续抢焦点；按键目标突变 | **淘汰**。故障只请求注意，用户显式进入处理 |

三项淘汰各有不同理由：错误地撤销、暴露内部调度、抢占人类注意。不是按“像不像竞品”筛选。

## 十一条可迁移／拒绝的设计规则

以下是针对 BONE 的研究者推断；需要原型检验，不宣称已被竞品实测证明。

1. **主对话按用户请求形成稳定段落，工具属于段落的证据。** 标题来自用户文字的可确定摘要；不能等模型事后总结才有结构。内部 Job 可多对多归属，界面不提供 Job 选择。
2. **历史事实与当前运行状态占不同位置。** 历史中保留已发生的开始／结果；当前条告诉用户 Agent 现在是否还在动作。新状态不能覆写过去证据。
3. **锚定语义对象和原文位置。** 用事件 ID＋原文偏移／行锚点；折叠、窗口缩放和异步更新不能靠旧屏幕行数恢复。显示“正在阅读旧输出；Agent 仍在运行”。
4. **消息接收、指令消费、动作效果三者分别回执。** `已接收` 表示队列事实；`已生效` 必须来自引擎；已经执行的命令继续保留。不能用绿色 toast 代替这些关系。
5. **执行期间 editor 始终可写，阅读动作始终可做。** 进入详情不冻结执行；返回后草稿、光标、选择范围恢复。问题到达只更新目标候选，不偷偷改已有草稿的回复目标。
6. **Enter 作用于可见焦点对象。** 输入区发送；候选区确认选择；阅读区打开／展开；行动处理页面明确显示实际按钮名称。候选预览和搜索不得执行 Agent。
7. **Esc 是退出当前交互层，停止有独立明确入口。** Esc 先关候选／详情，再回输入；停止采用一个所有焦点可到达的命令，显示正在停止直到收到真实结果。拒绝把一个裸 Esc 同时承担丢草稿、关详情和停止。
8. **导航不必切换输入焦点。** PageUp/Down 阅读，输入仍可编辑；需要选择／复制具体对象时再显式进入阅读焦点。拒绝让 Tab 在不同宽度切换不同数量面板又同时承担补全。
9. **省略是阅读选择，不是删除证据。** 每个短预览有原文入口；显示可用全文范围。实时日志可丢观察帧，最终原文以持久记录为准。新增文件作为完整内容阅读。
10. **问题、失败、未知写各有结束条件。** 回答后收到已接收；失败明确是否可恢复；未知写提供只读核查和核查结论。待处理项不能因 notice 消失就算结束，也不能自动重放未知写。
11. **小屏优先让一个证据读得完整，大屏增加同时可见关系。** 两种尺寸保留同一对象与键位；宽屏分栏可选，小屏用原位切换。拒绝缩小后给用户另一个模式世界。

第 1/9 条借鉴 Tig、Lazygit 和 Shneiderman 的对象→证据关系；第 2/3/8 条借鉴 Zellij、tmux 的读时钟；第 4/5 条借鉴 Pi 和 Horvitz 的协作时间；第 6/7 条借鉴 Helix 的先选后动，并拒绝 OpenCode 中需要读源码才能解释的裸键停止契约。来源支持研究问题，规则的具体 BONE 行为由本研究提出。

## 完整方向 A：工作段落中的对话与证据

### 信息结构

默认主区仍是一条纵向对话。每次用户请求开始一个工作段落；后续修正显示在同段落中并标出实际交付边界。段落内部依次是用户请求、Agent 可读进展、折叠证据组、正式答复／待处理事项。工具不平铺成十条同等级消息。段落完成后收成：用户意图、交付摘要、修改和检查数量、未闭合事项；正文按需展开。用户主动展开的段落不自动折叠。

一行“现在”固定在主区上方，显示真实执行对象，例如 `正在检查 · cargo check · 12s · 已输出 81 行`。底部 editor 独立存在。阅读旧段落时出现 `阅读：登录修改 · 新增 3 项 · 返回最新`；新事件不改变当前段落锚点。

### 尺寸预算

80×24：第 1 行工作区／会话；第 2 行现在；第 3–18 行主阅读区（16 行）；第 19 行阅读位置／新内容入口；第 20–23 行 editor（4 行，含边框）；第 24 行当前焦点的按键提示。身份与状态分开，不把 model、目录、usage、会话和进度全部放在一条低亮 footer。模型详情按需打开。

120×40：第 1/2 行同上；第 3–33 行主区（31 行）；第 34 行阅读状态；第 35–39 行 editor；第 40 行键位。默认仍单栏，证据详情可原位展开。需要并读时用户显式固定一份证据，宽屏变成 86 列对话＋1 列分隔＋33 列证据；标题明确固定对象，小屏关闭双栏但保留固定引用。

正在检查 cargo check · 12s · 已输出 81 行

你  保持 API 不变，解释并修复重复登录
Agent  原因在 session 失效后的重复重试。
  证据：读 4 文件 · 改 2 文件 · 检查 1 次

你  先解释，暂时别继续改

  Agent 已纳入 · 新源码修改被阻止

┌ 输入：新指令 ────────────────────────────────┐

### 按键和运行中协作

输入是默认焦点；普通字符始终写入 editor。Tab 在候选出现时补全，否则编辑器内插入／处理缩进，不切换面板。F6 在输入和阅读之间切换（命令面板提供同动作以兼容终端）；PageUp/Down 不抢 editor 焦点。阅读焦点下 Enter 展开选中的段落／输出，`y` 复制可见选中对象。Esc 关闭最内层或回输入；Ctrl+P 命令面板可从所有层打开。停止有 `/stop` 和面板入口，建议键为 `Ctrl+X s`，prefix 到达后 footer 显示 `s 停止 · Esc 取消`；键位仍待现有编辑快捷键与终端兼容测试。

运行中发送使用一个默认语义：修正当前工作。发送后回执首先是接收事实；实际生效后更新，保留此前已启动动作。结束后再做属于 P1，可通过发送选项显式选择，在 editor 标題写“结束后发送”；不以 Alt+Enter 默默改变语义。尚未消费的输入可取回编辑或撤回，已消费后只能发新修正。

如果有问题：不覆盖已有草稿，固定条出现 `待回答：数据库选择`。Enter 打开问题页面，选目标后 editor 显示 `回复：数据库选择`；Esc 取消目标返回新指令。新问题到达不改变正在回答的那个对象。

### 完成、失败和核查闭环

完成段落显示交付、已应用文件入口、实际检查结果和未做事项。失败工具显示关键错误与原文；当前状态显示 Agent 是否还在处理。未知写作为段落内一个未闭合事项，进入后先展示路径、动作发生时间和已知证据；只读核查结束后记录结论，再显式恢复。关闭页面不代表解决。

### 代价、拒绝项、证伪任务

优点假设：保持聊天熟悉感，减少工具碎片。成本：分组归属和段落标题必须可靠，跨请求修改需要能从证据反向定位所有关联指令。拒绝自动把读过的段落折叠、拒绝模型猜测任务“已完成”代替 Engine 状态。

证伪任务：80×24 中运行一个分阶段构建，用户阅读前一段的错误行并输入修正；再问“这个写操作是在修正之前还是之后”。如果用户只能根据消息视觉顺序猜测，A 失败。第二个任务是找新文件内容与解释正文；若分组需要反复展开才找到内容，默认摘要粒度失败。

## 完整方向 B：稳定的证据阅读面与持续工作的 Agent

### 信息结构

默认仍从聊天开始。用户打开文件、日志、diff 或长答案后，把主区视为一张稳定的阅读面：它展示一个有标题、来源和版本的对象。Agent 的新进展进入旁边的简短对话区域；输入在底部持续可用。这里的对象是用户可理解的文件／输出，不是 Job。

宽屏默认“对话 43 列＋分隔 1 列＋证据 76 列”。窄屏使用同一区域切换“对话／证据”，保留各自位置和 editor；固定的现在条说明正在执行什么。对话通知只计入有意义的新进展，不逐个 token 增加数字。

证据标题举例：`cargo check · 输出 · 运行中 · 阅读行132`，`session.rs · 已应用修改 · 基线10:42`，`登录方案 · 正式答复 · 10:45`。来源／版本是标题的一部分，以免把旧输出当作当前结果。新的 diff 不就地替换正在阅读的旧 diff，只出现 `已有更新 · 打开新版本`。

### 尺寸预算

80×24：第 1 行身份；第 2 行现在；第 3 行当前对象与切换入口；第 4–18 行证据／对话（15 行）；第 19 行阅读锚点／更新；第 20–23 行 editor；第 24 行键位。15 行不足时可以暂时收起 editor 到一行，必须由用户显式操作并恢复原稿。

120×40：第 1/2 行身份和现在；第 3 行两列标题；第 4–33 行并读（30 行）；第 34 行阅读状态；第 35–39 行 editor；第 40 行键位。长路径可在标题展开，不靠挤窄正文解决。

```text

正在检查 cargo check · 12s
对话 · 2 条新进展      | cargo check · stdout · 阅读行132
Agent 原因已定位。     | 132 error[E0308]: mismatched types
改动已应用，检查中。   | 133  --> src/session.rs:42:17
                      | 134   expected Session, found Option<Session>
你 先解释，暂时别改    | ...
已接收 → 已生效        | 新增14行 · 打开最新
                      |
待回答：保留兼容行为？ |
┌ 输入：新指令 ────────────────────────────────────────┐
│ 请解释这里为什么变成了 Option。                    │
└─────────────────────────────────────────────────────┘
Enter 发送  F6 切焦点  Ctrl+P 命令  阅读：y复制
```

### 按键、对象引用与读写并行

保持 A 的基础按键契约。证据阅读焦点支持选择原文和复制；一个显式“引用所选内容”动作把带来源的短引用插入 editor，不直接发送。此时 editor 明确显示所引用的行和版本；查看引用是只读动作，发送后是否由 Agent 读取文件正文依现有 Session 契约留记录。不会把“当前打开的文件”自动发给模型。

F6 在输入与当前主阅读面间切换。窄屏的“对话／证据”切换通过标题入口或命令面板，切换不改变运行状态和发送目标。宽屏选择新输出不自动拉走已固定的阅读面；主动打开才替换。只保留一个固定对象和有限阅读历史，避免演化成 IDE 的 tab 管理器。

用户读旧文件时 Agent 改了同一文件：旧版本标题留着，提示新版本已到达；按“打开新版本”才替换正文。用户正在选中日志时也保留原文，最终输出到达后提示对账差异，不静默覆盖选区。

### 状态闭环和完整工程流程

聊天提出要求 → 打开 Agent 提供的关键文件证据 → 在 editor 提出局部修正 → 收到明确生效回执 → 审阅已应用版本 → 打开真实构建输出 → 选错误行并引用 → 回答 Agent 的具体问题 → 检查通过后完成摘要仍出现在对话侧，证据阅读位置保持。

失败和问题到达时在对话标题与现在条请求注意。用户打开失败以后阅读面显示错误、完整输出和恢复入口；未知写显示核查对象，完成核查后留下结论。完成可以改变现在条，不能自动把读者赶去正式答复。

### 代价、拒绝项、证伪任务

优点假设：工程场景中用户能持续看一份证据并写指令，不反复打开弹层。成本：必须有对象版本与来源，输出被引用后应可追溯；80×24 两区域不能同时完整阅读，切换入口需要特别清楚。方向 B 对普通闲聊的价值弱，必须在无证据时自然退回单栏聊天。

拒绝多 tab、多 pane、文件树常驻、内部 Jobs 看板和自动切换“最重要输出”。如果用户花时间维护阅读布局，设计失败。

证伪任务：同一文件被 Agent 连续改两次，用户读第一版并引用三行，同时终端从120×40缩到80×24。用户必须知道自己读和引用的是哪个版本，能够继续编辑原稿、找到当前正式答复。如果不能做到，B 的稳定阅读承诺失败。

## 下一步选择依据

两方向共享接收／生效回执、独立停止入口和原文锚点；这些是语义基础，不应靠 A/B 选择回避。真正的分歧是默认阅读单位：A 以工作段落组织证据，B 以一份证据对象保持连续阅读。

优先做两段可操作原型，使用同一内容：长日志＋运行中修正、旧文件＋两次修改＋引用。比较错误次数、找回证据所需操作、草稿丢失／目标误认、用户对“已经发生了什么”的解释准确度。不是比较截图看起来是否更像成熟竞品。当前资料不足以宣布其中一个方向胜出。

## 第二轮：用实际缺陷攻击自己的方案

本节在独立初稿之后追加。已读 [critique.md](critique.md) 的新增 fixture 报告；以下将其作为同团队的实测记录引用，未声称本人重跑。统一情景采用实验室 README：修复 token 过期后 `/me` 仍返回 200；运行20秒测试时插话“只解释先别写”；编译失败后读错误，再回复“返回401；现在可以改代码，并补过期测试”。

### 三个真实约束先于新布局

- 422失败仍出现“就绪”和旧“等待纳入”notice，说明执行状态与输入回执的来源不可靠。A 的工作段落和 B 的现在条若仍使用这些派生值，只会在更醒目的地方说错。原型必须保留失败事实与那条输入的消费事实，不能把“进程空闲”命名为“任务成功”。
- 有选区的 Ctrl+C 实际只复制且 paused=false；无选区时才暂停。增加状态条还不够。两方向都需真正分开复制与停止的调度入口；我的建议 `Ctrl+X s` 也是待实现的契约，不能当作已修复。
- 进入 reconcile 目前会把原稿改成 `/reconcile ID`。我写的“草稿独立保留”必须包含具体输入对象的生命周期：核查有自己的表单和文本，进入时原稿／选区／发送目标保持原值，退出核查后恢复；如果所有文本仍共用 `take_draft()`，布局承诺没有意义。

### 淘汰自己的 B：作为默认完整方向不成立

连续反例，80×24：用户正在看 `auth.rs` 第42行，Agent 的20秒测试仍运行；用户写一半“返回401”。此时编译失败到达，对话入口显示新内容。用户切到对话，打开失败日志，读错误；Agent 又问是否保持兼容；用户再切对话选问题，回复“返回401；现在可以改代码，并补过期测试”；随后想核对原文件，需重新选择先前固定对象。我的 B 在这条常见路径中产生文件→对话→日志→对话→问题→文件的切换链。

“只固定一份证据”无法同时保留文件与失败日志；增加多个 tab 又违背本方案避免工作台管理的承诺。badge 只解决新信息是否存在，不能告诉用户信息的性质与下一动作；每个 badge 都要求一次侦察。在宽屏，43列对话也不足以显示长问题和插话回执，它们会成为新的弱区。

因此 **淘汰 B 作为默认完整方向**，也淘汰“把 A 与 B 的所有长处融成常驻双栏”的想法。单份证据固定仍可能作为未来显式阅读工具，但本轮不能将它并入默认方案并声称已经避免导航成本。

### 收缩自己的 A：UI不能伪造工作意图

第一条用户输入可以同时要求“解释、修复、补测试”，随后在旧测试仍运行时要求“只解释先别写”，再允许修改。按每次消息机械分段会把同一次合作切成三段；按意图分组则需要判断三条消息是否仍是同一个目标。那是 Agent 的认知工作，不能在不经过 Job 的 UI 中偷偷完成。

更危险的是按视觉时序归因：插话已保存但未消费，之前已启动的测试之后失败。若 UI 将插话后到达的失败放进“只解释”的段落，会让用户误认测试是新要求触发。内部 Jobs 不可见并不提供新的正确因果关系。

可接受的 A 只保留普通对话与机械可证明的证据关系：标题使用原始输入片段；消费／效果只采用引擎记录；缺少关联时显示时间与未知归属，不自动命名“这一工作已完成”。**撤回独立初稿中默认“按用户意图收束所有工具”的主张**。如果需要更高层的工作段落，Agent 必须在已有执行体系内显式产出并维护它，UI只呈现已持久的关系。不能用“确定摘要”掩盖语义判断。

这样保留的 A 是受约束的对话方向，创新集中于真实状态、稳定回退、输入目标和采纳回执；它没有资格仅靠新分组声称解决海量工具阅读。

### 对其他操作模型的预先压力测试

此处先攻击模型本身；`divergence.md` 的四方向尚未落盘，后续会按具体方案逐项核对，不把下面的推测写成对方已有缺陷。

**原生输出＋临时阅读器。** 用户在20秒测试第8秒 PageUp 查旧错误，进入临时 reader；第10秒发送要求的半成品草稿仍在主界面，第12秒失败到达，第13秒收到待回答问题。用户此时 Ctrl+C 的意图是暂停 Agent。若该键只是 reader 的退出／停止跟随，执行保护手势又随层变化；若全局暂停，需要 reader 明显说明含义。用户必须有路径知道新失败和问题，并进入 editor，同时 reader 与原生 scrollback 都回到进入位置。若 reader 独占输入且隐藏稿，读写并行承诺不成立。原生终端回滚的优点不自动解决应用内目标绑定和新结果发现。

**对象工作台。** 用户提出“解释 `/me` 为何200，先别写”，先看 auth.rs，再看日志；Agent 的新问题是“401还是403”。用户回复后想看先前的解释正文。若正文是另一个对象／tab，这条路至少需要识别文件、日志、问题、答案四类对象并切换；若对象列表按新内容自动排序，正在选择的条目甚至会换位置。工作台若只按文件组织，会让“为何200”的因果解释无家可归；若把所有消息都提升为对象，会使清单成为另一条更密的时间线。要求方案给出80列实际路径，不能以宽屏便利替代。

**用户可编辑的任务契约。** 用户首先要求修复，然后在测试已启动时输入“只解释先别写”。界面中的原契约若仍写“修复并补测”，新消息必须使旧契约在哪一时刻失效？Agent 若自动重写契约，它不能覆写用户正编辑的草稿；用户若自己编辑契约，把“返回401”改成“返回403”但尚未提交，它不能影响执行。若保存即生效，则局部编辑每个字符都有执行语义；若提交后生效，需要接收／消费两份版本和历史，不是一个“已保存”标签。之后的“现在可以改”还需明确继承哪些旧约束。契约合并需要 Agent 在 Job 内思考，UI不能代替它生成授权和意图。

对这三类模型，共同门槛是：指出每一步可见对象、草稿存放位置、全局停止效果、后台事件到达后的焦点，以及已发生事实与正在编辑意图的区别。不能只用“焦点不变／草稿保留”的句子跳过转移过程。

一个共同反例仍需修：共用底线把已关闭Q1的回复写成“Q1已关闭；作为补充”。用户原本明确回答Q1，不能因目标关闭就自动变成独立要求；应保留草稿、显示目标失效，让用户显式选择另发。选择对象、复制对象、关闭对象和目标失效，都不能偷偷改变消息作用。

我不建议把上述四者混成常驻四区。优先验证的是受约束的线性对话：真实状态持续可见、证据从所在处进入并回到所在处、原稿与明确回复对象独立。对象工作台与任务契约的所有控制结构不进入默认模型。

### 检查并修订合成原型的诚实边界

本次读取的 `index.html` 明确写了合成情景与生产未实现，这个声明需要保留。与此同时，纸面声明与交互代码仍有以下冲突，已发送主代理修正请求：

1. `screen()` 根据 `step===5` 自动把输入标题改成“回答Q1”，与旁边“明确选择回答后才绑定”的说明冲突。即使没有真正提交函数，显示作用已变。应有独立且仅由用户改变的 reply target 状态；新问题只显示未答入口。
2. `openEvidence()` 在任务刚收到／检查仍运行时也渲染同一份未来的失败证据，包含尚未发生的结束时间、exit101、编译失败。证据必须按合成步骤选择，不存在结果时只能展示当前可用输出。
3. reader／checking 在终端格内把输入替换成“阅读中，输入已保留”；页面外的 textarea 仍可编辑。这只能证明独立的网页textarea文本没有被清空，不能验证终端的读写并行、焦点、光标、选区或回复目标恢复。这里只能称文字留存示例；需要后续Rust原型检验完整契约。
4. 资料入口把 Emacs、Ableton 和中断研究都链接到本文件，而这些实际在 `divergence.md`。Zellij“离开scroll仍保留位置”的直接出处是官方 keybindings-modes。Pi 的引用应采用本次读过的固定SHA。不能让一个笼统PRIMARY标题替代逐项出处。
5. “已纳入／生效”是指Agent或执行版本已经接受新要求，不表示之前的物理动作已经结束。闭合工具事件、交付和新问题不能更改草稿目标。若原型只更新状态字符串，它尚未证明后台事件生命周期和回复绑定。

另一个实质修订：**cargo test/cargo check 不能按命令名称称为只读**。它们可能写构建产物、执行build脚本，测试本身也可能有副作用。新要求可以阻止尚未启动的新动作，但不能据此断言已启动命令之后没有写入。本情景只能明确约定“新源码修改被阻止；先前启动的检查仍在运行”；这个源码范围来自用户要求与合成执行记录，不来自test名称。若用户要求“禁止一切写”，应使用真实停止与核查路径，不将模型已纳入当作物理静止。

以上是源码阅读发现，不是浏览器/终端操作实测；主代理后续可能已修改页面，保留此节作为交叉对抗记录。最终推荐不能写成“这些设计问题已修复”：本轮完成了研究、筛选与合成原型，生产修订和同轨迹终端验证仍待实施。
