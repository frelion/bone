Executive verdict

基座已具备；缺的是完整的上下文生命周期。

Bone 已经避开了传统 transcript 回放的主要陷阱：它将权威事实保存为不可变 Record，按 Job 投影模型输入，并只压缩已读前缀。这个方向应当保留。

但目前它仍是局部的 Runtime 内压缩骨架，尚未形成稳定的跨 turn、跨 Runtime 连续性。最紧急的风险不是摘要文笔，而是：新回合看不到刚完成的结果、Core 字节预算不等于真实模型窗口、分页正文可失联，以及 history 绕过 Job 边界。

保留

不可变事实、Job 隔离、evidence、分页、已读前缀压缩。

补齐

统一 ContextPlanner、结构化 Working Memory、Session Capsule 与物理增长治理。

Current foundation

现在的实现不是没有上下文管理，而是两套尚未闭环的机制。

Runtime 内，Core 以 Job 为边界重建 WorkInput；跨 Runtime，App 从 durable public events 中摘取近期 background。 两者各自有价值，但还没有共同的连续性与预算契约。

01 · AUTHORITY

不可变事实

已被 Agent 接受的输入及其工具结果、回复、Outcome 进入不可变 Record / agent journal；App 输入生命周期另以 SessionEvent 持久化。两者共同构成可审计事实。

02 · RUNTIME

按 Job 投影

每轮 Worker 组装 spec、constraints、checkpoint、records、calls 与 tools，而非回放完整聊天。

03 · COMPACTION

已读前缀 checkpoint

超限时将已成功交给模型的旧 records 压成 summary + evidence，未读后缀保持原样。

04 · RESTART

近期 public bootstrap

新 Runtime 从 session history 取最近事件作为只读 background；它不是稳定的 Session 记忆。

1

模型输入膨胀

单次请求能否真正装进 provider window，并留出输出空间。摘要只能部分解决它。

2

Runtime 热状态膨胀

records、jobs、calls 与全量 AgentView 持续增长，影响内存和 observe 成本。

3

持久历史膨胀

append-only journal、启动扫描和历史读取需要索引、快照、冷热分层与 retention 协议。

关键判断：一个 summary 机制无法同时解决这三种增长。必须分别处理“模型投影”“热状态”和“耐久历史”。

P0 risks

先修这些断点，再谈更聪明的摘要。

以下问题会直接造成遗忘、越界、不可恢复的失败或上下文自我放大。它们都是架构不变量问题，而不是 prompt 调优问题。

P0 · 连续性

普通追问可能看不到刚完成的结论

bootstrap 只在 Runtime 创建时生成；新的 Coordinator 自动投影只含当前输入、constraints、冻结 bootstrap 与未完成 root。用户说“按上面的方案实现”时，刚完成的 Reply / Outcome 不会自动进入下一回合。

P0 · 预算

context_bytes 不等于真实 provider 窗口

Core 预算的是 DTO 字节；Adapter 之后还追加 instructions、外层包装和 tool schema，且没有统一 output reserve。Core 合规并不能保证请求真的可发、可输出。

P0 · 隔离

session_history 混淆了 UI 历史、模型记忆与 Job 权限

worker 可读取 session-global 的公开 history；由于当前 ToolFinished 会投影为公开事件，它可能看到未通过 Job delivery / evidence 链路进入的 sibling 工具结果。其返回又可形成 ToolFinished，存在 history-of-history 的递归放大路径。

P0 · 分页

checkpoint 后，大正文的下一页可能失去可发现性

read_through 表示模型见过通知，不表示已读完整 body；checkpoint 没有结构化保存未完成的 source / offset / cursor。

P0 · 可表示性

合法状态也可能完全无法构造下一次调用

children、inquiries、calls、background、tools 等固定区块不可分页，records 即使全部压缩，仍可能因合法对象数量增长而 TooLarge。

P0 · 可靠性

内部 compaction 失败有机会直接终止用户 Job

provider 临时故障、超时、截断或不合格摘要应是可恢复的维护状态；它们不能天然拥有结束业务任务的权限，也不能引发重复副作用。

Target model

用分层代替一个万能的 ContextManager。

权威事实、单 Job 工作记忆、跨 Runtime 会话记忆、检索和物理回收的职责不同。混在一个对象里，最终会让摘要拥有不该有的权威，也让 retention 变得不可验证。

Raw Records / Journal

输入、工具调用与结果、回复、Outcome、记录证据。它是审计、恢复与重建的唯一权威来源。

权威 · 不可变
ContextPlanner

按 Coordinate / Work / Compact 的真实预算，纯函数式地选择 pinned、checkpoint、recent tail、retrieved 与 omitted manifest。

派生 · 可重放
Job Working Memory

单个 Job 的决定、完成项、失败尝试、open loops、artifact 状态与未读 cursor；控制当前 Runtime 的工作窗口。

派生 · Runtime-local
Session Memory Capsule

跨 turn、跨 Runtime 的用户可见连续性。由 App 拥有、版本化、带 stable provenance，且可从原始事实重建。

派生 · 耐久
Retrieval Index

用于很久以前或跨 Session 的按需召回。embedding / vector 索引永远是可重建的辅助层，不是事实源。

可选 · 可重建
Retention / GC

热数据、冷数据、归档与真正删除。必须在 evidence、cursor、artifact lineage 和 history cursor 的引用闭包定义之后实施。

物理生命周期
不可妥协的权威规则：memory 与 checkpoint 都是“带出处的派生视图”。它们可以帮助模型回忆，不能覆盖 raw facts，更不能凭自身扩大权限或重新授权行动。

Planning & compaction

把“能不能塞进模型”变成可验证的规划问题。

ContextPlanner 应在完整请求形式上闭合预算；字节上限继续用于内部安全，但模型调用必须以 token window 为准。不同 consumer 有不同模型、工具和输出需求，应分别规划。

最终请求预算

available_input_tokens =
    model_context_window
  - reserved_output_tokens
  - instructions_tokens
  - tool_schema_tokens
  - provider_envelope_tokens
  - safety_margin

最后一跳由 Adapter 对完整 messages + tools 验证。Provider usage 应回传给 Planner，用于成本、真实余量与策略观测。

  1. Pinned：当前输入、contract、constraints、未回答 inquiry、active/unknown side effect、waiting state、未完成 cursor。
  2. Working memory：结构化 checkpoint，含完成项、决定、失败尝试、open loops 与按 claim 绑定的 evidence。
  3. Recent raw tail：保留近期原始语义尾部，避免只剩摘要导致漂移与因果断裂。
  4. Retrieved：按需引入长历史；明确标注为低权威的检索内容与出处。
  5. Optional：最后才丢生命周期噪声、重复状态和完整旧日志；pinned 本身超限时返回 typed overflow，而非静默篡改。

压缩必须有 liveness 证明

触发可采用约 75–80% 高水位，目标压回 50–60%，保留约 20–25% 原始尾部。更重要的是每次压缩必须证明尺寸实质下降、达到最小节省量，并为下一条 mandatory item 留出空间。

cursor 是 Kernel 状态，不是摘要文案

维护 { source, next_offset, state } 的消费账本。模型可以确认某页已满足，但不能仅依赖自然语言 summary 记住“还有第二页”。

Product contract

这几条语义，需要在实现前先由产品定下来。

你最值得参与的不是“摘要 prompt 怎么写”，而是哪些历史应连续、哪些事实可忘、哪些权限绝不能由记忆恢复。这些选择决定后续数据模型和测试边界。

决策 建议默认值 原因
同一 Session 的普通追问 跨 turn、跨 Runtime 保持认知连续性 此前目标、决定、结果、产物状态、未决项应可见，否则自然追问会断裂。
重启与副作用 恢复状态，不自动恢复行动 memory 可以说“此前运行到哪”，但不能重新发送、写入、执行或扩大曾经的授权。
跨 Session 召回 第一版默认关闭；以后显式 opt-in 先把单 Session 的确定性、隐私和可解释性做稳，再引入长时或 Workspace 记忆。
超大当前输入 转不可变 attachment + 分页 ingestion，或明确拒绝 当前用户授权不能被静默摘要。不能出现“App 接受了输入、Coordinator 注定装不下”的灰区。
长期记忆中的工具信息 保留脱敏摘要、稳定 ref、参数 provenance；正文按页读取 只记工具名与结果会丢失 command/path/query 上下文；整段原始输出又会污染 bootstrap。

Delivery order

按不变量推进，而不是按“摘要功能”推进。

0

先写 RFC 与边界测试

固定 Session continuity、authority、privacy、restart、overflow 与 retention 的语义。先让不变量可读、可争论、可测试。

1

闭合真实模型预算

Provider window 元数据、完整 envelope 计数、output reserve、usage 回传、typed overflow，以及最多一次 compact → retry。

2

修复连续性与 history 边界

每次输入接受时创建冻结的 Session Context snapshot；将 UI/audit history 与 model memory 分离；消除 history 自我递归。

3

升级 Job Working Memory

结构化 decisions、failures、open loops、artifact state、frozen evidence boundary、cursor ledger 和 recent raw tail。

4

实现耐久 Session Memory Capsule

App-owned、版本化、可重建；raw facts 耐久后再原子更新 checkpoint head，新 Runtime 用 capsule + recent tail 启动。

5

治理物理增长，最后才做 retrieval

增量 observation、热点索引、body 冷存储、schema migration、retention 协议；向量检索永远保持为可重建派生层。

Acceptance gates

第一阶段的完成标准，应该是这些失败模式被锁死。

若第一期只能投入五组架构测试，建议优先锁住能否调用、压缩是否越界、分页是否连续、历史是否隔离、重启是否安全续上这五条基本生命线。

测试 场景 必须成立的不变量
A · 真实窗口预算 Coordinate / Work / Compact；ASCII、中文、emoji、大 schema 完整 provider request 的输入 token + output reserve 不超过实际模型窗口。
C · 冻结边界 checkpoint 冻结于 T；T+1 在 compaction 中抵达；同时变更 contract T+1 不可作为旧 checkpoint evidence；新数据保持 unread；旧 revision checkpoint 被丢弃。
D · 分页连续性 关键事实只在第 2/3 页；连续执行 20 次 checkpoint 无测试私有 offset 提示时，模型仍可从结构化 cursor 发现并读取余页。
F · history 隔离与非递归 sibling A/B 分别产生工具结果；连续读取 history 100 次 未 publish 的 sibling 内容不可见；history 不嵌套 history；增长斜率有明确上界。
G · 重启恢复 checkpoint durable 后、Outcome 前模拟崩溃 重启保留目标、进度、失败、open loops、evidence 与 cursor；绝不自动重复副作用。
