# 主力推进任务，协调只判断插话

状态：2026-09-06 已实现主力驱动与插话审阅，使用同一套事件内核和异步作业执行器。
本文固定当前架构的权限、交错规则与验收要求；旧 `Decide / Analyze` 路径已移除。
可以通过 `walkthrough`、`interleaving` 和事件观察接口检查真实实现。

## 先掌握这一条循环

```text
用户要求 → 主力模型 → 工具 → 主力模型 → …… → 答案
                        ↑
                 工具结果、错误、软提醒

主力正在推理时收到插话 → 协调判断是否影响当前工作
                        ├─ 不影响：原推理继续
                        ├─ 需要重想：原话交回主力
                        └─ 要求暂停：停止自主推进
```

正常求解完全由主力推进。没有插话时，协调模型调用次数应当为零。
协调只补一个缺口：主力正在进行一次较长推理，此时需要理解新消息，
又不能因为每一句“进度如何”就重新启动主力。

主力空闲时，用户原话直接交给主力。工具还在运行，不等于主力正在推理：
此时只要没有未提交的主力结果或未结束的协调请求，就可以直接处理新输入。
主力结果已经回来、正在等待插话解释时，也视为有一项尚未提交的主力决定。

## 谁决定什么

| 问题 | 决定者 |
| --- | --- |
| 采用什么方案、深入哪个方向、使用哪个工具 | 主力模型 |
| 工具结果意味着什么、是否换方法、答案是什么 | 主力模型 |
| 卡住的工具还要不要等、是否取消、是否绕开 | 主力模型 |
| 忙碌时收到的插话是否需要交回主力重新考虑 | 协调模型 |
| 插话明确要求暂停吗 | 协调模型；显式 `stop()` 直接由代码处理 |
| 作业是否结束、调用是否超时、旧决定是否失效 | 代码 |
| 能否再开始一个写操作、通知如何发送、如何启动调用 | 代码 |

“需要理解语言”不是把判断交给协调模型的充分理由。
判断方案是否正确、旧分析是否还有价值，都属于求解，应由主力完成。
协调可以依据已有状态回复“检索仍在运行”；“为什么这个检索方案不好”必须交给主力。

所有原始用户消息保留在共同记录中，协调摘要不能替代用户要求。
如果保留 `requirement` 摘要，只允许主力更新，它也不能覆盖原话。

## 协调调用的权限只有三个选项

返回协议，省略序列化标注：

```rust
pub struct InputReview {
    pub disposition: InputDisposition,
    pub reply: Option<String>, // 简短交流或已有状态，不能承担任务求解
    pub note: String,          // 可观察的判断理由，不是内部思考过程
}

pub enum InputDisposition {
    Keep,       // 明确不改变任务，原结果仍须通过代码检查
    Reconsider, // 主力需要读这批原话并重新决定
    Pause,      // 这批输入要求暂停自主推进
}
```

- `Keep` 只用于明确不改变任务的状态询问、确认或闲聊。它不代表主力答案正确。
- `Reconsider` 包括新增要求、否定方向、专业追问和含义不明确的插话；不能附带替代方案或工具建议。
- `Pause` 取消当前自主工作的资格；不能消耗后来才收到的输入。

例如“进度怎么样？顺便别用 A”必须进入 `Reconsider`，不能只回答前半句。
“为什么 A 会死锁”也交回主力，协调不能自己完成这道技术题。
只有主力解释了新的原话，才决定保留、修改还是放弃原方案。

协调输入是共同记录的一个小视图：固定的用户消息批次、相关用户要求、
主力已公开的工作说明、作业状态和已报告的进度。
它不接收工具定义，不需要复制全部文件内容和分析产物。
上下文不足以确定 `Keep` 时，转交主力；不增加一次“协调深入分析”。

这是带有权限边界的模型判断，不是语义正确性的证明。
误把改要求判为 `Keep` 仍可能放行旧建议，必须通过混合指令、否定和歧义测试评估。
代码负责固定批次、阻止越权和检查版本，不能证明自然语言没有改变含义。

## 核心保持三个模块、同一种调用生命周期

```rust
impl Kernel {
    pub fn step(&mut self, event: Event) -> Vec<Effect>;
}
```

`step` 不调用模型或工具、不等待 I/O，也不读取系统时间。

- `kernel` 唯一修改记录和会话状态，决定哪些建议可以提交。
- `runtime` 启动作业、监督完成与取消、管理定时器，把结果送回内核。
- `ports` 提供一次模型调用或一次工具调用，不包含另一个 Agent 循环。

模型与工具继续使用同一套 `Start / JobFinished / JobProgress / RequestCancel`。
主力、协调只是调用用途与结果权限不同，不各自拥有收件箱、历史和执行器。

```rust
pub enum ModelTask {
    Work { messages: Vec<Message> },
    ReviewInput { messages: Vec<Message> },
}

pub enum JobOutput {
    Work(WorkResult),
    InputReview(InputReview),
    Artifact(Value), // 工具返回的数据，不能获得模型执行权限
}
```

`WorkResult` 承接原 `Decision` 的求解能力：`note`、`reply`、
主力维护的可选 `requirement`、`autonomy`、`operation`、`next`。
操作只保留 `Tool` 和 `Cancel`，删除“协调请求主力分析”的 `Operation::Analyze`。
`Continue / Wait / Finish` 由主力选择，连续多次纯推理不需要工具。
`Continue` 立即发起下一次推理；如果下一步需要工具结果，选择 `Wait`，由结果事件唤醒。
主力答案通过代码检查即可发布，不需要协调重新组织一遍。

保留现有 `Autonomy::Keep / Run / Pause` 的运行控制：新用户输入可以让主力提出 `Run`，
后台结果不能让已停止的会话自行恢复。“谢谢”可以只回复并保持暂停；
不能把“收到任意新消息”直接写成恢复规则。`Continue` 要求自主推进已开启，`Finish` 停止自主推进。

角色以 Kernel 登记的请求为准。协调返回伪造的主力结果，或结果出自已撤销请求，
都不能获得操作权限。限制同时落实在返回类型、适配器校验和内核中，不能只靠提示词。
系统级配置仍选择协调模型，任务配置只选择主力模型。
端口需支持两种用途各一次并发调用，不能用跨越网络等待的互斥锁把它们串行化。

## 调度只记住眼前这几件事

除已有记录、作业表、自主状态和版本外，内核保存：

```text
work               当前本地主力请求，最多一个，包括正在取消的请求
candidate          已返回但尚未提交的主力结果，最多一个
review             当前插话解释请求及其固定批次，最多一个
pending_messages   后来收到、尚未分配处理的原始消息
need_work          是否需要主力再考虑一次；重复提醒合并为一个标记
```

主力的 `work` 与 `candidate` 不同时占用：请求结束后可以转为一个暂存结果。
取消中的旧请求仍占本地槽，直到 Runtime 返回结束事件。
不引入任务树、意图树、多份对话或可执行方案队列。

每个模型请求固定自己的消息批次和快照。启动后收到的新消息属于下一批。
一批消息只按自己的 ID 标记处理，不能用“当前队列全部已处理”代替。
`Keep` 的交流批次可以由协调完成；`Reconsider` 只完成分类，原批次必须明确转入
下一次主力的 `messages`。凡未提交且仍需主力重新考虑的结果，包括被替换、依据过时、
因写入规则被拒绝的结果，其尚未处理完的原始批次都按消息 ID 去重、按原顺序归还；
已被 Pause／Stop 来源边界撤销的消息除外。模型失败后的暂停不触发自动重试。
不能只把原话留在历史里，却让下一次主力的输入批次为空。
这样主力才能明确承担新要求，并在符合暂停边界时提出 `Run`。

| 收到的事件 | 内核行为 |
| --- | --- |
| 用户消息，主力空闲，无暂存结果或未结束的协调请求 | 直接启动主力，读取原话和最新记录 |
| 用户消息，主力正在推理或结果等待提交 | 固定一批启动协调；已有协调请求时只追加到下一批 |
| 主力结果返回，仍有未解释的后来输入 | 保存为 `candidate`，暂不发布回复、执行操作或确认完成 |
| 协调返回 `Keep` | 只消费自己的批次；仍有下一批时继续解释，否则重新检查暂存结果 |
| 协调返回 `Reconsider` | 撤销原决定资格，把原批次转给下一次主力；有在途主力则请求取消 |
| 协调返回 `Pause` | 暂停、撤销原决定、请求取消；保留后续输入 |
| 工具产生实质结果 | 记录、增加决定依据版本；自主运行时请求主力再考虑 |
| 工具软提醒到达 | 记录提醒并请求主力考虑，不把工具判为失败 |
| 普通工具进度 | 只更新记录和通知，不调用任何模型 |
| 显式 `Stop` | 立即撤销此前模型资格、停止自主推进、请求取消；继续接收工具真实结果 |

主力正在取消时，新输入先留在队列；本地结束后用最新输入启动主力，
不为已撤销的推理创建额外替代请求，也不把已转交主力的批次再送去协调。
已有协调批次仍按自己的顺序完成。
启动新的主力前，先处理当前未结束的协调批次，避免绕过输入顺序。

直接交给主力的固定批次由这次主力解释，不再额外调用协调。
提交时的“未解释输入”指这次主力快照之后尚未解释的消息，不能把自己的批次算作阻塞。

## 主力结果返回后，代码检查四件事

1. 请求 ID 与运行代次仍有效，且它是被授予求解权限的请求。
2. 没有不属于这次主力批次、也未被协调处理的新增用户消息。
3. 决定依据没有变化。
4. 工具和运行规则允许这项操作，例如没有另一个结果未明的写入。

主力的 `reply / requirement / autonomy / operation / next` 作为整体，先检查再提交。
只有 `note` 等材料可以先记录。不能照搬旧 `finish_decision` 在新鲜度检查前
先发布批次回复、更新要求的行为，否则旧 A 答案仍可能在用户已经要求 B 后发出。

记录位置和决定依据版本分开。所有信息进入记录；普通进度、纯状态询问不使依据失效。
协调判定 `Reconsider`，以及工具产生实质结果，才使原决定需要重新考虑。
首版保守地把所有工具终态结果视为实质结果；暂不另设模型判断每条结果是否相关。
版本不符只表示旧建议不能直接执行，不表示它的技术内容错误。

过时结果作为材料保留，下一次普通主力结合新事实决定如何使用。
被写入规则阻止的建议也记录原因并交回主力，不偷偷排队到以后自动执行。
多个工具结果到达时只合并一次 `need_work`，不反复取消并重启正在进行的主力。
协调的有效性绑定自己的固定批次和运行代次，不能因工具结果更新而不断作废。
否则工具持续返回结果时，用户的“暂停”反而可能永远解释不完。
协调的状态回复标明来源快照位置；旧快照中的“正在运行”不能伪装成实时查询结果。

## 用四个过程检验边界

### 长推理时询问进度

```text
W1 正在推理
用户：“到哪了？” → 启动 C1；W1 继续
C1 返回 Keep 和基于已有状态的回复
W1 返回 → 代码检查 → 执行 W1 的下一步
```

W1 的 JobId 不变，没有重启，也没有协调审批技术方案。
如果 W1 先返回，就暂存等待 C1；C1 未解释完时收到的新消息不会被漏过。

### 深入 A 时，用户要求不要 A

```text
W1 正在深入 A
用户：“不要 A，考虑 B。” → 启动 C1
从收到原话起，W1 的新建议不能直接提交
C1 返回 Reconsider
撤销 W1 资格 → 请求取消 → 收到本地结束事件
W2 读取原话和最新事实，自己决定 B 怎么做
```

C1 不分析 B、不写新计划、不选择工具。
即使任务只是探讨方案，旧 A 答案也受同样的提交检查约束。
已收到或取消竞态中收到的 A 结果保存为旧材料，不再当作当前回复发布。

### 工具长时间不返回

```text
W1 提议启动 T，并选择 Wait
Runtime 运行 T；主力槽空闲
30 秒软提醒 → 代码直接启动 W2，说明 T 仍未结束
W2 决定继续等、查询、取消或换办法
```

整个过程无需协调。此时用户提出新要求，空闲主力直接处理。
如果 W2 已在推理，提醒只合并，不另开并行 W3。
取消请求不证明 T 停止，更不证明外部写入没有发生。

### 工具先结束，旧建议后回来

```text
W1 基于“写入 T 仍未决”的快照推理
T 成功 → 更新记录与依据版本
W1 返回新的写入建议
代码发现 W1 依据过时 → 保存材料，不执行
W2 读取 T 的真实结果，再决定下一步
```

写入名额空出来，不代表旧建议现在就正确。
此处不需要协调理解 W1，只需代码核对版本，再由主力重看。

## 取消、暂停和完成要说实话

**一个本地主力请求槽足够首版。** Runtime 在可放弃的只读调用 Future 外层监听取消，
不依赖模型端口自己检查信号。先撤销资格、再请求取消，收到本地 `JobFinished`
后释放槽并启动替代主力。取消与成功竞态时，旧请求都已失去执行权限。
同一监督策略适用于可放弃的只读工具，不另造模型执行循环。

丢弃 Future 只结束本地等待，不保证服务商停算，也不保证远端并发或费用只有一份。
只能承诺保留已收到的旧结果，不能承诺每个取消请求的最终答案都会回收。
端口 Future 必须异步让出执行器，不能隐藏继续启动模型和工具的 Agent 循环。
旧请求的取消或超时只结束旧请求，不能误停新输入要求启动的工作。
当前有效模型请求失败或超时，仍发布错误并暂停；不自动无限重试。

**写操作采用保守处理。** 取消后继续接收真实结果；传输失败和超时可能意味着 `Unknown`，
不能当作没有写入。最多一个结果未明的写操作，查询和取消仍允许。

交叉审查补齐了一个事实输入：调用已返回 `Unknown` 后，宿主取得外部确证，可以调用
`AgentHandle::resolve_write(id, outcome)`，通过同一个 `JobFinished` 事件确认结果。
它只接受已结束且结果未知的写作业，以及 `None / Applied` 的工具数据或错误结果；
不能用主力或协调的输出确认写入。相同确证重复提交是幂等的，不同的再次改写会被拒绝。
停止后确认只更新事实，不自行恢复。该入口不做查询，也不把模型的自然语言判断当作外部确证。
对本地已结束的未知写入再次请求取消，会明确报错，不能假装取消了一个已经不存在的 Future。

**批次里的暂停与显式 Stop 分开实现。** C1 正在解释“先暂停”时又收到“继续做 B”，
C1 的 `Pause` 只消费第一句，暂停旧工作，第二句仍须处理。
它不能调用会清空全部 `pending_messages` 的通用 `stop()`。
暂停边界是 C1 固定输入批次末尾在记录中的位置，不是 C1 回调到达的时刻。
边界之后的输入保留；被撤销的旧主力批次若位于边界之前，不能归还后又自动恢复旧任务。
显式 Stop 按到达顺序撤销此前请求；旧主力和旧协调回调都不能恢复会话。
恢复需要停止之后的新用户输入，由主力依据原话决定是否 `Run`。

**Finish 表示主力交付当前任务，自主推进结束。** 未解决的写入阻止成功 `Finish`。
残余只读调用允许由主力选择放弃：内核请求取消，在完成通知中列出仍待清理的调用，
不把它们伪装成已经结束。后续实际结果继续记录，不能自行恢复任务或再次发布完成。
这是对旧规则“任何未决后台作业都阻止完成”的明确调整，避免废弃的 A 检索拖住 B 交付。
`Finish` 仍不能同时申请新的工具调用。
已接受的回复先于 `Paused` 发布，保证终端先显示澄清问题再结束本轮；
`Pause` 与 `Finish` 同时出现时只发布 `Finished`，不产生两个结束通知。

## 事件接口用来证明分工

继续使用已有 `AgentHandle::observe()`，一份原子快照加有序 `StepEvent` 流。
观察者看到输入、内核追加记录和 Effect，不另设协调专用事件总线。
这次调整至少暴露：

- 每次主力／协调调用的用途、来源消息 ID、快照位置和依据版本。
- 协调实际返回的三个选项及简短理由。
- 主力结果何时暂存，等待哪些输入。
- 建议接受或撤销的原因、请求取消与实际结果的区别。
- 最终交付时仍在清理的只读调用，以及未明确的写入。

这些是返回协议与代码行为，不是模型隐藏的思考过程。
慢观察者不能阻塞工作，遗漏通过序号和 `Lagged` 暴露。
扩展使用显式输入接口影响工作，不能通过监听回调修改 Kernel 或偷偷启动下一步。

## 对抗审查舍弃的方案

| 方案 | 为什么不采用 |
| --- | --- |
| 协调先理解所有要求，再给主力派分析任务 | 任务分解与下一步选择落到较弱模型，正常路径每轮多一次调用 |
| 主力提建议，协调逐项审批 | 协调仍须理解整个专业问题，性能和质量瓶颈未消失 |
| 每来一条消息就取消主力 | 连续状态询问让深度推理反复开始 |
| 多个主力快照同时跑，谁先回来谁执行 | 旧方向可能覆盖新要求；增加请求数不能取消资格检查 |
| 所有新消息排到下一次主力 | 简单，但长推理时无法及时解释自然语言暂停与状态询问 |
| 第二个主力槽专门替代被取消的请求 | 外层取消已能结束本地等待，首版无需额外槽；若必须回收所有旧输出再讨论 |

系统始终可以接收输入，不意味着每个专业追问都能同时获得主力深度回答。
首版遇到专业插话会交回主力，必要时替换原推理，不让协调为了“秒回”越权做题。
持续收到尚未解释的新指令时，旧建议提交可能持续推迟。
不能同时保证“执行前理解所有已收到的新要求”和“不管新消息多少都立即执行”。

## 开源依据与适用范围

查阅固定提交，借鉴可核对的局部机制，不把项目名称当作整套设计的背书。

- **pi**：主循环从模型回复提取工具调用，把工具结果和 steering 消息交回后续模型请求。
  借鉴主力持有工具循环；该循环仍等待一次模型和工具批次，不能直接满足卡住时重新考虑的需求。
  [主循环源码](https://github.com/earendil-works/pi/blob/9767ba275f3e9a5ee0f5c5342249b629ab1b2282/packages/agent/src/agent-loop.ts#L156-L254)
- **Codex**：统一命令执行器先保存存活进程，再有限等待；返回结果可以携带进程 ID。
  借鉴外部工作寿命长于一次模型调用，不能由此推断所有工具都不会阻塞下一轮推理。
  [进程保存与等待](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/core/src/unified_exec/process_manager.rs#L565-L618)、[进程 ID 返回](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/core/src/unified_exec/process_manager.rs#L791-L810)
- **OpenCode**：标题生成使用单独选择的辅助模型，工具集合为空；求解循环另行运行。
  这是辅助职责有限的具体例子，不证明它使用了本文的插话协议。
  [标题调用](https://github.com/anomalyco/opencode/blob/337fd144d2ba144743368f78d9579a99cce175bd/packages/opencode/src/session/prompt.ts#L193-L242)、[求解循环](https://github.com/anomalyco/opencode/blob/337fd144d2ba144743368f78d9579a99cce175bd/packages/opencode/src/session/prompt.ts#L1226-L1286)

固定批次、暂存结果、插话权限和保守写入的组合，是针对 BONE 用例作出的设计决定。

## 实现切口与验收

先改变结果权限和正常路径，再处理交错，最后接真实模型。不能仅修改提示词便宣布重构完成。

1. **归还求解权。** `ports.rs` 定义两类请求与输出；Kernel 让主力直接选择工具、继续和交付，删除 `Analyze` 派工路径。
2. **只在插话时协调。** `kernel.rs` 固定批次、暂存结果、区分记录位置与依据版本，落实三个选项和 Stop 顺序。
3. **执行与可观测性。** `runtime.rs` 对可放弃调用实施外层取消，补齐暂存原因、权限变化和完成清理信息。
4. **可控端口通过后接真实模型。** 在 `bone-agent/src/model.rs` 接入协议与配置，终端前端只使用 Agent API，更新 walkthrough、crate README 与真实验收。

| 验收场景 | 必须得到的结果 |
| --- | --- |
| 无插话，连续十轮工具求解 | 协调调用为零；主力直接取得每次结果 |
| 三次纯推理 Continue 后 Finish | 无工具也能推进；主力答案直接发布 |
| 长推理期间连续状态询问 | 固定批次可完成；同一主力 JobId 不重启 |
| 主力先返回，协调还未返回 | 回复、工具与 Finish 都暂存 |
| 协调解释第一批时收到第二批 | 第一批不误处理第二批；暂存结果仍受检查 |
| 协调将新要求转交主力 | 新主力持有原消息 ID；取消或过时的旧批次不丢失，也不重复协调 |
| “进度如何，顺便不要 A” | Reconsider；协调不制定 B，主力读取原话 |
| 纯讨论否定 A，旧 A 返回 | 保留已收到材料，不发布成当前答案 |
| 工具先完成，旧建议后到达 | 即使写入名额已空，也交回主力重新考虑 |
| 工具不返回，软提醒触发 | 直接唤醒主力，输入可处理；不调用协调 |
| 模型端口不主动检查取消信号 | Runtime 结束本地等待、释放槽，再启动主力 |
| Stop 后旧主力／协调返回 | 不恢复、不回复旧任务、不启动工具 |
| 暂停批次处理中又收到“继续 B” | B 留在队列，不被暂停清空 |
| 停止后只说“谢谢” | 可以回复，不自动恢复旧工作 |
| 写操作拒绝取消，后来成功 | 保留未决状态，记录真实成功 |
| 已返回 Unknown，宿主后来报告确证 | 通过 Runtime 更新原作业、解除写入门禁；错误或重复确认不产生多余操作 |
| 废弃只读 A 未结束，B 已解答 | 可以交付 B 并取消 A；未知写入阻止成功 Finish |
| 重复完成、过期唤醒、旧模型取消或超时 | 不重复交付，不启动旧操作，不误停替代工作 |
| 观察消费者变慢 | Kernel 不阻塞，消费者明确获知遗漏 |

定时测试使用 Tokio 单线程测试运行时与虚拟时间。
首版不增加持久化、复杂依赖图、多主力并行求解或自动无限重试。

本轮实际测试、发现并修复的问题和真实事件见[重构验收记录](certifications/bone-agent-2026-09-06-solver-loop.md)。
