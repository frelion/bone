01 / approval summary

先批准六个核心判断

这六条不是未来规划，而是当前实现的结构性事实。技术审批的重点，是确认这些语义足够小、足够稳，能作为后续能力的底座。

Authority

Agent 自主产生 Action

调用方只提交用户输入；父模型决定直接回答，还是通过私有 start_action 创建一个或多个 Action。不存在公开的“提交 Action”入口。

Isolation

每个 Action 拥有独立上下文

兄弟 Action 不共享内部 Turn，也不会读取彼此的中间工具结果。它们只在整个批次结算后，各自以一个终态结果回到父 Agent。

Atomic unit

Turn 包含完整工具批次

一个 Turn 是一次 Action 模型响应，加上该响应产生的全部工具调用及其结果。批次未完全结算，Action 不会进入下一 Turn。

Concurrency

工具并发，模型串行

同一 Turn 的工具并发；不同 Action 的工具也能重叠运行。整个 Agent 同一时刻最多只有一个模型请求在飞。

Barrier

父 Agent 等待整批 Action

一个快 Action 可以先完成，但父循环只有在本轮所有 Action 都完成或失败后，才获得整批结果并作下一次决策。

Settlement

公开 trace 永远已结算

AgentReply::actions() 中不会出现 pending 工具。成功、失败、超限、截断都先落成确定状态，再跨越公开边界。

审批建议： 批准当时的“双层循环 + 中央调度器 + 整批屏障”作为首版方案。它保持了 Action 的语义完整性，也解决了“长工具阻塞所有其他 Action”的问题。 如果未来要求父 Agent 消费部分结果，应单独设计事件、历史和取消协议，而不是在现有循环上加一个布尔开关。

03 / parent controller

Agent Loop：决定回答，还是创建工作

父循环是用户会话的唯一控制者。它不执行真实工具，只把清晰的 intent 变成隔离 Action，并消费其终态结果。

一次 Agent::chat 的控制流

max 32 decisions
Pseudo code

父循环的最小形状

conceptual Rustagent.rs
async fn chat(&mut self, user_input) {
  let mut working = self.history.clone();
  working.push_user(user_input);
  let mut completed_actions = Vec::new();

  for _ in 0..MAX_DECISIONS {
    let response = parent_model(&working.input).await?;
    validate_response(&response)?;
    let calls = response.tool_calls().collect();

    if calls.is_empty() {
      let text = require_text(&response)?;
      working.push_response(&response);
      let reply = AgentReply { text, actions: completed_actions };
      self.history = working;       // 唯一提交点
      return Ok(reply);
    }

    ensure(calls.len() <= MAX_ACTIONS_PER_DECISION)?;

    // 先按旧 action_context 创建 Action / rejection；
    // 当前 parent response 此时还不在 context 中。
    let starts = parse_calls(&calls, &working.action_context);
    working.push_response(&response);

    let actions = drive(accepted_actions(&starts)).await;
    for start in starts_in_original_order {
      working.push_tool_result(
          start.call, accepted_result_or_rejection(start, &actions));
    }
    completed_actions.extend(actions);
  }

  Err(DecisionLimit)
}
Important semantics

四个容易忽略的控制规则

  • 调用优先：响应同时含文本和 start_action 时，文本不是最终回复；进入 Action 分支。
  • 快照先于创建响应：新 Action 继承创建它之前的 action_context，不会把自己的创建指令重复塞入上下文。
  • 拒绝可恢复：错误工具名、畸形参数或空 intent 不创建 Action，而是以控制工具结果反馈给下一次父决策。
  • 错误是事务边界：父模型失败、超时、不完整或超限时，当前 chat 的工作历史整体丢弃。
04 / action scheduler

Action Loop：一个中央调度器推进全部 Action

当前实现没有“一 Action 一任务/Actor”。一个 drive() 持有 ready 队列和 running 工具集合，以最少的显式状态让 ready Action 依次、交错推进。

准确抽象： ready: VecDeque<ActionId> 表示可以请求下一次模型决策的 Action； running: FuturesUnordered<FinishedTool> 表示所有正在执行的工具。 Action 本身只是数据，调度权集中在一个循环里。

runtime::drive()

serial model / concurrent tools
N tools

一个 Turn 内同时启动

模型一次返回的有效工具调用全部立即进入 FuturesUnordered；返回顺序不影响 trace 的原始索引。

1 model

Agent 级串行请求

调度器不会同时请求两个 Action 模型。这压低 Provider 并发和历史竞态，但慢模型会推迟其他 Action 的下一次模型决策。

100% batch

Turn 级完整屏障

即使某个工具先失败或先成功，也必须等同 Turn 其他工具全部结算，才把完整观察交给下一次模型请求。

响应分支的精确行为
Action 模型响应的分类与精确运行时行为
模型响应是否记录 Turn是否执行工具Action 结果
模型错误 / 120s 超时否否Failed Model / ModelTimeout
空 items是否Failed Incomplete
截断响应，含或不含 calls是；calls 标记 Skipped绝不执行Failed Incomplete
calls 超过每 Turn 限制是；全部标记 Skipped绝不执行Failed ToolCallLimit
无 calls 且有文本是否Completed 文本成为 Action output
1…N 个有效 calls立即记录整批并发Waiting 全部结算后再推进

关键：Skipped 只保留在公开 trace 中，随后 Action 立即失败；不存在“下一次 Action 模型读取 skipped 原因”的回合。

05 / concurrency timeline

长工具不会冻结其他 Action，但父批次仍有屏障

这是当前并发语义最重要的例子：Action A 跑一个很长的测试，Action B 仍能继续读文件、形成结论并完成。

示例：A 运行长测试，B 快速检查配置

time →

父 Agent 先创建 Action A 和 B，然后等待整个批次。A 的第一 Turn 启动长时间测试。A 等待时，B 完成模型 Turn、read 工具和第二 Turn，先进入终态。A 的测试稍后完成，A 再进行第二 Turn 并进入终态。只有 A 和 B 都完成后，父 Agent 才开始下一次决策并回复用户。两个模型请求不重叠，但不同 Action 的工具可以重叠。

t0 t1 t2 t3 t4 t5 t6 t7 t8 t9 t10 父 Agent 创建 A + B 等待整个 Action 批次 再决策 回复用户 Action A 模型 Turn 1 run_tests · 长时间执行 模型 Turn 2 完成 Action B 模型 Turn 1 read 模型 Turn 2 已完成 Scheduler pop A pop B settle B；同时轮询 A A → ready

示意图表达顺序与屏障，不按真实耗时比例绘制。模型调用不与另一模型调用重叠；工具调用可跨 Action 重叠。

Non-blocking guarantee

A 的工具等待不占用推进权

A 启动工具后离开 ready 队列。调度器继续 pop B；B 可以经历多个 Turn 并先终止。

Parent barrier

B 完成不等于父 Agent 可见

父循环等待 drive() 返回整批 Action。B 的结果会保留，但必须等 A 也进入终态才整体回灌。

Model caveat

慢模型仍会短暂阻塞调度

请求 A 的模型期间，会继续结算已运行工具，却不会启动 B 的模型请求。最坏受单次模型超时 120 秒约束。

精确回答“长测试会不会 hung”： 默认 900 秒后该工具变为 ToolFailureKind::Timeout；完整批次结算且仍有 Turn budget 时，其 Action 可以在下一 Turn 尝试恢复； 其他 Action 在这期间可继续推进。当前没有“把仍运行的 Action 放到后台并提前返回父 Agent”的语义。
06 / data & state

状态不是新抽象，而是数据结构自然导出的事实

实现刻意没有 ActionState 枚举、Actor mailbox 或任务句柄。已有字段已经足够判定“可推进、等待中、已终止”。

概念状态机

derived, not stored

纯思考 Action 可从 Deciding 直接进入 Terminal；只有产生工具调用时才经过 Waiting。上述状态全部由现有字段推导，没有重复存储。

Ownership model

四层数据，各自回答一个问题

Agent、Action、Turn 与 ToolExecution 的数据所有权
结构持有回答的问题可变时机
Agent Model、instructions、Tools、history、Limits “这个会话如何继续？” 构建时配置；成功 chat 时提交历史
Action intent、context、Turns、terminal result “这件独立工作做到哪里？” 仅由中央 runtime 推进
Turn 一次 Response、按原序排列的 ToolExecution “模型这一步决定了什么？” 创建时写 response；随后只结算 outcomes
ToolExecution 精确 ToolCall、一个 eventual ToolOutcome “这次调用实际发生了什么？” outcome 从 None 精确写入一次
Why this is enough

三个不变量替代复杂状态机

  • 终态唯一：Action.result 只从 None 变成一次 Some。
  • 结果唯一：ToolExecution.outcome 只从 None 写入一次，并通过 action/turn/tool 三重索引定位。
  • 重排唯一：仅当一个 Turn 的所有工具结算后，Action 才重新进入 ready 队列。
公开边界：调用方拿到 Action 时，result() 和每个 ToolExecution 的查询都不会遇到 pending。

07 / protocol & history

三条信息通道，各自服务一个观察者

父 Agent、Action 模型和调用方 trace 不共享一条万能消息数组。它们保留的细节不同，但转换点集中且可追踪。

长期会话到底保留什么？
  • 成功提交后，父 input 保留用户输入、每次父 Response、每个 start_action 结果和最终父回复。
  • action_context 保留用户输入以及父模型内容/调用/控制结果的文本化表示，作为以后 Action 的背景。
  • 在 BONE 提交的长期父历史中，不保留 Action 的内部模型响应、业务工具参数和原始输出；成功 chat 后，调用方可在本次 AgentReply.actions() trace 中查看它们。Provider、工具自身或外部系统的日志与保留策略不属于此保证。
  • 上下文目前只增长：没有持久化、压缩、token 窗口治理或敏感字段裁剪策略。
08 / failure & cancellation

错误分层：谁能恢复，错误就返回给谁

模型、Action、工具和安全阀没有被压成一个字符串错误。每层只处理自己有能力恢复的失败。

错误传播与恢复责任
发生层表示下一观察者是否可继续历史语义
父 Agent 决策 AgentError Agent::chat 调用方 本次结束 工作历史不提交
Action 模型/上限 ActionError 父 Agent，JSON failed 父层可恢复 父层记录终态结果
业务工具 ToolFailure 同一 Action 的下一 Turn（若仍有 Turn budget）；否则只保留于 trace 通常可恢复 受 Turn limit 约束 完整批次结算后进入输入
截断/调用过多 ToolOutcome::Skipped + ActionError 公开 trace；父 Agent 收到 failed Action 结束 工具零副作用，不再有下一 Turn
控制调用非法 文本 ToolOutput 父 Agent 下一决策 父层可恢复 作为原 call 的结果写入
Failure privacy

操作员信息与模型信息分离

ToolFailure 同时保存稳定分类、operator message、可选 source error，以及唯一允许回给模型的 model_output。

Transactional conversation

chat 的历史只有一个提交点

  • 进入时 clone 上一次已提交 AgentHistory。
  • 用户输入、父响应和 Action 结果只写临时 working copy。
  • 只有父模型产生最终文本后，working copy 才替换正式历史。
  • 任何 AgentError 或 future 被 drop，都保留调用前历史。

这是会话历史事务，不是外部世界事务：已执行的文件写入、命令或网络副作用无法回滚。

Cancellation contract

当前取消方式是 drop chat future

没有公开 CancelHandle 或后台 Action 句柄。future 被 drop 时，运行时持有的模型/工具 future 一并被 drop；单次模型或工具超时也会 drop 对应 future。

  • Tool::call 必须是异步友好的，不能阻塞 executor 线程。
  • 清理不能依赖 future 一定运行到结束。
  • 工具若自行 spawn 脱离 runtime 的任务，取消和副作用收口由工具实现负责。
  • 超时或取消后，工具不得留下会与后续 Turn 冲突的未管理状态。
Tool failure kinds

稳定分类，保留扩展空间

  • InvalidArguments — 参数无法按 schema 反序列化
  • Timeout — 超过单工具期限
  • NotFound — 模型请求未注册工具
  • PermissionDenied — 工具策略拒绝
  • Other — 具体工具自定义失败

#[non_exhaustive] 允许后续增加稳定类别，而不让调用方穷举绑定内部实现。

安全不变量： Provider 标记截断，或一 Turn 请求超过允许数量时，调用即便看起来语法完整也不会执行。 trace 会保留 Skipped 证据，Action 随后终止，避免半截参数产生真实副作用。

One thing, one way

API 收敛原则

  • 一个模型入口：Agent::new(Model)，Provider 复杂度已由 bone-llm 隐藏。
  • 一个能力入口：Agent::tool(Tool)；没有第二套 dynamic/provider tool API。
  • 一个交互入口：Agent::chat(&mut self, input)；用户不创建 Action 或 Turn。
  • 一个 Action 终态：result() -> Result<&str, &ActionError>。
  • 一个工具观察：ToolExecution 直接暴露 call、状态、failure、model_output。

Architecture trigger

什么时候才重新讨论 Exchange？

只有当产品明确要求“父 Agent 在 Action 未结束时先返回/继续决策”，才需要新的生命周期边界。

  • 部分结果如何进入 Provider 合法历史
  • 未完成 Action 的身份、所有权和持久化
  • 事件顺序、背压、重连和重复投递
  • 用户取消与工具副作用如何传播

那会是新的产品协议，不是调度器小改。

审批会上建议追问的五个问题
  1. 当时首版是否接受：任意一个 Action 很慢时，父 Agent 等整批结束才继续？
  2. 默认理论峰值 128（且可配置增大）是否要求当前阶段加入全局 semaphore？
  3. 未来第一批写工具是否具备可证明的 drop/timeout/重试语义？
  4. 调用方是否已经需要实时进度，还是最终 trace 足够？
  5. 何种量化指标会触发模型并发、历史压缩或结构化 Action output？
