# BONE TUI 差距与产品需求

## 结论

当前 TUI 提供了内核的基本操作入口，产品层仍是原型。编辑器、命令发现、工具阅读、运行中的协作和异常恢复需要形成连续的交互流程。现有测试证明了一部分执行正确性，没有证明日常操作是否顺手；此前将这些测试作为成熟 TUI 的交付依据，判断过于乐观。

底层已经使用 Ratatui 和 Crossterm。编辑、补全、Markdown、焦点、选择器和详情弹层主要由 BONE 手写。当前有 `/xxx` 命令解析、Tab/Ctrl+P 打开的可过滤列表，以及模型/会话选择器；尚无输入 `/` 即出现并随草稿过滤的就地候选，也没有统一的参数交互。需要从交互设计、组件复用一直落实到执行接口。

本轮整理需求，没有实施新界面。BONE 基线为 `e74ea32`；2026-10-02 审查源码，并在安装版 80×24 本地 PTY 中检查 `/ → Tab`。该检查只使用合成凭据、本地服务，模型调用为零，文字重放保留在 [实际命令输入检查](results/2026-10-02-tui-gap/slash-input.json)。竞品依据官方文档和代码，尚未做相同任务、同一终端的并排试用。

## 产品原则

1. 用户看到任务、输入、答案、行动和需要处理的事项。内部 Job 的选择、创建、转交和等待由 Agent 管理。
2. 界面优先显示当前有用的信息。工具默认为短摘要，失败及等待用户处理的事项有明显入口；审计信息按需打开。
3. 输入、选择、执行必须能区分。补全和选择文件不会发送消息；可填写参数的命令不会因选择候选项而直接执行。
4. 所有省略都明确标注，并能继续阅读原文。预览、拟议修改、已执行结果各有清楚名称。
5. 查看和复制已有内容不会启动 Agent。思考、压缩和 Agent 工具仍属于 Job。
6. 状态要说明下一步：正在执行、等待回答、暂停、完成、失败、需要核查实际效果。恢复入口必须可操作。

## P0 日常工作必须顺手

### R01 输入框和命令补全

- 在输入框键入 `/`，候选列表就地出现，输入 `/mo` 即过滤到模型相关操作；显示名称、用途及当前快捷键。
- 明确 Tab 补全、Enter 选择/执行、Esc 关闭的区别。需要参数的命令先进入参数步骤，例如模型搜索和会话选择。
- 候选无匹配、配置不可用、执行失败均有对应状态；关闭菜单恢复草稿和光标。普通句子里的 `/` 不触发命令。
- `@` 引用可以搜索、确认、移除。界面区分“路径引用”和“已附加正文”；正文读取须在 Job 中完成并留下记录。
- 多行中文、emoji、组合字符、长粘贴、撤销/重做、文本选择与复制必须连贯。长粘贴可折叠为可展开对象，原文不能丢失。

**验收：** 不看帮助完成 `/ → /mo → 选择模型 → Esc 返回`；没有模型请求、草稿未丢。粘贴长代码后编辑中间一行，撤销并发送，输入原文一致。

### R02 可阅读的对话与工具块

- 用户输入、答案、工具、提问、错误使用一致而不同的层级。模型名、工作区和执行状态各有明确位置，避免重复挤在同一行。
- 保留工具开始和完成更新同一块的既有能力；默认显示名称、目标、状态、耗时和必要摘要，补齐展开与完整状态。运行、成功、失败、取消、结果未知分别呈现。
- 在主对话直接展开结果、打开原文、复制输出；错误显示关键原因和退出码。阅读工具无需进入 Job 审计面板。
- Markdown 的列表、表格、链接、代码块需要可读。代码和 diff 可选择适合内容的换行/横向阅读方式。
- 80×24 和 120×40 都保留输入和当前状态。查阅旧内容时新输出不强制拉到底，返回最新位置有明确动作。

**验收：** 阅读一次读文件、编辑、构建失败的完整流程；能找到并复制错误行，辨认哪个修改已经发生，期间新输出不打乱阅读位置。

### R03 长操作的真实反馈

- shell/build 日志在进程运行时可读；stdout/stderr 可辨认。只有耗时变化不算“实时日志”。
- 日志预览有界，省略和观察丢帧有说明；最终结果以持久记录为准。正文/日志更新不能阻塞用户输入。
- 显示当前工作阶段和停止入口。取消后不能将旧结果显示为新任务的完成。

**验收：** 一个分阶段输出、持续超过十秒的命令，在退出前能看到早期输出；期间查看旧消息、输入新要求和停止仍可操作。

### R04 运行中协作与提问

- 收到新要求后显示已接收、待处理/已生效状态，并说明正在执行的动作是否已发生。
- 单个问题可直接回复；同时存在多个问题时可以选择回答目标，也能取消目标发送独立要求。界面不暴露 Job 选择。
- 提问显示问题文本和回答入口。模型提供选项时呈现选项，同时保留自由输入；不从普通文本猜出选项。
- 停止、恢复和补充指令的入口及反馈统一。恢复后真实继续同一任务，失败不会伪装成完成。

**验收：** 流输出中收到“先解释，别继续写”，后续未启动的旧写动作不发生；两项同时提问分别得到正确回答；用户能看见暂停是否生效。

### R05 原文阅读 搜索与复制

- 对完整会话按原始消息文本搜索，不依赖终端软换行。结果含上下文，并能打开对应消息或工具原文。
- 旧历史分页进入同一阅读位置；超过预览上限的单条记录有继续读取入口，不能默默截断。
- 可以选择消息、代码块或工具输出复制；选中内容和复制成功可见。全屏鼠标捕获必须有完整的选中复制能力或可关闭。
- 退出后给出可直接使用的恢复命令，并按用户偏好保留可阅读结果。

**验收：** 在长会话中找到仅出现于早期消息尾部的约束；窗口改变后同一短语仍命中；能复制准确原文且不调用模型。

### R06 修改证据与异常恢复

- 按文件查看真实已应用变更，带上下文及行号；明确区分拟议修改、本次操作结果和当前 Git diff。
- 展示新增、修改、删除及未跟踪文件，不能漏掉新文件内容。并存的人为修改有说明；缺少基线时显示不可归因。
- 失败、认证失效、额度耗尽、写结果未知分别给出处理路径。未知写提供只读核查和记录结论入口，完成后由用户主动恢复。
- 如果必须到 CLI 处理，界面提供退出、完整命令和重开的步骤，避免当前会话独占导致提示不可执行。

**验收：** Agent 修改已有文件并新增文件，用户可核对真实内容；一次未知写中断后可完成核查和恢复，操作不被自动重放。

## P2 需要单独证明价值的能力

- 从旧消息编辑并开新分支：保留原始对话，明确新上下文来源及文件是否共享。
- 撤销任务的文件修改：与输入框 undo 分开；处理用户后续修改及无 Git 仓库场景。对话分支不等于文件回滚。
- 图片/PDF 附件：显示发送对象及大小；依赖模型能力和 Session 输入支持。
- `!` 运行用户命令：如果进入 Agent 工作历史，必须经过 Session/Job 执行；不能由 TUI 直接调用工具绕过归属和持久化。
- 分享、插件和复杂工作台：在核心交互达标后，根据实际工作流决定。

## 从交互到实现

### 技术选型

现有依赖见 [Cargo.toml](/Users/zzhang/Documents/ChatGPT/BONE/Cargo.toml:20)。Ratatui 提供渲染基础，完整产品交互仍要依靠合适的组件和状态设计。单纯换框架无法证明需求已经实现。

| 路线 | 应复用什么 | 成本和验证 |
| --- | --- | --- |
| Rust 与 Ratatui | 优先验证成品编辑组件，例如 ratatui-textarea；补全、对话和阅读组件按明确职责实现 | 保持单 package 和直接 Session 接口；必须验证 Unicode、选择复制和当前 Ratatui 版本兼容，不能继续扩展巨型按键分支 |
| OpenTUI 与 Solid | 现成输入、布局、滚动与鼠标能力，再实现 Agent 交互组件 | UI 仍使用 Rust core，但会改变原单 Cargo package 的分发形态；增加 UI 工程、运行时和进程通信成本，需要证明这些成本换来了更少手写交互和更好体验 |

ratatui-textarea 上游提供成品多行编辑部件；当前依赖采用拆分后的 ratatui-core/widgets。具体集成兼容性尚未实测。[编辑组件](https://github.com/ratatui/ratatui-textarea)、[当前依赖](https://github.com/ratatui/ratatui-textarea/blob/main/Cargo.toml) OpenTUI 提供输入、选择、滚动及 TypeScript/React/Solid 接入，OpenCode 使用该栈。[OpenTUI](https://github.com/anomalyco/opentui)

建议先用同一组真实交互验证编辑器、slash 补全、选择复制及长工具块，再选技术路线。比较体验、需要维护的自写代码、故障定位和安装成本；库功能表不能作为选型验收。

| --- | --- | --- |
| 输入与命令 | 编辑器、就地候选、参数步骤、按键路由 | 现有 Session 发送/停止/恢复；命令元数据保持一处维护 |
| 对话和工具 | 消息列表、工具块、展开/复制、浏览位置 | 现有持久事件与原文读取；工具实时输出需要新增有界观察入口 |
| 问题与异常 | 明确回复目标、确认、核查和恢复视图 | 现有显式 reply_to/resolve_write 可接 UI；结构化选项和行动确认需要扩充契约 |
| 原文与修改审查 | 搜索结果、原文分页、文件/diff 阅读 | 全会话文本检索；可靠变更基线，不能把拟议参数当作已应用 diff |
| 模型和会话 | 选择器、配置引导、保存偏好 | 现有原生 provider 接入；重命名/归档/默认选择持久化 |

采用普通结构体、函数和必要的具体组件。只保留一处活动浮层及明确按键优先级，避免帮助、搜索、选择器、详情同时争夺输入。UI 保存显示与草稿状态；执行状态来自 Engine，不创建第二个调度器。实时观察可丢帧，持久事件与动作归属不能丢。

## 交付顺序和验收方式

1. **先验证交互基础。** 用真实中文输入、`/`、`@`、长粘贴和选择复制验证组件路线；用户可以实际操作，再选框架。
2. **完成一条工程流程。** 正常聊天 → Agent 读/改文件 → 真实构建日志 → 运行中补充 → 回答提问 → 审查变更 → 暂停 → 重启续接。
3. **补齐阅读和失败流程。** 长历史检索、完整原文、认证失败、未知写核查恢复和首次配置。
4. **再做长期管理。** 会话整理、偏好、后续队列，以及有实际需求支持的分支/回滚等。

固定使用同一个小型真实项目、同样输入和终端尺寸，对 BONE、Pi、OpenCode 记录操作过程。对照应包含成功、长输出和失败，不只截一张空白首页。BONE 的新录屏同时保留会话事件，便于核对看到的操作确实发生。

测试分别证明：按键/文本行为、组件可见状态、Session 执行契约及真实工程结果。人工可操作验收检查命令是否容易发现、工具是否看得懂、阅读是否被打断、错误是否能继续处理。用户无需知道 Job、call ID 或 SQLite；仅通过这些操作完成工程流程，才可称为日常可用的 TUI。
