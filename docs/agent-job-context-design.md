# Job 与上下文：一个工作单元，两种信息视图

状态：2026-09-08，核心设计已落入 `bone-agent`。本文记录当前架构及仍需用真实模型评估的效果假设；可执行行为以 [Agent API](agent.md)和源码为准。

具体类型、所有权、函数边界和实现顺序见[代码实现设计](agent-job-context-implementation.md)。实现可以重写旧结构，不承担旧 API 兼容要求。

## 1. 设计决定

**Job 是有明确交付责任、拥有局部工作记忆、通过报告与外界协作的工作单元。**

保留 `Event → Kernel → Effect → Runtime → Event`。Rust Kernel 是唯一状态写入者；协调模型提出工作组织决策；Worker 推进具体工作；Runtime 执行模型、工具、定时器及必要的上下文 I/O。模型端口仍只执行一次调用。

Job 的四个部分分别回答四个问题：

| 部分 | 问题 | 性质 |
| --- | --- | --- |
| `Spec` | 做什么，范围是什么，怎样算完成？ | 当前工作契约 |
| `Context` | 继续这项工作需要记住什么？ | 局部工作记录与恢复记忆 |
| `Report` | 上层为了协调这项工作需要知道什么？ | 可替换的公开视图 |
| `Outcome` | 这次工作最终交付了什么？ | 一次封存的终态记录 |

这四部分属于同一个 Job，不是四个服务。`Context` 中的历史、`Report` 中的结论都不能覆盖 Kernel 的当前状态。进度只用于观察，不等于成果，也不决定是否完成。

不增加长期 Worker 身份、独立工作流引擎、全局共享聊天记录或常驻记忆模型。一次次 Worker 调用通过 Job 的局部记忆保持连续性。

## 2. 架构与职责

```text
用户原话与控制
       │
       ▼
Rust Kernel ── 调用指令 ──► Runtime ──► 协调模型 / Worker / 工具
       ▲                      │
       └──── 执行结果事件 ─────┘
       │
       ├── Job 状态、版本、拥有关系、等待与交付责任
       └── Context 记录、Report 和 Outcome 的有效提交

协调模型的视图：当前用户要求 + 活跃工作目录 + 相关 Report
Worker 的视图：当前 Spec + 自己的 Context + 待处理消息 + 必要成果
```

图中 Runtime 执行模型请求；是否需要调用、结果是否有效，仍由 Kernel 决定。高层可以把协调模型称为内核的语义部分，但当前 `struct Kernel` 不直接持有或等待模型。

全局协调模型负责新输入归属、根工作的创建与调整、跨工作冲突和用户层面的共同约束。根 Job 的 Worker 负责领域方案、局部委派、验证和成果整合。局部工具结果和子工作结果直接交给所属 Worker。

协调模型通过有界的工作目录读取接口按需展开活跃根工作、已知工作或证据。这个接口只读内核记录，不执行业务工具；查询结果由 Kernel 直接写成 Record 并在下一次模型调用中提供。它不会默认接收所有子工作历史。

只有新用户输入、明确的协调请求以及相关查询返回等需要语义处理的事件触发协调推理。普通进度、报告刷新和工具完成先更新状态或投递消息，不因一次工具操作多调用一次协调模型。Worker 发现跨工作影响时更新 Report 并显式请求协调。

## 3. 一个小的工作契约

保留现有身份、父子关系和版本机制。以下是领域形状，具体 Rust 字段组织可沿用现有类型：

```text
Job
  id / parent / version / state
  spec       { goal, scope, done_when, input_refs }
  context    { local_record, checkpoint, inbox }
  report     { summary, evidence_refs, version, as_of }
  outcome    Optional<{ kind, summary, evidence_refs, remaining, version, as_of }>
```

`goal / scope / done_when` 使用短的自然语言。`done_when` 同时说明预期交付和必要验证，不另建验收 DSL。简单问答的一句话契约就足够；不要求创建前先生成详细实施计划。

例如：

```text
goal: 查明刷新 token 后仍然返回 401 的原因。
scope: 调查客户端认证流程及相关服务端校验；本次只调查。
done_when: 给出根因与证据，区分已证实结论和未验证假设，指出修复位置。
input_refs: 用户提出该要求的原始输入。
```

原始输入由 Kernel 记录，按实际接收顺序提供。委派说明另外注明来自父工作，不能伪装成用户原话。模型填写的 `scope` 描述工作边界；实际能力仍由宿主和工具适配器限制，代码不能仅凭自然语言契约证明任意操作得到授权。

Job 划分采用一个标准：**有独立目标、值得保留的局部理解和明确交付对象，才拆成独立工作。** 读文件、搜索和普通验证通常是 Job 内的步骤。高度耦合的规划、修改、验证留在同一 Job。模型负责判断必要性；Kernel 限制活跃 Job 总量和委派深度。容量不足返回明确结果，不丢失请求或静默裁剪子工作。

## 4. 创建与局部委派

只保留一种 Job，实现上用创建来源区分交付归属：

| 来源 | 谁提出 | 交付对象 |
| --- | --- | --- |
| 用户输入 | 协调模型提出 Create 或 Update | 对应 Input 的交付责任 |
| 局部委派 | Worker 提出 `Delegate(spec)` | 父 Job |
| 输入解释所需的调查 | 协调模型提出有范围的 Investigate | 当前固定解释批次 |
| 已完成工作的跟进 | 当前用户要求或仍有效的父工作委派 | 新请求或当前父 Job |

`Delegate` 由 Kernel 直接验证并提交，不再为归属明确的每个子工作额外调用全局协调模型。子工作只能属于提交者，不能借委派重写已有目标、解除用户暂停或扩大工具权限。子工作继承相关原始要求、父工作的委派说明和显式选取的证据；不默认复制父工作全部历史。

创建子 Job 必须原子完成三件事：创建记录、建立拥有关系、向父 Job 投递 `ChildCreated` 回执，回执包括 child ID 和契约。父 Worker 的每次上下文都可见活跃直属子工作的简表。子工作终态后，再用 `DeliveryKind::Outcome` 投递权威 Outcome；历史子工作可按需读取。

创建提案由 CallId 标识；重复处理同一提交不能重复创建。父工作取消与创建提交按 Kernel 事件顺序裁决：先创建则随后级联取消；先取消则拒绝迟到创建。

父 Spec 的目标、范围或完成条件改变时，第一版默认撤销并取消活跃的拥有子树，由新父调用按新契约重新委派。已产生的成果仍可引用，未决外部效果仍须核对。普通追加材料和内部询问不触发这一规则；第一版不增加“自动猜测哪些旧子工作还能保留”的分支。

创建子工作不把历史 Input ID 重新变成新的用户请求。子工作的交付由父工作承接；根工作的 `InputFinished` 继续由原输入的 required jobs 决定。

## 5. 公开报告与正式成果

`Report` 是一份短的、可替换的工作说明。只强制正文和证据引用，不把每个句子拆成模型必须填写的复杂 schema。正文应覆盖相关结论、影响、未知项，以及需要上层决定的事项；没有的项目不必填空。

```text
结论：请求拦截器仍读取旧 token 缓存。
影响：修复会涉及共享认证拦截器，与认证重构工作有交集。
未知：并发刷新是否也会触发相同问题。
需要协调：确认由哪个工作负责修改该文件。
证据：代码位置、复现记录与测试输出的引用。
```

Worker 理解细节并写报告；Kernel 补充 job ID、当前版本、事件水位及真实状态。Report 与对应有效提案一起提交。旧版本报告保留在历史里，不继续充当当前报告。目标改变后目录立即显示新契约，并将旧报告标为待更新。

关键结论改变、出现阻塞、需要协调或准备交付时更新报告。普通工具进度不用重写它。`Outcome` 的 summary 可以直接形成最后一份公开报告，不要求模型在完成时写两遍相同内容。

证据引用指向已存在的记录或发布成果，携带来源 Job、产生时的版本/序号，以及可用的文件版本或内容标识。引用正文按需读取。跨 Job 默认共享报告和选中的成果，不共享工具历史或可变 Context。

Report 不是事实证明。需要确认时，协调者可以定向追问、读取有限证据或委派独立核查。不能因为报告说“已发送”就绕过工具执行记录里的 Unknown。

## 6. 消息、追问与完成的边界

每个 Job 有一个有界 inbox 视图，消息正文来自权威记录，不再复制一套消息历史。消息用已有事件序号标识，不增加独立消息版本计数；需要回答的消息使用该序号作为关联 ID。来源和类别由 Kernel 决定：用户要求、内部询问、创建回执、子工作交付和执行观察不能互相冒充。

ChildCreated、Outcome 和真实调用结果先进入权威记录，再按序号投影进 Job Context；子工作进入终态不依赖父 Context 容量。Busy 只拒绝尚未接收的新输入或询问，Delegate 在活跃 Job 容量不足时整批拒绝。相同进度会去重，工具正文按工具输出限额处理。

当前有效调用携带它已看到的事件水位。有效提案提交后才推进读取水位，但读取不等于回答：Kernel 另保留以询问序号为键的未决项，直到关联回答或明确的结束结果到达。提案可以同时提交局部笔记、可选 Report、对已知询问的关联回答以及下一步操作；不需要为一条回答增加新模型角色。

### 6.1 活跃 Job 的询问

协调者用 `Inquire(job, question)` 把一个范围明确的问题交给该 Job。Worker 在下一次调度边界用已有 Context 回答；同一 Job 不为答疑启动第二个并行可写 Worker。通常不打断在途调用，接收提案后再处理待答消息。

询问只获取理解或证据，不改变 Spec，不制造新用户授权。若问题要求新的实验或改变交付范围，Worker 返回“需要额外工作”及原因，由合法的创建或更新路径处理。普通工具等待、定时等待可因询问安排一次推理；明确的用户暂停不被询问唤醒。

询问有明确的处理结果：已回答、需要额外工作、当前不可回答、因取消或超时结束。目标 Paused 时直接向请求者返回不可回答，保留原暂停；等待用户必要信息时也可返回缺少该信息。请求者不得把没有回复解释为同意。

每个请求者对同一目标至多保留一个未决询问；全局未决 Inquiry 达到 `AgentLimits::inquiries` 时返回明确结果。依赖询问的等待也加入现有等待环检查，拒绝彼此等待。Stop、取消和用户控制仍走独立入口。

### 6.2 询问与 Finish 交错

若 Finish 提交前出现未读的新要求、创建回执或子 Outcome，Kernel 放弃这份完成候选并重新调度，让 Worker 读取新增消息。任何已接受但尚未结算的询问也阻止正常 Finish，即使模型已经看过问题并提交了 Continue。回答、需要额外工作、不可回答、取消或超时才结算询问；普通进度不会使完成失效。

同一提案可以回答已知询问并 Finish，校验以本次关联回答提交后的未决集合为准。出现完成候选时暂缓接收普通的新内部询问，排空有限已接受消息；用户控制仍可进入，避免持续询问让一项工作永远无法交付。当前有效输入解释批次保留一个关联询问入口，不受这项限流影响；接收后放弃旧完成候选并调度回答，避免“等待解释才能完成、又禁止解释所需询问”的互锁。

已经投递的内部询问可在未解释用户输入期间得到内部回答；回答只回原请求或解释批次，不向用户交付答案，不启动未授权写入。这样解释过程不会因全局交付门禁而等待自己。旧解释批次被新输入取代时，旧询问回答只留材料，不能恢复旧批次的决定权。

如果目标先完成、询问后到达，返回“已完成”及 Outcome 引用；请求者按下一节创建跟进工作。若取消先发生，未决询问以取消结果结算。回答按关联 ID 幂等接收，迟到重复回答不重复触发工作。

### 6.3 已完成 Job 的跟进

**终态不可重开，记忆可以复用。** 需要继续问已完成工作时，创建新的小 Job，以旧 Job 的冻结 Context/checkpoint 为来源，加入新契约和当前约束。这里不增加另一种 consultation 调用或长期 WorkerId。

```text
Job A：调查登录根因 → Completed + Outcome + 冻结记忆
                                      │
                                      ▼
Job B：基于原调查，解释并发场景的影响 → 新交付
```

来源关系不是拥有关系：B 的 parent 是当前委派者，或为空，不能是已完成的 A。A 的状态、Outcome 和旧 InputFinished 不改变。复用旧原话只提供背景，新的交付必须有当前请求或仍有效的父工作授权。

若 B 是为了澄清未解释输入而建立，交付对象仍是当前固定解释批次，继承调查工作及其子树的只读限制。其内部 Outcome 可以返回解释过程，不受普通根答复门禁阻塞，也不对用户交付答案或重建旧输入义务。归属随创建确定，Worker 不能自行把业务工作改成调查以绕过门禁。

默认只自动复用 Completed 工作；Failed/Cancelled 工作可以贡献显式成果引用，但不能通过自动分叉重新执行已取消目标。用户明确重试时创建新工作。所有复用都重新应用当前权限与约束，不复制过去的行动许可。当前进程保留来源记录；未来启用 retention 后，缺失来源必须返回明确不可用结果，并使用已有 Outcome 或重新调查。

## 7. 局部记忆与压缩

### 7.1 存储与模型输入是两件事

`Context` 保存本 Job 的真实输入、已提交工作笔记、调用与结果关系、inbox 和 checkpoint。记录属于 Kernel 管理的 Job 数据；`context.rs` 提供数据结构和有界投影。Runtime 负责读取外部证据等 I/O，并把结果交回 Kernel。模型适配器不藏可变会话或私有 Agent loop。

不再为每次模型调用克隆包含所有 Job 历史的全局 Snapshot。Effect 携带本次所需的冻结视图或不可变引用及读取水位。完整观察接口仍服务于宿主，不能直接复用为默认模型输入。

```text
Worker 请求 = 当前契约与约束
             + 尚未处理的消息
             + 局部 checkpoint 与近期有效记录
             + 本次必要的证据内容

协调请求   = 当前待解释原话与共同约束
             + 活跃根工作简表
             + 本次相关报告与查询回复
```

契约、未处理用户要求、当前暂停/取消状态、未决外部写事实始终由内核的当前记录提供，不能由压缩摘要替代。较早原话保留来源和按需读取能力；当前硬约束和更正不得只存在于可丢弃摘要里。

inbox、近期记录与选中证据是同一记录的不同入口，构造器按事件序号或证据 ID 去重，每条正文只展开一次。近期记录从 checkpoint 的覆盖水位之后开始；保留的摘要引用不再额外带上已被摘要覆盖的完整前缀。

### 7.2 先保留真实协议，避免伪造对话

第一版继续使用结构化 `submit_work`，同时保存按 Job 归属的真实执行记录及局部工作笔记。上下文连续性由这些记录提供，不要求为了看起来像聊天而合成 assistant 历史。

如果保留 provider 原生 replay，只保存模型真实返回的消息，并为实际的 `submit_work` 调用配对 Kernel 对提案的处理回执。业务工具藏在 proposal 的 operation 内；它不是模型直接发出的原生工具调用，不能伪造成某个 provider tool_call 的返回值。

`bone-llm` 已有带来源限制的 replay/tool-result 类型，按其真实协议使用。跨模型或从完成工作建立新上下文时，优先使用可迁移的 checkpoint、外部材料与来源引用；不复制不兼容的 provider 私有状态。不得把同一笔工具结果同时完整放进历史、results 和材料三处。

### 7.3 最少的版本规则

用 Job 契约版本、CallId 的提交资格和单调记录序号表达有效性。具体实现见[代码实现设计](agent-job-context-implementation.md)：Stop 撤销全部活跃调用与路由，CallId 不复用，因此不再额外维护 generation，也不增加 report_version、memory_generation 等平行版本系统：

- 目标、控制或需要 Worker 重新处理的用户要求改变时，撤销旧提交资格。
- Report、关联回答、工作笔记必须来自有效调用；失效提案只留审计记录，默认不混入当前工作记忆。
- 真实工具结果即使晚到也要保留执行事实，注明产生时的 Job 版本；尤其不能丢弃写入成功或 Unknown。旧版本材料按历史证据处理。
- checkpoint 只替代它明确覆盖的记录前缀；发布后到来的消息和执行观察保留在后缀。目标改变或 Stop 后到达的旧压缩结果不成为当前 checkpoint。
- 跨 Job 读取固定成果版本，Producer 后续变化不悄悄改写 Consumer 已读内容。需要新结果时，显式等待或读取较新版本。

### 7.4 有界选择先于压缩

宿主提供 Agent context payload 预算，并另行给模型 instructions、工具协议和输出留空间。构造器先选当前要求、未处理消息和近期必要记录；历史大输出以引用替代，最后才压缩较早工作记录。不能只截断尾部、丢掉工具结果或剪坏协议消息对。

压缩在 Worker 调用边界执行，使用已有 worker 模型与容量，是一种调用目的，不增加模型角色。它只产生 checkpoint，不执行业务工具；不会和同一 Job 的有效 Worker 并行修改记忆。摘要保留目标、已执行操作、关键发现、失败尝试、未解决项、证据引用和下一步，不要求保存隐藏推理。

压缩失败保留旧记录与 checkpoint，按一次模型调用失败形成 Failed Outcome，并结算相关询问；显式重试可建立使用这些记录的新工作，不自动无限压缩。必要输入在预算内仍放不下时，同样明确报告上下文准备失败，不能静默省略当前要求。

结束的 Job 移出默认活跃目录，但 Outcome 与 Context 仍保留在本进程的权威历史中。第一版不承诺跨重启恢复，也尚未实现历史正文的物理回收。后续 retention 必须先定义输入幂等收据、未决写、Delivery 读取授权和 evidence 引用的保留闭包；不能直接按 checkpoint 水位删记录。

## 8. 生命周期与交付

对外提供以下状态；内部如何存储与派生见代码实现设计，不额外引入“Agent 活着但 Job 不活着”的第二套生命周期：

```text
Ready → Running → Ready / Waiting / Paused
                  │
                  └── Completed / Failed / Cancelled

Waiting → Ready：工具、定时、依赖或被接受的消息使工作可推进
Paused  → Ready：有用户依据的 Resume
终态   → 无自动返回路径
```

Worker 通过 `Finish(outcome)` 申请完成。正常完成必须提交 summary 和对 done_when 的交付说明；需要验证的任务附真实证据。无法完成时可以提交失败及已产生成果。取消、执行异常等由 Kernel 根据真实事件形成相应 Outcome，不等待模型写报告。

正常完成时 Kernel 检查当前执行资格、必要消息读取水位、未决询问、工具状态和所有拥有子工作的终态。不能在同一提案开始工具并宣告完成；整个拥有子树的未决写入都阻止成功交付；不能让父工作在子工作仍执行时成功结束。父工作失败或取消时，立即撤销其拥有子树的执行资格，不等待模型答疑或外部清理才能进入失败/取消终态。

Pause 是拥有子树的执行门禁：撤销受影响的在途 Worker 提交资格，暂停新的业务执行，但不覆盖子 Job 自己的暂停标记。Resume 只解除本次继承门禁，不能顺带解除用户单独暂停的子工作。真实在途工具结果仍然入账，外部写的取消仍是尽力而为。

子工作失败或取消后，父工作收到明确 Outcome 并重新考虑；不会因为子工作“进入终态”就自动把父工作算作成功，也不机械地让父工作必然失败。父 Worker 根据原契约决定补救、解释失败或接受已有交付。

语义质量由负责工作的 Worker 承担；有明确机器验证要求时检查相应执行记录。Kernel 不宣称能证明任意自然语言目标已经满足。需要独立审查时委派普通验证 Job，不让全局协调模型逐条审批答案。

Outcome 在终态转换时与通知原子提交、只提交一次。根工作的正常最终答复来自该 Outcome；子工作 Outcome 投递仍活跃的父工作，父已终止时只记录观察，不再唤醒或修改其冻结 inbox；调查工作交给所属解释批次。现有非终态 Reply 可继续存在，但不能代替 Outcome，也不能满足完成等待。

Cancelled/Failed 后若外部写结果后来被确证，更新 Call 的真实事实并产生新的观察通知，不改写已发布的终态 Outcome；查询时同时显示原交付与最新外部事实。取消不等于外部回滚。

`InputFinished` 保持独立：原输入的 required jobs 全部进入终态后，按实际完成、失败、取消情况汇总。子工作不随意新增用户交付义务，后继工作也不改写旧收据。

## 9. 工作流只需要拥有关系和明确成果

父子关系只表达拥有和取消传播。证据引用只表达读取，不授予控制能力。父工作默认收到直属子工作卡片与 Outcome；其他工作只有经允许选取的报告和成果。

保留两种等待：

| 等待 | 满足条件 |
| --- | --- |
| `WaitForJob(id)` | 目标明确进入终态，投递 Outcome；不等于成功 |
| `WaitForResult(id, after)` | 目标在给定水位后显式发布成果，或结束后返回没有新成果的明确结果 |

提前成果通过 `PublishResult` 显式发布，复用证据记录的序号作为身份；不是任意 note、错误日志或 Report 非空。一次发布可以包含多条证据引用，发布本身不结束 Job。消费者消费固定版本，需要下一份时推进水位再等待。等待环在提交时校验。

等待建立时同时绑定所见的目标 Job version。目标契约改变后返回明确的依赖变化消息，让消费者重新选择；不能把另一版本目标的成果当成原来的交付。已消费成果保留历史版本，不自动改写消费者记忆。

父工作正常完成前必须处理已经收到的子 Outcome。与父工作无关的长期监控应由协调者根据用户意图建立独立根 Job，不能把拥有关系临时改成脱离管理的后台执行。

## 10. 实施顺序与验收

直接按新目标结构实现，不要求维持旧字段或双轨兼容。代码实现设计给出六步顺序：类型 → 上下文 → Kernel 生命周期 → Runtime → 询问/路由/压缩 → 适配与文档。每步同时迁移对应行为测试，最终更新公开 API、提示词和示例。

完整路径通过下列验收后，才能把本提案改为“已实施”；不能只更新类型便宣称上下文隔离完成。模型效果需要单独验证。

| 场景 | 必须观察到的结果 |
| --- | --- |
| A、B 并行，A 产生大日志 | B 和协调者默认输入没有 A 的日志；宿主仍可观察 A |
| Worker 创建两个子工作 | 父收到确定 ID 和契约；不用猜 ID 就能等待并整合 |
| 子工作产生 note 或工具错误 | 不误触发提前成果等待 |
| 子工作失败，父原本准备 Finish | 父重读失败 Outcome，不能直接提交旧成功候选 |
| 修改目标后旧报告、笔记、压缩晚到 | 不覆盖新目标上下文；真实外部效果仍入账 |
| 父契约改变时子工作正在执行 | 旧拥有子树失去资格；新委派依据新契约 |
| Finish 与询问先后交错 | 先接受询问则答完再完成；先完成则返回终态并走跟进 |
| 读过询问只提交 Continue，随后 Finish | 询问仍未决，不能越过答复责任 |
| 用户暂停后收到询问或子成果 | 子树门禁保持；恢复父工作不解除子工作自己的暂停 |
| 输入解释正在等待 Worker 的回答 | 内部回答能返回，业务写入和旧用户答复仍被暂扣 |
| 输入解释需要追问已完成工作 | 跟进调查向原解释批次内部交付，不因门禁互等 |
| 旧解释批次被取代后收到回答 | 不复活旧解释或制造旧输入的新交付 |
| Completed 后追加问题 | 新 Job 复用限定记忆，旧 Outcome/InputFinished 不变 |
| 压缩时新增工具结果或用户更正 | 新增后缀保留，旧版本摘要不覆盖当前事实 |
| 活跃工作、输入或 Inquiry 达到容量 | 明确 Busy/整批拒绝；控制保持可用 |
| 会话历史长期增长 | 当前随进程保留；物理 retention 作为明确的后续阶段 |
| inbox 满时子工作结束 | Outcome 仍入账且可消费，不阻塞子终态 |

受控测试验证这些状态与投递规则。另用真实模型比较单 Job 与多 Job 在同组任务上的原始要求保留、重复调查、错误完成、无谓拆分、上下文用量及完成耗时。评价 Report 是否足以支持正确协调决策，不把“摘要更短”当作唯一目标。

## 11. 保持范围小

现有有界并发、每 Job 单一提交资格、Stop、Unknown 写入确证、输入幂等、观察流继续保留。共享文件的并发修改由宿主隔离或工具的冲突检测处理；Context 独立不等于资源隔离。

第一轮不新增通用 DAG 引擎、角色市场、权限 DSL、向量记忆库、自动跨 Job 全文广播、跨重启恢复或通用分布式事务。上述能力只有在明确场景证明必要时再扩展。

## 12. 参考与本项目的取舍

- [Claude Code subagents](https://code.claude.com/docs/en/sub-agents#resume-subagents)：独立上下文和恢复后的追问。本设计保留记忆复用，但不把可恢复 Agent 实例的生命周期直接等同于 Job 终态。
- [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)：中间探索留在子工作，上层接收摘要。BONE 进一步区分可替换报告与封存交付。
- [Kimi CLI 的 Agent 协议，固定提交 86f1364](https://github.com/MoonshotAI/kimi-cli/blob/86f136422a0aae6b217ea49e7ea1d2e8a1defcd2/src/kimi_cli/tools/agent/description.md)：优先向已有背景的实例继续提问。本设计将终态后的继续表达为复用记忆的新工作。
- [Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：局部压缩、工作笔记、上下文隔离和按需读取相互补充。本设计分别处理 Worker 恢复记忆与面向协调者的报告。

以上是设计参考，不代表这些产品采用 BONE 的 Job 协议。当前实现可从 [ports.rs](../crates/bone-agent/src/ports.rs)、[context.rs](../crates/bone-agent/src/context.rs)、[kernel](../crates/bone-agent/src/kernel/mod.rs)和 [model.rs](../crates/bone-agent/src/model.rs)核对。
