# 旗舰 core 工程验收

## 首轮：失败，不构成工程能力证明

冻结核心 `f468c0b`、`chatgpt:gpt-6-luna`、48,000 字符上下文、每输入 48 次调用；复用现有 Codex 订阅。工程合同要求在隔离 BONE 仓库实现源码搜索、安全局部编辑及后续原生工具目录发现，所有执行仍经 Job。任务、十阶段自然交互、预算和独立功能检查在运行前冻结。

首轮在第一阶段耗尽额度：318.24 秒、48 次模型调用（其中 11 次摘要），没有源码修改。全部响应报告的 token 合计 304,679，费用未知。尚未进入后续中断、更改规格、停止/重启和最终回查阶段；这些检查标记为未执行。没有功能交付，因此没有把未来工具缺失计作已实现功能的故障。完整失败保存在 `trial1-failure.json` 及其指向的私有目录。

## 失败后的诊断与最小修复

- 原生请求重建发现三次有界 WORK 历史替换了整个 `chat_history`。Rig 的系统 preamble 也存在这个数组里，因此丢失了约 2.9k 字符的 Job、当前输入、停止及权限规则。对应源码预览仍有约 28–30k 字符，不能归因为没有源码窗口。修复保留原生请求模板并追加派生历史；用实际协议 fixture 验证系统指令、原始输入、工具配对和请求上限。
- 模型摘要曾作为系统消息进入后续请求，并把原文的“CLI 后续再做”误归纳成当前要求。改为明确标记的普通背景资料，保留原摘要文本，原始输入及最新约束优先。
- 摘要多次重复仍以原文保留的 ACTIVE 合同，工程发现很少。调整摘要指令，优先保留已读代码的符号/定位、已验证结果、未知项与下一步；从工作集中移除的历史要求仍保留精确承诺与来源。这项模型行为收益需要真实再验，不能用提示词字符串测试宣称成功。
- 独立公开 API fixture 复现：父输入已经交付失败说明后，默认恢复仍让保留的失败后代重新执行。恢复规则使用已有输入来源与事件顺序，保留原输入和预算，并区分自动恢复与 Agent 当前显式重试；同时验证独立排队工作仍可执行。

修复后统一门禁：121 项 Rust 测试通过、1 项忽略；格式、全部 targets Clippy（warnings 为错误）、全部 features 编译及 CLI build 均通过。恢复逻辑另经只读交叉审查，未发现阻断项。第二轮真实任务尚待记录。第二轮保持原任务、模型、48k 上下文和预算；首轮失败永久保留，不以增加资源掩盖结果。一次再验也不构成统计性的消融结论。
