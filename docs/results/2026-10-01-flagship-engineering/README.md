## 首轮：失败，不构成工程能力证明

冻结核心 `f468c0b`、`chatgpt:gpt-6-luna`、48,000 字符上下文、每输入 48 次调用；复用现有 Codex 订阅。工程合同要求在隔离 BONE 仓库实现源码搜索、安全局部编辑及后续原生工具目录发现，所有执行仍经 Job。任务、十阶段自然交互、预算和独立功能检查在运行前冻结。

首轮在第一阶段耗尽额度：318.24 秒、48 次模型调用（其中 11 次摘要），没有源码修改。全部响应报告的 token 合计 304,679，费用未知。尚未进入后续中断、更改规格、停止/重启和最终回查阶段；这些检查标记为未执行。没有功能交付，因此没有把未来工具缺失计作已实现功能的故障。完整失败保存在 `trial1-failure.json` 及其指向的私有目录。

## 失败后的诊断与最小修复

- 原生请求重建发现三次有界 WORK 历史替换了整个 `chat_history`。Rig 的系统 preamble 也存在这个数组里，因此丢失了约 2.9k 字符的 Job、当前输入、停止及权限规则。对应源码预览仍有约 28–30k 字符，不能归因为没有源码窗口。修复保留原生请求模板并追加派生历史；用实际协议 fixture 验证系统指令、原始输入、工具配对和请求上限。
- 模型摘要曾作为系统消息进入后续请求，并把原文的“CLI 后续再做”误归纳成当前要求。改为明确标记的普通背景资料，保留原摘要文本，原始输入及最新约束优先。
- 摘要多次重复仍以原文保留的 ACTIVE 合同，工程发现很少。调整摘要指令，优先保留已读代码的符号/定位、已验证结果、未知项与下一步；从工作集中移除的历史要求仍保留精确承诺与来源。这项模型行为收益需要真实再验，不能用提示词字符串测试宣称成功。
- 独立公开 API fixture 复现：父输入已经交付失败说明后，默认恢复仍让保留的失败后代重新执行。恢复规则使用已有输入来源与事件顺序，保留原输入和预算，并区分自动恢复与 Agent 当前显式重试；同时验证独立排队工作仍可执行。

## 验证状态

修复后统一门禁：121 项 Rust 测试通过、1 项忽略；格式、全部 targets Clippy（warnings 为错误）、全部 features 编译及 CLI build 均通过。恢复逻辑另经只读交叉审查，未发现阻断项。第二轮保持原任务、模型、48k 上下文和预算，仍在第一阶段失败：222.05 秒、48 次调用、11 次摘要、两个 Job、没有源码修改。37 个完成的 WORK 响应均保留 BONE 系统指令，provider 确认推理强度为默认 medium；290,885 个已报告 token，费用未知。见 `trial2-failure.json`。这证明修正请求构造不等于已经具备工程执行能力。

第三轮仅把同一 `gpt-6-luna` 的原生 reasoning effort 设为 high；代码、任务、上下文和额度不变，实际回执已确认 high。557.46 秒内耗尽 48 次调用，其中 18 次摘要，仍没有源码修改；327,961 个已报告 token，费用未知。见 `trial3-failure.json`。提高推理强度没有解决这一配置下的工程推进问题。

独立只读诊断未发现新的工具配对或持久数据丢失证据：两轮都没有持久工具错误，各三次 shell 成功，全部 29 次摘要均没有覆盖所属 Job 最新的工具批次。对 `src/tools.rs` 的原始读取范围重复率分别为 77.2% 和 87.8%，但原始工具返回范围不等于每次 WORK 实际看到的投影。部分摘要错误地声称不能编辑或执行工具，与同 Job 已成功的 shell 记录矛盾。现有摘要降权和原文回查保留了纠正途径，不能保证模型总能正确使用它们；再加一条提示词只是尚未验证的假设。完整事件 ID、统计和边界保存在各 trial 的 `analysis/rig-independent` 工件中。

第四轮只把上下文改为 128,000 字符，继续使用 high 和同样的调用额度。2 次调用后，模型询问完整合同中的 CLI 发现条款是否属于当前阶段；原始计划确实同时包含后续条款，不能把这次合理提问算作重复读取或完成。保留原始 trial4 的提问、暂停和全部证据，在新的工件目录通过 SQLite backup 继续同一 Session；普通用户输入只澄清“先实现 search_files/edit_file，CLI 留在后续”，不提供实现或验收答案。续跑保留原输入身份、原预算、原 2 次调用和 12.18 秒累计时间，另记澄清输入。

所有失败永久保留；单次配置实验不构成统计性的消融结论。并行的 Sol 工程工具备用实现位于独立私有目录，绝不作为 BONE 自主产物记分。其首次独立功能验收 26/27 通过：短行搜索的 snippet 包含太多后续行，提前占满输出上限，未满足默认页条数；保留该失败后修复再验。

第四轮澄清后的续跑确实修改了源码，并在首次修改后响应“先解释”：独立持久证据审计确认所有 Job 没有新写入或 shell，文件哈希一致，交付精确匹配输入，旧工作仍在队列中。随后按修改后的规格继续实现并运行了自身测试，但第三阶段在 600 秒内没有交付，因此原门禁仍失败。累计 50 次模型启动、4 次摘要、769.86 秒，未知写为空；被中止的调用用量未知，完整费用和完整 token 不填零。见 `trial4-timeout.json`。从该暂停点的补充恢复必须另行标记，保留原输入已用的 36/48 次预算，不能覆盖这次时限失败。

## 摘要任务边界修复与补充恢复

第四轮超时后的两次补充恢复，分别使用 high、medium，在同一个原输入、同一份工程历史上再次遇到 180 秒摘要超时。两次都有大量流式正文，包含模拟工具调用及重复字符；并非没有响应。原生工具调用没有发生，未知写为空。固定 Rig 的 ChatGPT 订阅 wire 会移除 `max_output_tokens`，所以不能把本地摘要的 2048 配置当作服务端输出上限。短普通调用仍成功，但这不证明摘要路径正常。

最小修复是在摘要资料之后追加原生用户任务：本次只总结，不能继续执行历史工程任务；仅本次摘要没有工具。它先计入请求固定开销，再选择历史，不创建持久输入、Job 或额外调用。独立离线比较同一失败快照：历史与 covered IDs 完全相同，请求由 119,229 增至 119,800 字符，低于 128k。这里比较的是重建的原生请求，不是捕获的 HTTP 包。见 `summary-request-comparison.json`、`summary-fix-summary-patch-review.json`。实际协议回归和完整统一门禁通过，见 `summary-fix-gates.json`。

补充实验沿用 `aec1fa3` 的工具，仅应用这两处摘要实现修改，没有引入 Sol 工具实现或修改自主候选源码。6-luna/medium 的下一次摘要在 19.719 秒完成，第三阶段随后交付，普通“继续”、原始三项承诺回查、自然“停止”也完成。累计仍包含所有失败：62 次模型启动、5 次完成摘要、1,205.77 秒。独立审核确认回查实际读取原输入两页；解释/回查窗口所有 Job 没有新写或 shell，哈希不变；Session 原生暂停、未知写为空。原输入仍 pinned/queued，因此这项回查不能宣称冷历史检索。两个旧输入尚未结算，后续阶段和功能验收仍待完成，原门禁继续保留 `FAIL_time_cap`。见 `summary-fix-phase1-6-review.json`。

这一次成功恢复说明修复帮助了这个具体故障，不是统计性消融结论，也不能证明任意长度、任意仓库的工程成功率。只读架构交叉审查未发现所审边界的新阻断项，范围与限制见 `architecture-review.json`。

## 后续四阶段与独立功能纠正

新 CLI 进程完成第 7–10 阶段，累计 128 次调用、9 次完成摘要、1811.10 秒。第 8 阶段通过原生 `input_resolve` 将原始请求标为 completed，将先前暂缓 CLI 的澄清标为 superseded；原预算仍分别为 2/48、9/48，没有重置。第 10 阶段前原请求已离开工作 history，模型确实再次读取原始事件并找回三项承诺。所有 Job 的第 2、5、10 阶段均无新写或 shell，文件哈希一致；旧停止请求没有重放，最终队列与未知写为空。

这些执行事实不保证生成代码正确：独立功能检查第一次只有 24/27。进程内随机游标密钥导致正常分页跨进程失效，重复的长 snippet 使简短输入也提前用尽输出额度。第 9 阶段要求的真实源码搜索与临时示例编辑演示也未执行，Agent 在最终答复中明确承认了这一点。冻结覆盖审计虽通过，仍不能替代这项未完成义务。证据见 `trial4-independent-final-review.json`、`trial4-candidate-functional.json`。

新的补充工件用 SQLite backup 继续同一 Session，向 Agent 提供三个外部失败现象，不提供替代实现。19 次调用、119.82 秒后，游标改为稳定校验，snippet 缩小，同一冻结功能检查达到 27/27。完整门禁随后发现一处未使用变量；另一次明确的编译诊断输入用 6 次调用、25.03 秒清理，未抑制警告。最终源码与已通过 27/27 的版本仅少这一条未使用声明，逐字比较已验证；独立 fmt 和全部 targets、全部 features Clippy 通过。`correction-*`、`lint-correction-*` 保留每次结果和失败。

最后在私有源码副本中编译候选工具，仅追加已经审查的两处摘要任务修复，未改候选工作区源码。补充演示在同一 Session 原生执行：`search_files` 找到 `src/runtime.rs:1119`（byte offset 41187），核对完整 SHA-256；创建唯一临时文本，读出原始 hash，通过一次 `edit_file` 将 `alpha\nbeta\n` 非级联替换为 `beta\ngamma\n`，读回核实后用 Job 内 shell 删除。11 次调用、45.45 秒，所有操作有原生 Job/call/result 配对，源码哈希不变。见 `candidate-demo-result.json`、`final-delivery-review.json`。
